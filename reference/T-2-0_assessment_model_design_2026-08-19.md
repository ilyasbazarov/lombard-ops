# `T-2-0` · Проектирование модели оценки: варианты и их цена · 2026-08-19

> **Объект замера определён:** `sql/ddl/lombard_ops.sql` (таблица `assessments`),
> `03_BUSINESS_SPEC.md` §5, `12_UX_CONTRACT.md` §3.5 — все существовали до этой сессии.

**Класс работы:** A. **Метка:** `продукт`, пункт контракта готовности **4**.
**Формат назначен `ADR-058` п.3:** архитектор предъявляет варианты, каждый со стоимостью в сессиях
и ценностью; выбор делает владелец по паре «ценность/сложность» с учётом даты поставки.

---

## 1. Что именно выбирается

`ADR-058` зафиксировал ТРЕБОВАНИЕ (факторы — настраиваемый справочник, новые поля без правки кода)
и оставил задаче проектирования ровно два вопроса:

1. **Физический вид записи применённых факторов** в `assessments` — вложенная запись, отдельная
   таблица или JSON.
2. **Где живёт сам справочник факторов** и чем он правится.

Всё остальное решением уже закрыто: фиксированные колонки по факторам не заводятся, `total_discount`
и набор применённых факторов пишутся записью на осмотр, пять факторов `03 §5` — стартовое
СОДЕРЖИМОЕ справочника, а не схема.

**Что уже стоит в репозитории и менять не предлагается:** таблица `assessments`
(`sql/ddl/lombard_ops.sql`) с полями `assessment_id`, `contract_id`, `vehicle_id`, `make`, `model`,
`vin`, `year`, `mileage`, `total_discount`, `base_price`, `max_loan`, `photos_gcs_path`, `assessor`,
`created_at`. Ни один вариант ниже её не переписывает — все три только ДОБАВЛЯЮТ хранение факторов.

## 2. Три варианта

### Вариант 1 — вложенная запись в `assessments` + справочник файлом

```
applied_factors ARRAY<STRUCT<
  factor_id STRING, value STRING, weight NUMERIC, discount NUMERIC >>
```

Справочник — `data_inbox/factor_catalog.csv` → импорт тем же приёмом, что уже работает у справочника
ликвидности (`tools/catalog_import.py`, `ADR-060`): шапка сверяется, значения нормализуются, счёт
принятых и отклонённых печатается с причиной. Экрана редактирования в v1 нет.

- **Стоимость: ~1 сессия.** DDL-правка одной колонкой, импортёр по готовому образцу, форма и API
  читают один объект.
- **Ценность.** Запись осмотра атомарна: один `INSERT`, одна строка, история не разъезжается.
  Аналитика по факторам доступна через `UNNEST` — «какой фактор чаще всего снимает цену» считается
  одним запросом, и это ровно тот вход, который понадобится для калибровки справочника после даты.
  Добавление фактора не трогает схему.
- **Цена, названная честно.** Правка одного применённого фактора задним числом переписывает всю
  строку осмотра. Для v1 это не проблема: осмотр — событие, а не редактируемая карточка.

### Вариант 2 — отдельная таблица `assessment_factors` + `factor_catalog` в BigQuery

Строка на каждый применённый фактор: `assessment_id`, `factor_id`, `value`, `weight`, `discount`.
Справочник — своя таблица, редактируемая экраном.

- **Стоимость: ~1,5 сессии.** Две таблицы вместо одной, джойн в каждом чтении карточки и реестра,
  отдельный экран правки справочника (а он `ADR-060` п.3 из v1 уже сокращён до просмотра).
- **Ценность.** Самая чистая аналитика и точечное обновление одного фактора. При портфеле около
  сотни активных договоров ни то, ни другое в v1 не окупается.
- **Цена.** Осмотр перестаёт быть одной записью: сбой между вставками оставляет полуосмотр, и это
  надо чинить транзакцией или проверкой целостности — работа, которой в бюджете нет.

### Вариант 3 — JSON-колонка + справочник в конфиге

`applied_factors JSON`, справочник — файл в GCS рядом с `connector/config.json`.

- **Стоимость: ~0,5 сессии.** Самый дешёвый путь.
- **Ценность.** Форма и API пишут произвольную структуру, схема не мешает вовсе.
- **Цена.** Аналитика по факторам — только JSON-функциями, без типов и без контроля состава;
  ошибка формы (опечатка в `factor_id`) обнаруживается не при записи, а при разборе через недели.
  Это ровно тот класс тихого отказа, который в проекте уже дорого стоил.

## 3. Сравнение по паре «ценность / сложность»

| | Вариант 1 | Вариант 2 | Вариант 3 |
|---|---|---|---|
| Стоимость, сессий | **~1** | ~1,5 | ~0,5 |
| Осмотр — одна запись | да | нет | да |
| Аналитика по факторам | `UNNEST`, типизированная | лучшая | слабая, без типов |
| Контроль состава при записи | схемой | схемой | нет |
| Добавление фактора без правки кода | да | да | да |
| Экран правки справочника | не нужен (v1 — просмотр) | нужен | не нужен |

## 4. Рекомендация

**Вариант 1.** Он берёт всю ценность, которая в v1 реально используется — атомарную запись осмотра,
типизированный контроль состава и аналитику через `UNNEST`, — за цену на пол-сессии больше самого
дешёвого пути. Вариант 2 дороже на полсессии и окупался бы при тысячах осмотров и живом
редактировании справочника, а редактирование из v1 уже сокращено до просмотра. Вариант 3 экономит
полсессии ценой тихих ошибок в данных, которые проявятся после даты поставки.

Дефолт `ADR-058` п.4 (пять факторов с фиксированными весами, справочник структурой без экрана)
вариантом 1 не нарушается, а исполняется: структура есть, экрана нет, содержимое правится файлом.

## 5. Что закрывает выбор

- `sql/ddl/lombard_ops.sql` — колонка `applied_factors` в `assessments`.
- `02_DATA_CONTRACTS.md` §2 — строка `assessments` дополняется физическим видом.
- `03_BUSINESS_SPEC.md` §5 — таблица факторов помечается как стартовое содержимое справочника с
  назначенным местом хранения.
- `T-2-5` (форма осмотра) получает контракт записи и перестаёт ждать `T-2-0`.
- `T-2-4` (справочник ликвидности) остаётся независимым: у него свой справочник и свой импортёр.

Выбор фиксируется решением в `06_DECISIONS_LOG.md` (`ADR-091`) той сессией, которая его получит.
