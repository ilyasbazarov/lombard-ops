## Шаг 6-е — отбивает ли транзакция только на чтение попытку записи (под `LOMBARD_RO`)

**Первая попытка — не засчитана, дефект команды.** Команда шага, как она была расписана в брифе,
не содержала строку подключения к файлу базы для `isql`. Все восемь операторов отбились
`Use CONNECT or CREATE DATABASE to specify a database`, код возврата `1`. Это гэп наблюдения
(отказ не по режиму транзакции, а по отсутствию соединения), а не результат проверки. Исправление:
в вызов `isql` добавлена строка подключения `localhost/3057:D:\PawnShop_DOL\DB\DOL.FDB` —
та же, что зафиксирована в `reference/T-0-5_readonly_measurement_2026-08-11.md`.

**Вторая попытка — не засчитана, недостоверный вывод.** Файл результата не был очищен перед
запуском и содержал хвост первой (неудачной) попытки поверх нового вывода: в одном логе смешались
восемь строк `Use CONNECT...` от старого прогона и результат нового. По второму `UPDATE` (в
транзакции только на чтение) строки отказа не было видно, но лог признан ненадёжным целиком —
запрошен чистый повторный прогон с очисткой файла результата перед стартом.

**Третья попытка — чистый лог, код возврата `0`.**

```
COMMIT;
SELECT COUNT(*) AS CNT_ALIVE_RW FROM DEPOSIT_TYPES;

CNT_ALIVE_RW
============
           7

UPDATE DEPOSIT_TYPES SET ID = ID WHERE 1 = 0;
COMMIT;
SET TRANSACTION READ ONLY;
SELECT COUNT(*) AS CNT_ALIVE_RO FROM DEPOSIT_TYPES;

CNT_ALIVE_RO
============
           7

UPDATE DEPOSIT_TYPES SET ID = ID WHERE 1 = 0;
COMMIT;
```

Первое изменение (обычная транзакция) прошло без ошибки — ожидаемо, это контроль исправности
пробы (уже подтверждено 2026-08-11 шагом 6-г). `CNT_ALIVE_RW` и `CNT_ALIVE_RO` равны `7` — то же
число, что и в замере 2026-08-11, данные не менялись.

**Второе изменение (транзакция только на чтение, измеряемое) — тоже прошло без строки отказа.**
После `UPDATE ... WHERE 1 = 0;` в режиме `SET TRANSACTION READ ONLY` в логе сразу следует `COMMIT;`
без единой строки ошибки — ни `Statement failed`, ни любого другого текста отказа.

## Вердикт

**Названное в брифе стоп-условие сработало буквально:** «попытка изменения в транзакции только на
чтение прошла БЕЗ отказа» (правило приёмки поправки `ADR-032`, раздел «Исходы шага 6-е»).
Компенсирующий контроль, на котором стоит решение `ADR-032` («гранты `PUBLIC` не отзываются,
read-only держится нашим слоем через транзакцию только на чтение»), фактом не подтверждён — он
**опровергнут**: под учётной записью `LOMBARD_RO` режим `READ ONLY` на клиентской стороне запись не
блокирует.

**Действие по правилу брифа:** учётная запись `LOMBARD_RO` дальше в этой сессии не используется.
Шаг 6-ж не исполнялся. Вопрос заведён в реестр заново (`Q-16`) и возвращён архитектору — решение
`ADR-032` требует пересмотра, отзыв прав `PUBLIC` этой сессией не производился и не разрешён.

## Итог

Приёмка `T-0-5` **не закрыта**. Шаг 6-е измерен и провален по своему собственному критерию
(отказ ожидался, отказа нет). Шаг 6-ж не измерялся — учётка выведена из использования до решения
архитектора. Переезд чтения БД в класс A (условие `ADR-032`) **не наступает**.
