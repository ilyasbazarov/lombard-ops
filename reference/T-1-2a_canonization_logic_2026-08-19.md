## Файлы

- `sql/canonization.sql` — SQL канонизации (BigQuery Standard SQL, `CREATE OR REPLACE VIEW`/
  `FUNCTION` поверх `lombard_ops.raw_*`): дедупликация снапшота, `status_raw`, детектор продлений
  (обе ветви + `OR`), canonical view со смещением от плановой даты, единственная реализация
  статуса `03 §1` (`ADR-089` п.2, портирована дословно из `functions/cf_daily/status.py`).
- `connector/canonize/duckdb_runtime.py` — загружает и исполняет ЭТОТ ЖЕ текст на DuckDB. Три
  точечные адаптации СИНТАКСИСА (не логики), исчерпывающий список — докстринг файла: снятие
  обратных кавычек, `EXCEPT(col)` → `EXCLUDE(col)`, порядок аргументов `DATE_DIFF` (BigQuery
  `DATE_DIFF(a,b,part)` = a−b; DuckDB `date_diff(part,a,b)` = b−a — та же разность, замена
  единственного вызова).
- `connector/canonize/fixtures.py` — билдеры фикстур слоя сырья.
- `connector/canonize/test_canonization.py` — прогон, 11 проверок (шаги 1–10 брифа, шаг 7/8 —
  один прогон, печатающий таблицу эквивалентности).

## Решения исполнителя, зафиксированные этой задачей

- **`renewed_date` при срабатывании обеих ветвей — более поздняя из двух дат** (явный `CASE`, не
  `GREATEST`: в BigQuery `GREATEST` с любым `NULL`-аргументом возвращает `NULL`, а здесь нужна
  дата даже когда сработала только одна ветвь). Брифом эта деталь не зафиксирована числом —
  решение реализации, не гэп значения.
- **Активность договора для canonical view — `contract_state = 0` (`OPEN`)**, справочник кодов —
  дословно из `reference/T-0-4a_renewal_detector_measurement_2026-08-18.md`, шаг 12
  (`contract_state_catalog`).
- **Оффсет и статус вынесены в переиспользуемые SQL-функции** (`lombard_ops.offset_days`,
  `lombard_ops.status_for_offset`) — canonical view и таблица эквивалентности (шаг 8) используют
  РОВНО ОДИН И ТОТ ЖЕ SQL-код статуса; таблица эквивалентности не байпасит canonical view, она
  вызывает тот же путь с синтетическим `today` вместо `CURRENT_DATE()`.
- **Дедупликация снапшота применена к `raw_contracts` и `raw_contract_states`.** `raw_operations`
  дедупликации не требует в этой задаче: ветвь «Погашение» агрегирует по `deposit_id` через
  `MAX(op_date)` и считает DISTINCT договоров — повтор той же операции в двух снапшотах не меняет
  ни максимум даты, ни множество затронутых договоров.
- **Три точечные адаптации синтаксиса для офлайн-прогона на DuckDB** (не логики) — исчерпывающий
  список в докстринге `connector/canonize/duckdb_runtime.py`.
