## 2. Способ 2 — пробные подключения через `access_point.py` (дал ответ)

### 2.a. Доставка чистого файла `charset_probe.py` на сервер — отдельная грабля

Первая передача файла через Notepad (тот же метод, что использовался ранее для PowerShell-скриптов
без кириллицы) дала `SyntaxError` при запуске на сервере. HEX-дамп байт подтвердил: файл на диске
сервера лежит в кодировке **Windows-1251**, хотя отправлялся как UTF-8 — кириллица в докстринге и
символ длинного тире (`—`) декодировались как ВАЛИДНЫЙ cp1251-текст, не как мусор, то есть отказ не
визуальный, а фактический — интерпретатор Python получил не те байты, которые были в исходнике.

Причина подмены НЕ установлена окончательно. Подозрение — системная замена кодировки в буфере
обмена RDP конкретно для файлов, содержащих не-ASCII символы; воспроизведено дважды, включая явную
запись через PowerShell `[System.IO.File]::WriteAllText(..., [System.Text.UTF8Encoding]::new($false))`
— результат на диске сервера всё равно оказался cp1251. Точный механизм не подтверждён измерением,
и это НЕ подставляется правдоподобным объяснением дальше данного абзаца.

**Принятое решение — не диагностировать RDP-буфер дальше, а убрать сам класс входа:**
- файл `charset_probe.py` переписан целиком на ASCII: кириллица убрана из ВСЕХ строк, исполняемых
  интерпретатором (сообщения, докстринги, комментарии — заменены на транслит), длинное тире тоже
  убрано (дефис не спасал сам по себе, но при чистом ASCII вопрос снят полностью);
- доставлен методом, уже проверенным для ZIP-кода агента на шаге 6 — **base64 + `certutil -decode`**,
  с разбиением на 2 части и сверкой SHA-256 на каждом шаге. Первая попытка доставки одним куском
  тоже разошлась по хэшу (то же подозрение на потерю/подмену символов в RDP-буфере при большом
  объёме, что и в шаге 6) — закрыто разбиением.

**Обобщение для `10_GCP_INFRA_PLAYBOOK.md` (раздел 5):** правило «base64+certutil со сверкой
SHA-256» ранее было записано только для ZIP/бинарных объёмных передач (шаг 6). Замер этой сессии
показал, что оно требуется и для ЛЮБОГО текстового файла с НЕ-ASCII содержимым, даже небольшого —
класс отказа (потеря/подмена символов в RDP-буфере) один и тот же, отличается только форма
проявления (для ZIP — рассинхрон хэша целиком, для текста — тихая перекодировка, не дающая ошибки
копирования, но дающая `SyntaxError` при запуске). Правка внесена, раздел 5 ниже.

### 2.b. `[WinError 193] %1 не является приложением Win32` — несовпадение разрядности

После доставки чистого ASCII-файла проба запустилась, но упала при попытке загрузить
`fbclient.dll` через `ctypes`/`fdb`.

Найдено: `C:\Program Files (x86)\Firebird-2.5-PawnShop\bin\fbclient.dll` — **32-битная** (каталог
`Program Files (x86)` подтверждает: сервер Firebird на этом сервере установлен как 32-битный
процесс). Python 3.14.7, установленный шагом 5-Б/6 (`11_INFRA_FACTS.md`, раздел «Среда сервера
ERP»), — **64-битный** (`amd64`, стандартный установщик `python.org`). 64-битный процесс не может
подгрузить 32-битную DLL через `ctypes` — это ограничение платформы Windows, не дефект кода.

### 2.c. Отклонённый путь — 32-битный Python (найден, НЕ применён)

Первая попытка исправления — установить `python-3.14.7.exe` (win32-инсталлятор с `python.org`)
параллельно с уже стоящим 64-битным. Установка Python прошла, но зависимость `cryptography`
(нужна `jwt_signer.py`, уже часть кода агента) отказала: для Python 3.14 win32 на PyPI нет готового
`wheel`, `pip` собирал из исходников (Rust/`maturin`), а на сервере нет MSVC-линкера — сборка упала.

Проверено локально (`pip download --only-binary=:all: --platform win32`), что `cryptography`
перестала публиковать 32-битные пакеты для Windows начиная с последних версий, но версия `48.0.1`
ещё публикует (`cryptography-48.0.1-cp311-abi3-win32.whl`, ABI3, совместима с 3.11+). Это НЕ было
применено — решение пошло путём 2.d, более простым и не добавляющим второй интерпретатор в
контур клиента.

**Факт, а не грязь:** `C:\Python314-32` остался на сервере установленным и НЕ используемым.
Названо явно в `11_INFRA_FACTS.md` (раздел 4 ниже) — это неиспользуемый артефакт диагностики на
сервере клиента, оставленный сознательно (удаление отдельным шагом не входило в задачу и не
запрошено).

### 2.d. Финальное решение — 64-битная `fbclient.dll` отдельно от сервера

У проекта Firebird нет отдельного client-only дистрибутива, но есть официальный ZIP-кит x64
(`Firebird-2.5.9.27139-0_x64.zip`, GitHub releases `FirebirdSQL/firebird`, тег `R2_5_9`, 11 МБ).
Скачан на сервер, из него взят `bin\fbclient.dll` (64-битный), помещён в
`C:\LombardAgent\firebird-client64\fbclient.dll`, каталог добавлен в `$env:Path` первой строкой
`run_daily_wrapper.ps1`, ДО остальных переменных окружения агента.

Сработало сразу. **Архитектурная находка, важная для любых будущих задач на этом сервере:**
разрядность клиентской библиотеки Firebird обязана совпадать с разрядностью процесса, который её
грузит через `ctypes` (наш Python-агент), но НЕ обязана совпадать с разрядностью СЕРВЕРА Firebird —
клиент по протоколу TCP не зависит от разрядности серверной части. Записано в
`10_GCP_INFRA_PLAYBOOK.md` (раздел 5) и `11_INFRA_FACTS.md` (раздел 4).

## 3. Итоговый вердикт

Список кандидатов (закрытый, по подготовленной мере): `WIN1251`, `UTF8`, `NONE`, `DOS866`.

- `WIN1251` → читаемый текст: `Среднее`, `Хорошее`, `Тех Паспорт Серии AB0496319`.
- `UTF8` → тот же читаемый текст, побайтово идентичный результат.
- `DOS866` → тот же читаемый текст, побайтово идентичный результат.
- `NONE` → мусор двойного перекодирования: `РЎСЂРµРґРЅРµРµ` вместо `Среднее` — классический
  признак сырых UTF-8-байт, прочитанных как cp1251 без объявленной кодировки соединения.

**Различающий факт:** `NONE` даёт мусор, три остальных кандидата — нет. Это единственное, что
подтверждено измерением с уверенностью.

**Совпадение WIN1251/UTF8/DOS866 на этом конкретном тексте НЕ объяснено окончательно** — возможная
причина: столбец `CUSTOM_FIELDS_VALUES.FIELD_VALUE` имеет `CHARACTER SET NONE` на уровне схемы
Firebird, и клиентская транслитерация в этом случае идёт иначе, чем для столбцов с объявленным
набором символов (гипотеза, не подтверждена, дальше не разбиралась, потому что для ответа не нужна).

**Выбрано `WIN1251`** — не как единственно возможное, а как конвенциональная кодировка для
Firebird-приложений в СНГ (та же логика выбора кандидатов, что уже применялась при подготовке этой
меры 2026-08-15), подтверждённая рабочей из трёх совпавших вариантов. Различающий факт (`NONE` даёт
мусор) достаточен для закрытия CONTEXT GAP; неполное объяснение совпадения трёх остальных не
блокирует ответ — оно названо как открытый остаток знания, не как факт.
