# T-0-8 · Замер организационных политик (шаг 5-БИС) · 2026-08-13

Предмет: сужение развилки `Q-21` до одного вопроса клиенту — запрещена ли организацией клиента
федерация удостоверений (workload identity federation) так же, как запрещено создание ключей
сервисных аккаунтов (`ADR-049`). Основание — `briefs/T-0-8.md`, ПОПРАВКА 2, раздел «Шаг 5-БИС».

Класс B, только чтение, четыре команды `gcloud org-policies` / `gcloud iam workload-identity-pools`.
Исполнено владельцем в Cloud Shell под своей учётной записью на проекте
`project-c451b48a-07ae-4de4-961`. Вывод перенесён дословно, БАЗОВЫЙ состав из брифа — без
предложенного архитектором расширения (то расширение не применялось).

## Вывод (дословно)

```
=== 1. Управляемая версия ограничения на ключи SA ===
name: projects/450925595005/policies/iam.managed.disableServiceAccountKeyCreation
spec:
  rules:
  - enforce: false

=== 2. Все политики, действующие на проекте ===
Listed 0 items.

=== 3. Разрешены ли поставщики федерации ===
name: projects/450925595005/policies/iam.workloadIdentityPoolProviders
spec:
  rules:
  - allowAll: true

=== 4. Заведён ли пул федерации в проекте ===
Listed 0 items.
```

## Разбор по пунктам

- **Пункт 1** (`iam.managed.disableServiceAccountKeyCreation`, `--effective`): управляемая версия
  ограничения печатает `enforce: false`. Это отдельный (управляемый) вариант ограничения от того,
  что уже зафиксирован в `ADR-049` как активный (`constraints/iam.disableServiceAccountKeyCreation`,
  `enforce: true`) — команда 1 брифа спрашивает про управляемую версию имени, не про уже известную.
  Факт печатается как есть, вопроса о создании ключей SA он не переоткрывает: `ADR-049` остаётся в
  силе по своему собственному замеру.
- **Пункт 2** (`org-policies list --project`): `Listed 0 items` при коде возврата 0. Само по себе
  это гэп наблюдения (`05 §I`), но здесь он **корроборирован обратным контролем той же командой
  `org-policies describe --effective`**: пункты 1 и 3 — тот же класс запроса (`describe --effective`
  на этом же проекте) — вернули непустой, разобранный ответ. Значит инструмент и учётная запись
  исправны, а пустая выдача `list` — факт «явной (не управляемой) политики на проекте нет», что
  совпадает с уже известным фактом из `ADR-049` («явной политики на проекте нет»). Новым гэпом это
  не считается.
- **Пункт 3** (`iam.workloadIdentityPoolProviders`, `--effective`): `allowAll: true`. **Федерация
  удостоверений НЕ запрещена организацией клиента.** Это прямой ответ на вопрос шага 5-БИС.
- **Пункт 4** (`workload-identity-pools list --location=global`): `Listed 0 items`. Ожидаемо —
  никакой пул федерации в проекте ещё не заводился (ни разу не было причины). Это не гэп
  наблюдения, а факт «пула ещё нет», согласующийся с тем, что федерация в этом проекте вообще не
  настраивалась.

## Вердикт

Федерация удостоверений организацией клиента **не запрещена** (пункт 3). Путь «вариант 2» развилки
`Q-21` остаётся живым и не снимается со стола. Пул федерации в проекте не заведён (пункт 4) — это
ожидаемое состояние «ещё не создавался», а не отказ.

**Недостающий факт, без которого вариант 2 не продвинуть:** есть ли в контуре клиента (Windows
Server) пригодный поставщик идентичности, способный выступить источником для workload identity
federation. Какой конкретно механизм (OIDC/SAML/иной) — не измерено и не угадывается; это отдельный
замер на стороне сервера клиента, ещё не выполнявшийся.
