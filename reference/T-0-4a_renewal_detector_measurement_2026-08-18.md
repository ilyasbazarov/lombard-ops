## Шаг 9 — попутный замер 1: пустые идентификаторы объекта (класс B, `Q-6`, три исполнения — дефект найден и исправлен реальным прогоном)

**Первая попытка (дефект):** подзапрос искал `DIR_CUSTOM_FIELDS.NAME = 'SUBJ_AUTO_VIN'` точным
совпадением. `vin_field_catalog` (`NAME LIKE '%VIN%' OR '%AUTO%'`, 12 строк) показал: реальное
значение `NAME` несёт системную обвязку — `'&$DIR_CUSTOM_FIELDS.SUBJ_AUTO_VIN#&'`, не голое имя.
Две строки для VIN: `(ID=12, ID_OBJ_TABLE=9)` и `(ID=22, ID_OBJ_TABLE=16)`. Точное совпадение никогда
не срабатывало → подзапрос возвращал `NULL` → `LEFT JOIN` пустой для ВСЕХ строк `SUBJECTS` →
`empty_vehicle_id_count` дал `(2507, 2507)` — **100%, артефакт синтаксиса, не факт**.

**Диагностика:** `tables_table_lookup` (`TABLES_TABLE WHERE ID IN (9, 16)`):
```
(9, 'SUBJECTS', 'Loan items table', 'mSubjs:', 'field.NAME')
(16, 'SH_PRODUCTS', 'Shop products', 'products:', 'field.NAME')
```
`ID_OBJ_TABLE=16` — `SH_PRODUCTS`, НЕ предмет залога. `vin_field_values_existence_check`
(`ID_FIELD IN (12, 22)`, группировка) вернул **ОДНУ** строку: `(12, 1876, 426)` — у `ID_FIELD=22`
вообще нет строк в `CUSTOM_FIELDS_VALUES`, он не участвует в данных.

**Исправленный запрос** (`EXISTS` вместо `LEFT JOIN`, оба `ID_FIELD` явно, без нового текстового
совпадения по `NAME`):
```
empty_vehicle_id_count: (2507, 2093)
```
**TOTAL_SUBJECTS=2507, EMPTY_VIN=2093 → 83.5% пустых VIN.**

**Расхождение 426 (непустых строк `CUSTOM_FIELDS_VALUES`) vs 414 (непустых объектов, `2507-2093`)
— разобрано полностью, не сглажено:**
```
vin_duplicate_check: (426, 426)   -- ROWS_CNT, DISTINCT_OBJ_CNT — дубликатов НЕТ
vin_orphan_check: (12,)           -- ровно 426-414=12, совпадает идеально
```
**Причина: 12 строк `CUSTOM_FIELDS_VALUES` с непустым VIN ссылаются на `ID_OBJ`, которого нет в
`SUBJECTS` — осиротевшие записи.** Дубликаты ID_OBJ как причина отклонены числом (`DISTINCT_OBJ_CNT`
= `ROWS_CNT`).

**`Q-6` ЗАКРЫТ: 83.5% объектов (2093 из 2507) не несут VIN, расхождение измерения полностью
объяснено. Суррогатный ключ `VEH-{YYYYMMDD}-{госномер}` — обязательный основной путь, не запасная
ветка.**

## Инцидент, не связанный с данными, но существенный для инфраструктуры

`schtasks /change` для password-based задачи планировщика требует пароль заново при КАЖДОЙ смене
`/tr` — реальное ограничение платформы. Это привело к введению механизма control-файлов
(`C:\LombardAgent\control\t0_4a_next_queries.txt`, `t0_4a_renewal_op_vids.txt`) — действие задачи
`LombardAgentDiscoveryT0-4a` зафиксировано один раз (без `-Queries`), между шагами брифа меняется
только содержимое файлов, `schtasks /change`/`net user` больше не нужны. При первом заходе смены
пароля `[System.Web.Security.Membership]::GeneratePassword]` упал («тип не найден», `System.Web` не
подгружен) — `net user` не применил пустой пароль, но `schtasks /change` для `LombardAgentDailyRun`
всё равно выполнился С пустым паролем (с предупреждением платформы, не молча) — на несколько минут
сохранённые учётные данные прод-задачи разошлись с реальным паролем учётки. Устранено в течение той
же сессии рабочей генерацией пароля, `net user` и `schtasks /change` синхронизированы одним новым
значением. **Инцидент полностью закрыт фактом:** `LombardAgentDailyRun` отработала штатно в плановом
прогоне `03:00:01` того же дня — все девять таблиц прочитаны и выгружены в GCS без ошибок.
