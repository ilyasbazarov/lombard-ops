## Разбор по разделам

- **Разделы 1-2 (корпоративный поставщик идентичности):** машина — рядовой сервер в рабочей группе
  (`DomainRole: 2`, `ProductType: 3`), НЕ в домене (`В ДОМЕНЕ: False`). Корпоративного поставщика
  идентичности НЕТ, подтверждено ТРЕМЯ независимыми способами: (а) роли `AD-Domain-Services`,
  `ADFS-Federation`, `Windows-Identity-Foundation` — `InstallState: Available`, то есть доступны к
  установке, но НЕ установлены; (б) все семь служб, по которым узнаётся живой AD FS / AD DS / Azure
  AD Connect (`adfssrv`, `drs`, `ADWS`, `NTDS`, `Kdc`, `ADSync`, `AzureADConnectHealthSync`) — «НЕ
  ЗАРЕГИСТРИРОВАНА»; (в) поиск по установленному ПО с признаками федерации в имени — 0 совпадений,
  корроборировано обратным контролем (всего прочитано 39 записей `DisplayName` — инструмент исправен,
  список не пуст сам по себе). Путь «использовать существующую корпоративную IdP» (гипотеза 2a
  разбора `Q-21`) закрыт фактом, не гаданием.
- **Раздел 3 (самоподписанный OIDC):** криптографически годен. RSA 2048 создан в памяти, подпись
  RS256 получена (256 байт), проверка подписи — `True`, открытая часть экспортируема (модуль 256
  байт, экспонента 3 байта) — это ровно то, что нужно для публикации JWKS. Путь 2b исполним
  технически на этом сервере.
- **Раздел 4 (Python):** не установлен ни в одной из четырёх проверенных форм (`where python`,
  `where python3`, `py -0p`, `python --version`). Это НЕ блокер выбора механизма федерации (раздел 3
  подтверждает годность пути средствами PowerShell/.NET без Python), но обязательная зависимость для
  будущего шага 6 (установка агента) — агент написан на Python (`connector/agent/agent.py`). Учесть
  при установке: Python ставится ДО или вместе с агентом.
- **Раздел 5 (часы):** арифметика времени сходится — локальное `15:35:35 +06:00` и UTC `09:35:36`
  расходятся на 6 часов и секунду выполнения команд, что соответствует часовому поясу `Central Asia
  Standard Time`. Служба времени Windows (`w32tm`) при этом НЕ ЗАПУЩЕНА — код `0x80070426`,
  «Служба не запущена». Это НАЗВАННЫЙ отказ именно проверки статуса службы синхронизации, не гэп
  наблюдения: означает отсутствие активной NTP-синхронизации на сервере и риск дрейфа часов со
  временем. JWT чувствителен к рассинхронизации времени (проверка `iat`/`exp` на стороне STS).
  Рекомендация — включить службу времени Windows перед боевым прогоном; это относится к будущему
  шагу 6 (установка агента), решением этой сессии не является.
- **Раздел 6 (связность к эндпоинтам федерации):** оба эндпоинта, `sts.googleapis.com` и
  `iamcredentials.googleapis.com`, под ШТАТНЫМ валидатором вернули `HTTP 404` на `GET /`. По правилу
  наблюдения `ADR-048` (там, где предикат уже реализован штатным механизмом платформы — валидацией
  цепочки сертификата и имени хоста, — `404` на пустом пути API-эндпоинта есть штатное поведение, не
  транспортный отказ): тот же паттерн, каким закрывался остаток связности `secretmanager.googleapis.com`
  (`reference/T-0-8_channel_remeasurement_2026-08-12.md`). Оба эндпоинта федерации живы, канал с
  сервера до них не блокирован ни прокси, ни `hosts`, ни цепочкой сертификатов.

## Вердикт

**Путь федерации на сервере ERP годен, и единственный доступный механизм — самоподписанный OIDC
(2b).** Корпоративной IdP на сервере нет (три независимых подтверждения, раздел 1-2), путь 2a
закрыт фактом. Криптографическая годность 2b подтверждена (раздел 3). Связность к обоим эндпоинтам
федерации подтверждена (раздел 6). Развилка ВНУТРИ варианта 2 `Q-21` **закрыта**: если владелец
выбирает вариант 2 (федерация) как механизм учётных данных агента, конкретная реализация — 2b,
альтернативы 2a на этом сервере нет.

Два факта переносятся вперёд как учтённые, не блокирующие: Python на сервере отсутствует (учесть
при установке агента, будущий шаг 6); служба времени Windows не запущена (включить перед боевым
прогоном, будущий шаг 6).

**Что остаётся нерешённым и держит `Q-21` в статусе OPEN** (см. `07_GAPS.md`):
(а) где публикуется JWKS — новый публичный бакет (решение владельца: текущие три бакета `T-0-7`
созданы с `public_access_prevention: enforced`, issuer-документ обязан читаться анонимно) либо
передача напрямую при создании OIDC-провайдера (платформенная гипотеза, проверяется отдельно
печатью `--help`, объектов не касается);
(б) подтверждение владельца на выбор самого пути федерации как механизма `Q-21` — архитектор дал
риск-анализ (2b не снимает класс риска «долгоживущий ключ на сервере клиента при компрометации
машины», но снимает три других названных риска) в прошлой сессии, окончательное решение за
владельцем.
