## 3. Разбор случая 1 — запрещённый оператор

Отбитый запрос: `UPDATE CONTRACTS SET NOTE = 'probe' WHERE CONTRACT_ID = 1`.

Отказ дан строкой ИМЕННО той проверки, которую мерили, а не посторонним сбоем: точка доступа
назвала разобранный тип оператора (`sqlparse определил тип 'UPDATE'`) и правило, по которому
отказала. Это исполнение правила поправки 1 брифа — проверка стоит на РАЗОБРАННОМ операторе, а не
на поиске подстроки.

**Подключение к базе на момент отказа было установлено.** Порядок в коде: `fdb.connect` → вызов
точки доступа → отказ → `connection.close()` в `finally`. Отказ произошёл до отправки запроса
серверу, то есть требование «на реальном подключении, но в базу не ушло» выполнено обеими
половинами. Красная линия «только чтение» не задета: ни одной операции записи к PawnShop не
исполнялось.

## 4. Разбор случая 2 — просроченный JWT

Токен пробы: `iat=1786973298` (2026-08-17 13:28:18 UTC), `exp=1786973358`, TTL 60 с. Токен рабочего
шага для сравнения: `iat=1786980496` (15:28:16 UTC). Разница `iat` — 7198 с, то есть проба
действительно отнесла выпуск на два часа назад, как задумано.

Отказ платформы: `invalid_grant`, обмен не состоялся.

**Существенная оговорка, записана как есть, а не как ожидалось.** Платформа называет причиной
НЕСВЕЖЕСТЬ ВЫПУСКА токена (`ID Token issued at … is stale to sign-in`), а не истёкший `exp`.
Формулировка отказа тождественна той, что платформа дала на несвежем боевом токене (раздел 6,
дефект 1). Из логов НЕ следует, что платформа проверяет `exp` — следует лишь, что токен с
`iat` двухчасовой давности к обмену не принимается. Требование брифа («обмен отбит платформой»)
этим выполнено; более сильное утверждение о механизме проверки не предъявлено и делаться не должно.

Проба намеренно строга: засчитывается только отказ, содержащий `invalid_grant`; любая иная ошибка
пробрасывается наружу и валит прогон, чтобы посторонний сбой не выдал себя за пройденный случай.

## 5. Как прогон был исполнен — маршрут и его вынужденность

Пробам нужны файлы учётных данных, закрытые правами на служебную учётку (раздел 6, факт 3).
Из-под интерактивной сессии администратора они не читаются. Штатный путь «временно сменить
исполняемую команду задачи планировщика» оказался закрыт:

```
schtasks /change /tn LombardAgentDailyRun /tr "..."
Введите пароль для lombard-agent-svc: ...
ОШИБКА: Неверное имя пользователя или пароль.
```

`schtasks /change` требует пароль учётки даже при смене одной лишь исполняемой команды. Пароль
хранится Windows внутри LSA и нам не принадлежит — путь отвергнут, задача при этом не изменилась
(команда отпала до применения).

**Применённый маршрут:** определение задачи НЕ трогалось вовсе. Боевой `run_daily_wrapper.ps1`
временно переименован в `.bak`, на его место скопирована обёртка проб
`negative_probes_wrapper.ps1`, задача запущена по требованию (`schtasks /run`), затем файл
возвращён. Пароль не участвует ни на одном шаге; сохранённые учётные данные задачи не могли
пострадать, поскольку задача не перерегистрировалась.

Отвергнутый вариант «сменить команду средствами PowerShell вместо `schtasks`» — плохой исход
несоразмерен выигрышу: удачная перерегистрация с потерей сохранённого пароля остановила бы боевую
задачу без возможности починить её без пароля.

Отвергнутый вариант «временно выдать администратору права на файлы ключей» — ослабление защиты,
поставленной шагом 5-Б, ради одного прогона.

**Возврат доказан счётом, а не осмотром.** SHA-256 боевого wrapper'а до подмены и после возврата:
`085653FDE3A2671A2DA61D41D8C6AFF856AE5E5E99B663CBBC3AA62F05DEFB5A` — совпал во всех четырёх
проведённых циклах подмены. Боевая задача осталась указывающей на `run_daily_wrapper.ps1` от
служебной учётки; ближайший штатный запуск — 18.08.2026 03:00.

**Прогон шёл от служебной учётки — предъявлено положительным фактом**, строкой
`WHOAMI: WIN-RSAGM3JEOUA\lombard-agent-svc` в логе, а не рассуждением.

**Состояние `signed_jwt.txt` после проб:** содержит просроченный токен пробы. Восстановления не
требует — боевой прогон обновляет его первым шагом (строка
`JWT обновлён перед прогоном` в логе выше это подтверждает).

## 6. Дефекты, найденные по пути, и факты для реестра

**Дефект 1 — проба не обновляла токен перед первым случаем.** Первые два прогона упали на создании
клиента Secret Manager: `invalid_grant: ID Token issued at 1786969037 is stale to sign-in`. Метка
`1786969037` — 2026-08-17 12:17:17 UTC, время прошлого боевого прогона: проба работала токеном,
оставшимся на диске. Случай 1 требует ДЕЙСТВУЮЩЕГО токена, чтобы дойти до Secret Manager.
Исправлено вызовом `run_daily._refresh_jwt()` — той же функции, что использует боевой прогон;
второй набор логики работы с учётными данными не заводился.

**Дефект 2 — ловился не тот класс исключения.** Отказ платформы приходит как
`google.auth.exceptions.OAuthError`, а обработчик ждал `RefreshError`. Прогон это доказал:
исключение прошло мимо `except RefreshError` и вылетело наружу с кодом `1`. **Факт установленной
версии библиотеки: `OAuthError` НЕ является подклассом `RefreshError`.** Исправлено перехватом
обоих классов.

**Дефект 3 — исполнялась не та версия файла.** Один прогон был проведён при несовпавшем хеше
скрипта. Доказательство, что исполнялся старый файл, — два независимых признака: хеш
`2116C698…` вместо ожидаемого `A9D67397…` и номера строк в трейсбеке (`60`, `120`, `126`),
тогда как в исправленной версии те же места стоят на `65`, `131`, `137`. Вывод для правила: сверка
хеша перед прогоном — не формальность, её несовпадение есть стоп-условие.

**Факт 3 — точечные права на файлах учётных данных (для `11_INFRA_FACTS`).** Замер `icacls`
2026-08-17:

```
C:\LombardAgent\keys        NT AUTHORITY\СИСТЕМА:(I)(OI)(CI)(F)
                            BUILTIN\Администраторы:(I)(OI)(CI)(F)
                            BUILTIN\Пользователи:(I)(OI)(CI)(RX)
                            BUILTIN\Пользователи:(I)(CI)(AD)
                            BUILTIN\Пользователи:(I)(CI)(WD)
                            СОЗДАТЕЛЬ-ВЛАДЕЛЕЦ:(I)(OI)(CI)(IO)(F)

C:\LombardAgent\keys\credentials.json   NT AUTHORITY\СИСТЕМА:(F)
                                        WIN-RSAGM3JEOUA\lombard-agent-svc:(R)

C:\LombardAgent\keys\private_key.pem    WIN-RSAGM3JEOUA\lombard-agent-svc:(R)
                                        NT AUTHORITY\СИСТЕМА:(F)

C:\LombardAgent\keys\signed_jwt.txt     NT AUTHORITY\СИСТЕМА:(I)(F)
                                        BUILTIN\Администраторы:(I)(F)
                                        BUILTIN\Пользователи:(I)(RX)
                                        WIN-RSAGM3JEOUA\lombard-agent-svc:(I)(F)
```

Реестр сейчас записывает ограничение `icacls` только на файл приватного ключа. По факту ограничены
ТОЧЕЧНО, с разрывом наследования, ДВА файла — `private_key.pem` и `credentials.json`; сам каталог
`keys` не ограничен.

**Находка — `signed_jwt.txt` наследование НЕ разорвано.** Файл несёт `BUILTIN\Пользователи:(I)(RX)`,
то есть подписанный токен читаем всеми локальными пользователями сервера. Токен есть предъявитель:
прочитавший его обменивает токен на облачный в пределах срока жизни, приватный ключ для этого не
нужен. Каталог отдаёт чтение с наследованием на новые файлы, поэтому создаваемый заново
`signed_jwt.txt` получает эти права каждый раз.

Находка приёмку шага 7 НЕ срывает: критерий говорит о секретах в логе и в репозитории, здесь ни то,
ни другое — это факт о контуре. **Мера не исполнена:** разорвать наследование на `signed_jwt.txt`,
оставив систему и служебную учётку, — отдельное действие класса B с отдельной карточкой, вне
радиуса шага 7. Смешивать её с этой приёмкой было бы дефектом нарезки.

## 7. Что этим артефактом НЕ закрыто

- **Основной прогон агента** — предмет отдельного артефакта. Его логи (`run_daily_*.out.log` /
  `.err.log` за 2026-08-17 18:17 и вывод чтения бакета) в сессию не предъявлялись; писать по
  пересказу запрещено. `CONTEXT GAP` открыт.
- **Шаг 8** — патч `10_GCP_INFRA_PLAYBOOK` и `INFRA_PATCH` в `11_INFRA_FACTS`, включая три факта
  раздела 6.
- **Третий факт условия переезда чтения БД в класс A** — оценка не выносится этим артефактом;
  ответ обязан прозвучать в session-блоке отдельно.
- **Мера по `signed_jwt.txt`** — см. конец раздела 6.

на исход отрицательных случаев влиять не может — отказ случая 1 даёт разбор оператора до отправки

дублирования — правка вне радиуса шага 7, после его приёмки.
