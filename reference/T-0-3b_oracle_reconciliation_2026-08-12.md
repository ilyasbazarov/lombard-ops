# T-0-3b · Сверка с оракулом (экран приложения вендора)

**Дата снимка:** 2026-08-12 · **Кто снимал:** сотрудник клиента (оценщик/кассир), приложение
PawnShop на рабочем ноутбуке в офисе клиента, по просьбе Ilyas. **Валюта на экране:** доллары США.
Снимок-первоисточник (кто, когда, какие суммы) хранится у Ilyas вне репозитория — в публичный
репозиторий идёт только обезличенный результат ниже (`ADR-024`).

## Метод

«Наша величина» считалась по формуле 2 (`03 §4` расширенная, см.
`T-0-3b_accrual_params_measurement_2026-08-12.md §7`) на ту же дату 2026-08-12, двумя кандидатами
пени (`§6` того же файла), поскольку формула пени не была подтверждена однозначно ДО сверки
(`ADR-023`):
- **Кандидат А** — ставка пени берётся из поля базы `PENALTY_PERC` (0.15–0.425%/день по договору),
  без разового штрафа (поле для него в базе не найдено).
- **Кандидат Б** — ставка пени и разовый штраф со слов владельца: `0.3%/день` + разовый `2,5%`
  от суммы возврата в момент старта пени.
- Начисление процентов и хранения — от `CONTRACT_DATE`, месячная ставка по дням (подтверждено
  владельцем), без учёта возможных продлений/погашений (детектор продлений — `T-0-4`, вне scope
  этой задачи; см. вывод ниже).

## Договор `1.2` (порядковый «договор 5» / контроль не относится) — исключён из сверки

По этому договору клиент делал частичное погашение долга; исходное тело в базе (27 000) не
отражает актуальную задолженность на экране, которая уже учитывает это погашение. У нас нет в
scope этой задачи данных по операциям погашения (таблица `OPERATIONS` не запрашивалась под это).
**Сверка по договору 5 не проводится** — не подгоняется под цифру и не выбрасывается тихо, а
называется исключённым по названной причине.

## Вывод

**Не сошлось ни на одном из восьми проверяемых договоров** (`ADR-010 v3`, критерий `ADR-023`).
Ни кандидат А, ни кандидат Б не закрывают расхождение — смена формулы пени меняет числа
контрольной группы и договора 6, но не объясняет расхождение договоров 1–4, где пени ещё нет
вовсе, а расхождение уже сотни долларов.

**Вероятная причина, названная фактом, не подгонкой:** договор 1 (самый показательный — не
просрочен, `PLAN_CLOSE_DATE` в будущем) даёт разницу компоненты процентов **+701.66 $** при том,
что весь наблюдаемый разрыв с экраном — всего **+2.67 $**. Начисление процентов «по дням от
`CONTRACT_DATE`» непрерывно за 421 день (весь срок жизни договора в базе) даёт кратно завышенное
число. Наиболее вероятное объяснение — учётная система **сбрасывает точку отсчёта начисления при
каждом продлении/погашении** (44% договоров перезакладываются — `03 §2`), а `CONTRACT_DATE`
хранит ПЕРВОНАЧАЛЬНУЮ дату выдачи, не дату последнего цикла. Детектор продлений — предмет `T-0-4`,
прямо названной вне scope этой задачи (`briefs/T-0-3b.md`, «Вне scope»).

**Что это значит для задачи:** формула баланса не может быть провалидирована оракулом, пока не
известна точка отсчёта начисления с учётом продлений. Это блокирующий факт для `03 §4`, не
локальная поправка. Формула хранения (предмет `Q-9`) как таковая тоже не выделяется из общего
расхождения — расхождение слишком велико уже без неё.

## Что НЕ делается по итогам (`00 §3-БИС(b)`, `ADR-039`)

- `03_BUSINESS_SPEC.md §4` **не правится** — оракул не сошёлся ни на одном договоре.
- Формула хранения **не выбирается** между кандидатами — недостаточно данных для выбора, пока не
  решён вопрос точки отсчёта.
- Подгонка коэффициентов под цифру экрана не производится — расхождение называется фактом,
  закрывается решением архитектора, не «уточнённым коэффициентом» (`ADR-039`).
