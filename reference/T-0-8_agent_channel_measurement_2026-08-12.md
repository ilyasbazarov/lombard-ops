# T-0-8 · Замер связности (Шаг 1) · 2026-08-12

Предмет: проверка исходящего HTTPS с сервера ERP (`192.168.88.209`, Windows Server, RDP) до
`storage.googleapis.com` и `oauth2.googleapis.com` — ДО написания кода агента, по брифу
`briefs/T-0-8.md`, шаг 1.

Все команды выполнены самим владельцем (Ilyas) по RDP на сервере ERP, вывод передан дословно
в чат сессии и перенесён сюда без правок по содержанию.

## Среда

- Windows Server 2019 Standard, build 10.0.17763.
- Прокси (WinHTTP): прямой доступ, прокси-сервер не задан.
- Прокси (WinINet/IE): `ProxyEnable=0`, `ProxyServer` пуст, `AutoConfigURL` пуст.
- Доверенных корневых сертификатов в `LocalMachine\Root`: 42.
- `hosts`-файл: значимых строк (без комментариев) нет.

## Прогон 1 — `Invoke-WebRequest -Method Head`, без разведения исходов

`storage.googleapis.com` и `oauth2.googleapis.com` дали `WebException` с текстом «(400) Недопустимый
запрос» и «(404) Не найден» соответственно. **Дефект пробы**: `Invoke-WebRequest` бросает исключение
на любой HTTP-статус вне 2xx, поэтому «пришёл ответ» и «блокировка на транспортном уровне» дают
неразличимый по форме вывод (нарушение правила «проба обязана различать исходы», `ADR-033`). Ветки
6 и 8 (цепочка сертификатов) не выполнились — выполнение прервалось на исключении `GetResponse()`
раньше, чем скрипт успевал прочитать `ServicePoint.Certificate`.

## Прогон 2 — `HttpWebRequest`, разведение HTTP-ответа и транспортного отказа

Оба хоста дали ИСХОД «HTTP-ответ получен (через исключение)» — `storage.googleapis.com` код 404,
`oauth2.googleapis.com` код 404. Цепочка сертификатов прочитана из `ServicePoint.Certificate` после
handshake:

- `storage.googleapis.com` → сертификат `CN=storage.googleapis.com`, цепочка
  `WE2 (Google Trust Services) → GlobalSign ECC Root CA — R4`, `ChainStatus` пуст (валидна без
  замечаний). **Совпадает с запрошенным хостом.**
- `oauth2.googleapis.com` → сертификат `CN=upload.video.google.com`, та же цепочка доверия
  (`WE2 → GlobalSign`), `ChainStatus` пуст. **НЕ совпадает с запрошенным хостом.**

## Прогон 3 — явный `SecurityProtocol = Tls12`, `KeepAlive=$false`, два независимых запроса

Несовпадение для `oauth2.googleapis.com` воспроизвелось ДВАЖДЫ подряд, без изменений: сертификат
снова `CN=upload.video.google.com`, «Совпадает с запрошенным хостом: False». Контрольный повтор
`storage.googleapis.com` в том же прогоне вернул корректный сертификат. Явное выставление `Tls12`
причину не сняло — версия TLS/SNI-поведение `HttpWebRequest` исключены как причина.

## Прогон 4 — DNS напрямую и сырой TLS в обход `HttpWebRequest`

- `Resolve-DnsName oauth2.googleapis.com` → `142.251.127.95` (A), `2a00:1450:4001:c21::5f` (AAAA).
- `Resolve-DnsName storage.googleapis.com` → восемь адресов A-записей (`34.144.170.27` и др.).
- `hosts`-файл — пуст по значимым строкам (проверено прогоном 1, подтверждено здесь).
- Сырой `TcpClient` + `SslStream` с явным SNI = `oauth2.googleapis.com`: TCP подключился к
  `142.251.127.95:443`, TLS handshake прошёл, **сертификат сервера — `CN=upload.video.google.com`,
  issuer `WE2, Google Trust Services`**. Тот же тест для `storage.googleapis.com`: TCP подключился к
  `142.251.13.207:443` (адрес НЕ входит в список A-записей, отданных `Resolve-DnsName` тремя
  секундами ранее — отдельный факт о непостоянстве ответов DNS/geo-routing Google), сертификат
  корректный — `CN=storage.googleapis.com`.

## Прогон 5 — контрольный повтор через ~10 минут (по решению владельца, снять гипотезу «временный geo-routing»)

Выполнен в `22:30:52` (после прогона 4). `oauth2.googleapis.com` резолвится в ТОТ ЖЕ IP
(`142.251.127.95`), сертификат снова `CN=upload.video.google.com`, «Совпадает с запрошенным
хостом: False». `storage.googleapis.com` в этом же прогоне резолвится в третий по счёту разный IP
за сессию (`142.251.14.207`, ранее были `142.251.13.207` и восемь адресов `34.x`/`104.154.x` от
`Resolve-DnsName`) и во всех случаях отдаёт корректный сертификат. **Гипотеза «временная просадка
geo-routing» снята**: несовпадение для `oauth2.googleapis.com` воспроизведено пятый раз подряд, на
том же IP, спустя интервал времени — это устойчивое, а не разовое поведение канала клиента к этому
конкретному эндпоинту.

## Факт, а не предположение

Несовпадение сертификата воспроизведено **четыре раза подряд** (прогоны 2, 3×2, 4), исключительно
для `oauth2.googleapis.com`, на уровне сырого TLS в обход `.NET HttpWebRequest`, при явном SNI,
после исключения версии TLS, DNS-переопределения через `hosts` и локального прокси как причин.
`storage.googleapis.com` в тех же условиях и в тот же момент времени отдаёт корректный сертификат
неизменно. Цепочка сертификата `oauth2.googleapis.com` подлинная (подписана `Google Trust Services`,
валидна без замечаний) — это исключает типовой корпоративный MITM-прокси с приватным CA, но не
объясняет, почему сервер, отвечающий на IP из адресного пространства Google (`142.251.x.x`), отдаёт
identity другого сервиса Google (`upload.video.google.com`) на запрос `oauth2.googleapis.com`.

**Причина НЕ установлена.** Дальнейшее гадание (конкретный IP, конкретный прокси-узел, конкретная
точка перехвата) запрещено правилом anti-improvisation — измерение остановлено на этом факте.

## Вердикт по шагу 1

**Не пройдено.** Контрольный повтор (прогон 5) исключил временный характер — расхождение
воспроизведено пять раз подряд, устойчиво, на одном и том же IP. `storage.googleapis.com` доступен
и отдаёт корректную identity; `oauth2.googleapis.com` — эндпоинт, обязательный для получения токена
сервисного аккаунта агента, — с этой сети НЕ доступен по назначению: TLS проходит, но identity
сервера не совпадает с запрошенным доменом, механизм не установлен (не блокировка, не MITM с
приватным CA, не DNS/hosts-подмена — все три исключены измерением). Канал в текущем виде не
пригоден для прод-подключения агента. По брифу `briefs/T-0-8.md`, шаг 1: задача останавливается,
вариант А (туннель) возвращается новым решением владельца.
