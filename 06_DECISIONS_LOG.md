## ADR-001 · Публичный моно-репо + правило санитарии
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** raw-URL без токенов — нулевая настройка для сессий (проверено на dom-prorab-catalog); но проект содержит контур клиента.
**Решение:** репо `lombard-ops` публичный, docs+код вместе. ЗАПРЕЩЕНО в репо: креды/ключи любого рода (в т.ч. VPN-конфиги WireGuard), публичные endpoint'ы контура клиента (DDNS-имена, внешние порты VPN), токены Telegram, ПДн клиентов ломбарда (имена/телефоны/номера договоров в примерах — обезличивать). ДОПУСТИМО: внутренние LAN-IP, номера портов сервисов, PROJECT_ID, имена ресурсов GCP.
**Последствия:** дампы структуры БД перед коммитом санитизируются; секреты — Secret Manager; примеры данных — синтетика.

## ADR-002 · Единое Cloud Run приложение + Identity Platform вместо Apps Script / GCS static / cf-api
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** требование логин/пароль + роли несовместимо с Apps Script «Anyone»; драфт ТЗ размазывал UI по трём технологиям и сам помечал Apps Script на снос при росте; signed-URL через HMAC в Apps Script — самый хрупкий пункт драфта.
**Решение:** один Cloud Run сервис `app-lombard` (React + API); auth — Identity Platform (email+пароль), роли `owner`/`manager`/`assessor` в custom claims; API проверяет токен и роль на каждом запросе. Все экраны — роуты одного приложения.
**Последствия:** cf-api, GCS static hosting и Apps Script не строятся; фото — обычные signed URL из бэкенда.

## ADR-003 · Ingestion: pull-коннектор из БД Firebird; fallback — агент на сервере
**Дата:** 2026-07-10 · **Статус:** accepted (канал доставки — pending, см. ADR по T-0-8)
**Контекст:** дано прямое read-only подключение к БД PawnShop; file-drop драфта делал Бектура ручным звеном и порождал staleness-проблему.
**Решение:** данные забирает `job-connector` (Cloud Run Job) по расписанию напрямую из Firebird. Ручная загрузка файлов не строится. Запасные каналы: (B) агент на ERP-сервере с только исходящим пушем в GCS; (C) штатная выгрузка PawnShop «в бух. программы».
**Последствия:** дискавери смещается на схему БД и сеть; staleness-проверка остаётся как guard обрыва связи.

## ADR-004 · Guard схемы Firebird
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** вендор меняет структуру БД при обновлениях и не уведомляет.
**Решение:** перед каждым чтением — отпечаток метаданных используемых таблиц (RDB$) сверяется с эталоном в mapping.json; расхождение → стоп + алерт, чтения нет. `SELECT *` запрещён. Обновление эталона — осознанная правка конфига.
**Последствия:** обновление PawnShop ломает конвейер громко и безопасно, а не тихо портит данные.

## ADR-005 · Порядок фаз: конвейер данных раньше форм
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** драфт ставил форму осмотра первой (логично при file-drop); при pull-коннекторе данные доступны сразу, а форма требует готового приложения с auth. Урок референс-проекта: интегральный путь проверять рано.
**Решение:** Фаза 1 — конвейер + светофор с tracer bullet в конце фазы; Фаза 2 — приложение и формы; Фаза 3 — Stop-Loss.
**Последствия:** Иса получает ценность (сводка, алерты) раньше; допущения о данных проверяются первыми.

## ADR-006 · balance_amount вычисляется на нашей стороне
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** ответ вендора: начисления (%/пени) в БД не хранятся, считает приложение.
**Решение:** балансовая стоимость вычисляется в cf-daily из условий договора (тело, ставка, пени-правила — маппинг T-0-3) по формулам `03 §4`. Валидация: сверка на нескольких договорах с цифрами из UI PawnShop.
**Последствия:** дискавери обязан найти поля условий; расхождение с PawnShop UI — блокер запуска Фазы 3.

## ADR-009 · Дампы структуры БД вендора не коммитятся в публичный репо
**Дата:** 2026-07-14 · **Статус:** accepted
**Контекст:** вендор «Алгоритм» считает схему БД конфиденциальной; полный дамп структуры (108 таблиц, 1018 колонок) получен при выполнении T-0-2.
**Решение:** дампы структуры БД передаются архитектору только в чат (вне репо). В репо попадает исключительно маппинг используемых полей (документация `02 §3`). Синтетические примеры в кодексе/конфигах — без специфичных колонок вендора.
**Последствия:** T-0-3 и далее работают с производным маппингом (`mapping.json`), не с полным дампом; дамп остаётся в истории чата как справка для аналитики, недоступный для public github.

## ADR-010 v3 · Хранение (STORAGE_*) входит в balance_amount
**Дата:** 2026-07-25 · **Статус:** accepted (v1 и v2 superseded; v2 предполагала возможность «везде ноль»)
**Контекст:** структура CONTRACTS_TERMS показывает три симметричных семейства начислений (проценты / хранение / страховка), STORAGE_VAL имеет тип, идентичный процентной ставке. Владелец (Иса) подтвердил: из 98 договоров 6 несут начисление за хранение по тарифу прошлого года. Формула 03 §4 (тело + % + пеня) их не учитывает. Эти 6 — самые старые договоры портфеля, то есть наиболее вероятные обитатели 🟠/🔴, где точность баланса определяет решения Stop-Loss.
**Решение:** (1) хранение — полноправная компонента balance_amount, 03 §4 расширяется; (2) формула начисления определяется в T-0-3b и подтверждается оракулом UI на всех шести договорах (набор мал — сверяется целиком, не выборкой); (3) в слой канонизации ставится блокирующее утверждение: активный договор с ненулевым STORAGE_VAL или INSURE_VAL, для которого формула не определена → стоп + алерт, не тихий недосчёт (философия ADR-004 применительно к данным); (4) INSURE_* обрабатывается тем же механизмом; на текущих данных нулевое, но утверждение его страхует.
**Последствия:** правка 03 §4 в T-0-3b; T-0-3b получает готовый оракульный набор из 6 договоров и независимый контрольный счёт от владельца.

## ADR-016 · Размещение вендорских артефактов и маппинга
**Дата:** 2026-07-25 · **Статус:** accepted
**Контекст:** ADR-009 запретил полный дамп структуры в публичном репо, но не назвал, где он живёт. Итог: дамп остался в истории чата, а `mapping.json` — на машине Ilyas; 02 §3 в репо простояла пустой 11 дней при выполненной задаче.
**Решение:** (1) `mapping.json` — источник истины в публичном репо по пути `/connector/mapping.json`; допустимо по ADR-009 (производный маппинг used-полей) и необходимо: fingerprint used-таблиц — обязательный вход guard'а ADR-004. Копия в GCS `${PROJECT_ID}-config` — деплой-артефакт, не источник истины. (2) Полный дамп структуры, инвентарь схемы и исторические экстракты — в **приватный репо-сателлит `lombard-ops-vendor-schema`**, путь `schema-snapshots/<YYYY-MM-DD>_<артефакт>` + README с происхождением и версией билда PawnShop. Выбран git, а не GCS: вендор не уведомляет об обновлениях, поэтому нужен `diff` между снимками схемы — git даёт его без инструментов. (3) Инструменты разбора (парсеры) — в публичный репо: это наш код, не схема вендора.
**Последствия:** T-0-10 создаёт хранилище и переносит артефакты; после обновления PawnShop дифф снимков становится штатной процедурой при срабатывании guard'а.

## ADR-017 · Главный принцип: граница контракта двойная + закон фикс-форварда
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** метод держится на границе, которую слои не пересекают, но в конституции она не была объявлена главным принципом. Проверка по репозиторию показала, что границ фактически две и обе уже существуют: структурная — слой канонизации (`00 §3` принцип 3, правило в `02 §3`); приёмочная — экран приложения вендора (ADR-006, ADR-010 v3, «оракул на 6 договорах» в состоянии). Проверка кандидата на структурную границу вопросом «можно ли заменить производителя, не трогая потребителя» пройдена буквально: канал прод-подключения (`T-0-8`) до сих пор не выбран, а потребители уже спроектированы.
**Решение:** внести в конституцию секцию `3-БИС`, назвав (a) слой канонизации структурной границей, (b) внешний эталон границей приёмки с иерархией «экран вендора → агрегат по таблицам → число владельца», (c) guard схемы (ADR-004) её механической проверкой. Добавить закон фикс-форварда: слой не лезет через границу чинить чужой слой; мерить там, где видно, чинить там, где причина; разовое исключение — только явный override с причиной и сроком снятия, записанный решением.
**Последствия:**
- `00_CHARTER.md` §3-БИС — вставка [сейчас]. Номер `3-БИС` намеренный: сквозная перенумерация сломала бы ссылки `00 §4`/`§5`/`§6` в конвенциях, бутстрапах ролей, шаблоне брифа и четырёх брифах.
- `01_ARCHITECTURE.md`, `02_DATA_CONTRACTS.md` — сплошной поиск понятия «канонизация» с печатью всех совпадений и решением по каждому [задачей M-3].
- `03_BUSINESS_SPEC.md` — [без правок].

## ADR-018 · Модель исполнения: сессия исполняет сама; мандат по классу задачи
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** действующая модель (`05 §I`) ставит человека в каждый круг «выдал скрипт → скопировал → запустил → вернул лог». Владелец принял решение перейти на исполнение сессией. Мандат по задаче даёт узкое место: каждая задача ждёт отдельного решения.
**Решение:** мандат выдаётся по КЛАССУ задачи. Класс A — постоянный: чтение всего, дискавери, написание кода и конфигов без применения, запись в staging и `/reference`, локальный коммит. Класс B — задача-специфичное решение владельца, перечислен буквально в `05 §I`: облачные ресурсы, секреты, отправка в мессенджер реальным людям, операции за авторизацией, обращения к БД PawnShop (временно, до `T-0-5`), правки порогов цены, публикация наружу. При сомнении — класс B. Запись в БД PawnShop классом B не является: она запрещена совсем красной линией `00 §4`. Перед запросом подтверждения класса B — отдельное сообщение «что, на каком объекте, чем откатывается». Один скрипт на ШАГ брифа, не на команду. Ревью границы берут три механизма: хук, контрактные тесты, отдельная архитекторская сессия на диффах; совмещение автора и адъюдикатора запрещено.
**Последствия:**
- `05_CONVENTIONS.md` §I — замена блоков «Роли» и «Модель исполнения» [сейчас].
- `07_STATE.md` — таблица мандата, парная задача-строкам [сейчас].
- `CLAUDE.md` — закон о классах [сейчас].
- `.claude/settings.json` — разрешено/спросить/запрещено на уровне инструмента [задачей M-1].
- `08_TASK_BRIEF_TEMPLATE.md` — поле «Класс задачи» [сейчас].
- `09_RUNBOOK.md` — режим ревью на границе [сейчас].
- Строка «обращения к БД — класс B» снимается одной правкой после закрытия `T-0-5` [задачей T-0-5].

## ADR-019 · Компактизация состояния: индекс решений, архив, реестр вопросов, стенд-ап
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** замер по диску: раздел «Сделано» — 10 строк и растёт без границы; открытые вопросы — 9 строк плоским списком без идентификаторов, статусов и гейтов; состояние 4 450 байт, журнал решений 14 396 байт. Ретрофит этого разреза в проекте-доноре делался на файле в 300 КБ и стоил двух решений и сплошного прохода. Цена разреза — единственная в плане перехода, которая растёт каждый день.
**Решение:** три разреза по принципу «оглавление в обязательный контекст, полный текст точечно». (1) `06_DECISIONS_LOG` (полный текст) ↔ `06_INDEX` (номер · заголовок · дата · статус); в обязательный контекст входит только индекс. (2) `07_STATE` (только ОТКРЫТОЕ) ↔ `07_ARCHIVE` (закрытое дословно); полное закрытие строки = перенос в архив ТЕМ ЖЕ коммитом. (3) `07_STATE` (индекс вопросов: `ID · статус · вопрос одной фразой · гейт`) ↔ `07_GAPS` (полный текст); новая строка заводится в ОБА файла одним коммитом. Статус — из закрытого словаря `OPEN` / `READY` / `DEFER` / `PARTIAL`. Блок фокуса разделяется на стенд-ап (ровно пять строк, ЗАМЕНЯЕТСЯ целиком) и «Подробности для модели» (дописывается; критерий записи — только то, без чего сломается СЛЕДУЮЩАЯ сессия).
**Последствия:**
- `06_INDEX.md`, `07_GAPS.md`, `07_ARCHIVE.md` — новые файлы [сейчас].
- `07_STATE.md` — полная замена структуры [сейчас].
- `README.md` — карта базы знаний [сейчас].
- Хук: проверки «append решения ⇒ строка в индексе», «строка исчезла ⇒ архив», «множества ID индекса и реестра совпадают» [задачей M-4].

## ADR-020 · Ретайр роли Applier
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** роль ручного механического переноса session-блоков в файлы репозитория осмысленна, пока сессия не пишет на диск. С переходом на исполнение сессией (ADR-018) она теряет предмет. Плюс прецедент качества: в `CHANGELOG.md` запись `T-0-2` продублирована целиком — блоки строк 3–11 и 12–20 побайтово идентичны. Ручной перенос уже дал дубль, который никто не заметил три недели.
**Решение:** `_APPLIER.md` ретайрится. Файл не удаляется, а заменяется надгробием со ссылкой на это решение: удаление стирает провенанс, а репозиторий публичный и ссылки на файл могут существовать снаружи. Работу роли берут: в режиме внутри инструмента — сама сессия; при появлении параллельных сессий — проход сборки (отложенная часть ADR-025).
**Последствия:**
- `_APPLIER.md` — замена содержимого надгробием [сейчас].
- `README.md` — строка «Applier (Haiku)» в запуске ролей убирается [сейчас].
- `05_CONVENTIONS.md` — упоминания applier в Части III [сейчас].
- Дубль в `CHANGELOG.md` — [задачей T-0-16].

## ADR-021 · Единственный режим чтения — локальный диск; единственный источник списка обязательного контекста
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** два дефекта с общим корнем — источник истины назван в нескольких местах и в разных вариантах. (1) Сплошной поиск дал ТРИ места, где перечислен обязательный контекст, и ДВА разных набора, ни один из которых не совпадает с другим: `05:20` — `00+05+07+11`; `05:126` — `00+04+06+07`; `_ARCHITECT.md:6` — `00+04+06+07`, причём `_ARCHITECT.md:7` относит конвенции к разряду «по задаче, если сессия их касается». Правило языка ответов и правила агента живут операционно только в конвенциях; сессия, стартовавшая по списку бутстрапа архитектора, нарушает их в первом же ответе — этот отказ зафиксирован в проекте-доноре с датой. (2) Раздел «Доступ к документации в чате» предписывает чтение репозитория по сетевым ссылкам с пиннингом по коммиту. Это было верно, пока сессии шли в обычном чате; внутри инструмента файл лежит на диске, а сеть отдаёт кэш, то есть правило прямо вредно. Сплошной поиск нашёл сетевые ссылки в семи файлах, включая **два невыполненных брифа с незаполненным плейсхолдером коммита** (`briefs/T-0-5.md:15`, `briefs/T-0-10.md:14`) — оставленный плейсхолдер есть дефект посева, а не «потом».
**Решение (владелец, 2026-08-07):** (1) **Все роли работают внутри инструмента, на ЛОКАЛЬНОМ репозитории. Второго режима чтения нет.** Файлы читаются с диска по именам; `curl`, raw-URL, браузерный фетчер и пиннинг по коммиту за содержимым репозитория запрещены. Коммит фиксируется командой `git rev-parse HEAD`. Сеть остаётся для работы с удалённым репозиторием (`fetch`, `push`) и для задач, где внешний источник и есть предмет. (2) **Разговор без доступа к диску сессией не является:** он не цитирует файлы, не выдаёт патчей и в репозиторий не входит; чтобы его результат попал в проект, он переформулируется задачей. Роль без доступа к источнику истины неизбежно работает по памяти, а это запрещено главным законом. (3) Список обязательного контекста существует в ОДНОМ экземпляре — в `CLAUDE.md`; из всех прочих мест на него ссылаются, но не цитируют. (4) Разрез автора и адъюдикатора сохраняется: мандат класса A даёт право писать код и коммитить локально, но НЕ даёт права назначать правило.
**Последствия:**

## ADR-022 · Механические проверки на коммите
**Дата:** 2026-08-07 · **Статус:** accepted

Локальные прецеденты: (1) значение пароля администратора БД присутствует в `CHANGELOG.md` дважды, в `briefs/T-0-2.md` литералом и в 8 коммитах публичной истории — при том что санитария репозитория записана решением ADR-001 прозой; (2) игнор-файла в репозитории нет вовсе, то есть ничто механически не мешает закоммитить конфиг или дамп; (3) машиночитаемых полей брифа ноль во всех четырёх брифах и в шаблоне — подтверждено сплошным поиском с обратной проверкой исправности поиска.

## ADR-023 · Три типа приёмки; правило формулы; след от проверки глазами
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** одно решение (ADR-015) уже было потрачено целиком на спор о том, что считать приёмкой задачи `T-0-3`. Тип приёмки не был назван, поэтому спор был неизбежен. Отдельно: `ADR-010 v3` добавляет в формулу баланса третью компоненту, а `T-0-3b` эту формулу определяет — то есть соблазн написать приёмку «сумма портфеля не изменилась» возникнет на первой же правке и будет невыполним по построению, потому что добавление компоненты сдвигает сумму арифметически неизбежно.
**Решение:** три типа приёмки по типу задачи. (i) **Дискавери:** знание зафиксировано в репозитории и трассируемо к источнику, эталон датирован, открытый вопрос помечен на закрытие; возврат — обогащение репозитория, не код. (ii) **Код:** контрактный тест на границе (отпечаток схемы плюс контракт канонического представления) · интегрированный прогон по реальному пути, не изолированная проверка · «сделано» только по предъявленному логу, никогда по коду возврата; пустая или непарсимая выдача при нулевом коде возврата есть гэп наблюдения, а не факт «данных нет». (iii) **Денежные величины:** приёмка по цифрам против эталона `00 §3-БИС(b)`, расхождение закрыто явным правилом. Проверка «глазами» законна, но обязана оставлять след: что проверено, на каком экране, дата — строкой в session-блоке или артефактом в `/reference`. **Критерий приёмки выводится из формулы, а не из свойства данных:** обе формулы выписываются, разница предъявляется ДО прогона и входит в приёмку ожидаемой величиной.
**Последствия:**
- `08_TASK_BRIEF_TEMPLATE.md` — раздел приёмки [сейчас].
- `04_ROADMAP.md` — каждая детально расписанная задача несёт проверяемый критерий [сейчас].
- `T-0-3b` — приёмка формулируется сравнением формул, а не свойством данных [задачей T-0-3b].

## ADR-024 · Эталон датируется снимком; первоисточник — в приватный сателлит
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** приёмочная граница (ADR-017) требует датированного снимка эталона: учётная система пересчитывает историю при правках задним числом, и недатированный эталон даёт ложные расхождения. Прямой перенос донорского правила «снимок кладётся в `/reference`» сталкивается с красной линией: снимок экрана приложения вендора по конкретному договору несёт номер договора и, с большой вероятностью, имя клиента, а `00 §4` и ADR-001 запрещают персональные данные клиентов ломбарда в публичном репозитории.

В публичный репозиторий, в `/reference`, попадает только **обезличенный результат сверки**: дата снимка, предмет, наша величина, эталонная величина, расхождение, вывод. Номера договоров и имена клиентов не переносятся ни в каком виде.
**Последствия:**

## ADR-025 · Изоляция параллельных сессий, буфер session-блоков, проход сборки
**Дата:** 2026-08-07 · **Статус:** частично accepted, частично proposed (вариант C, решение Ilyas 2026-08-07)
**Контекст:** донорский метод покупает пропускную способность инвариантом «одна сессия — одно рабочее дерево — одна ветка» и отдельным проходом сборки, применяющим накопленные session-блоки. Три поломки, которые это лечит, у донора различены замером: гонка за индекс git, гонка за файл на диске, ложный вердикт хука под общим индексом. **Локального прецедента нет:** параллельных сессий в проекте не было ни разу, рабочих деревьев одно, веток `s/*` ноль.
**Разрез принятого и отложенного (вариант C).**
- **accepted, применяется сейчас:** закон «одно рабочее дерево на сессию» с явной командой заведения дерева (`git worktree add worktrees/<TASK> -b s/<TASK> HEAD`; точка ветвления задаётся словом `HEAD`, потому что настройка в конфиге машины не переживает переклонирование; каталог видимый, а не скрытый, потому что скрытого нет в диалоге выбора папки десктопного приложения), обе формы каталога деревьев в игнор-файле, счётчики деревьев и веток сессий в скрипте старта. Стоимость — одно предложение в конвенциях: механика под него приходит задачей `M-4` независимо. Основание принятия: класс отказа **тихий** (ложный вердикт хука под общим индексом), и мера стоимостью в предложение закрывает его дешевле любого другого способа. Механической проверки у правила нет; оно помечено непроверяемым намеренно и держится счётчиком, делающим нарушение видимым с одного взгляда.
- **proposed, ждёт гейта:** буфер `reference/_inbox/`, роль прохода сборки, скрипт проверки непересечения наборов файлов, режимы параллели и сборки в руководстве владельца. Основание отсрочки — предмет отсутствует, и это **измерено, а не предположено**: рабочих деревьев 1, веток `s/*` 0, единственная ветка `main`; обе заявленные в состоянии пары (`T-0-5` с `T-0-10`, `T-0-7` с дискавери БД) содержат задачу класса B и по `ADR-018` не параллелятся вовсе. Буфер и сборка сериализуют запись в состояние при нескольких потоках; последовательная очередь упорядочена сама, поэтому при нынешнем режиме они дают ноль, а стоят отдельной сессии на каждую пачку.
**Гейт снятия отложенной части — проверяемая формулировка.** Появление ДВУХ задач, у каждой из которых: (i) в таблице мандата `07_STATE` стоит класс A; (ii) в брифе объявлен полный набор файлов на запись маркированным списком; (iii) наборы не пересекаются. Части (i) и (ii) проверяются чтением, часть (iii) — скриптом, которого нет. Значит **первым шагом по гейту идёт скрипт проверки пересечения, а не заведение дерева.** Отказ проверки (поле отсутствует либо записано не списком) есть ЗАПРЕТ запуска, а не разрешение. До снятия задачи идут ПО ОДНОЙ.
**Последствия:**

## ADR-027 · Определение берётся из репозитория, не из текста запуска; правка по якорям — со сплошным поиском понятия
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** два разных отказа с одной причиной — утверждение принимается за факт без сверки с файлом. (1) Текст, которым запущена сессия METHOD-UPGRADE, сделал о содержимом этого репозитория восемь утверждений, оказавшихся неверными: журнал решений назван шестнадцатью записями при фактических двенадцати; роудмап назван не требующим правки при семи задачах, живущих в состоянии без строк роудмапа; раскрытие пароля названо однократным при восьми коммитах истории и двух местах в рабочем дереве. Сессия, принявшая текст запуска за вход, приняла бы все восемь. (2) `ADR-009` запретил дамп структуры в публичном репозитории, но не назвал, где дамп живёт; правка применилась по перечисленным в решении якорям, остаток нашёлся через одиннадцать дней и стоил отдельного решения `ADR-016`, а раздел `02 §3` простоял пустым при выполненной задаче.
**Решение:** (1) **Определение работы цитируется дословно из файла репозитория.** Текст, которым сессия запущена, входом НЕ является: его утверждение о содержимом репозитория, не подтверждённое файлом, есть стоп-условие и называется в отчёте поимённо. Отсутствие расхождения тоже называется одной строкой — канал, о котором отчёт молчит, нельзя ни измерить, ни закрыть по факту. (2) **Решение, отменяющее или переопределяющее понятие** (а не двигающее значение), применяется не только по перечисленным в нём якорям: исполнитель обязан прогнать сплошной поиск понятия по репозиторию с печатью совпавших строк с номерами и внести в блок последствий решение по КАЖДОМУ совпадению — «правится» либо «остаётся, потому что …». Пустая выдача поиска фактом не является и подтверждается обратным запросом.
**Последствия:**

- `CLAUDE.md` — короткая форма в законах [сейчас].
- `08_TASK_BRIEF_TEMPLATE.md` — требование «шапка и раздел правил говорят одно и то же» [сейчас].
- `M-3` — приёмка шага построена на сплошном поиске понятия «канонизац» с печатью всех совпадений [задачей M-3].
- Механической проверки у правила (1) нет и не предвидится; оно помечено непроверяемым и вынесено в ритуал старта [без правок].

**Дата:** 2026-08-08 · **Статус:** accepted
**Контекст:** разбор гейтов задачи `M-6` (артефакт `reference/ADJ_M-6_gates_2026-08-08.md`) нашёл три блокировки, из которых две — круговые, и одну ложную зелень. Замер 2026-08-08 дословно: (1) открытых задач класса A в таблице мандата шесть — `M-6`, `T-0-9`, `T-0-10`, `T-0-12`, `T-0-13`, `T-0-16`, то есть часть (i) гейта `ADR-025` выполнима; (2) поле «Файлы на запись» несут только брифы `M-1`, `M-3`, `M-4` — все три задачи ЗАКРЫТЫ, а брифы `T-0-2`, `T-0-3`, `T-0-5`, `T-0-10` поля не несут вовсе, то есть часть (ii) не выполнена ни на одной паре; (3) **все три закрытые задачи фазы M фактически правили `07_STATE.md` (коммиты `1156c10`, `b2937e2`, `63d0c13`, `32624be`), и ни одна не объявила этот файл в своём наборе** — объявленный набор `M-4` есть четыре пути в `tools/` и `reference/`, фактический на один файл шире.
Отсюда три вывода. **Первый круг:** скрипт проверки пересечения назван в `ADR-025` первым шагом ПО гейту, но живёт первым шагом задачи `M-6`, которую тот же гейт запирает — инструмент замера заперт внутри двери, которую открывает. **Второй круг:** условие (iii) «наборы не пересекаются» сегодня неисполнимо в обе стороны. Если наборы объявляются как сейчас, скрипт напечатает «пересечений нет», пока обе задачи в конце сессии пишут один и тот же файл состояния — это ЛОЖНАЯ ЗЕЛЕНЬ, тот самый класс тихого отказа, ради которого механизм и заводился. Если наборы объявляются полно, пересекается каждая пара всегда, и гейт не снимется никогда. Механизм, выводящий состояние из наборов, — буфер, то есть ровно то, что этим гейтом заперто.
**Решение.**
1. **`M-6` расщепляется на две задачи.** `M-6a` — скрипт проверки пересечения наборов; класс A, **гейта НЕ имеет**, стартует немедленно. Её приёмка самодостаточна и проверяется на СУЩЕСТВУЮЩИХ брифах: три брифа с полем дают печать обоих наборов целиком с указанием источника и печать всех пересечений, четыре брифа без поля дают ОТКАЗ. Пара задач для приёмки `M-6a` не нужна. `M-6b` — буфер `reference/_inbox/`, роль прохода сборки, полный оборот; остаётся под прежним гейтом.
2. **Состояние, реестр вопросов, журнал решений, его оглавление и архив в набор «Файлы на запись» НЕ входят.** Их правит не задача, а конец сессии: session-блок применяется по `05 §III` и принадлежит сессии, а не шагу брифа. Они объявляются ОБЩИМ СЕРИАЛИЗУЕМЫМ РЕСУРСОМ, и скрипт `M-6a` обязан печатать это отдельной строкой третьим исходом — молчание о них и есть ложная зелень. Пересечение считается по рабочим файлам; совпадение по общему ресурсу пересечением не считается, но при параллели требует сериализации, то есть буфера.
3. **Буфер и проход сборки остаются отложенными.** Основание отсрочки замером не изменилось: рабочих деревьев 1, веток `s/*` 0, параллельных сессий не было ни разу. Из гейта уходит только требование скрипта — он приходит `M-6a` независимо.
**Что отменяется в `ADR-025`.** Текст решения не переписывается (провенанс): отменяется дословно одна строка его блока последствий — «`reference/_inbox/.gitkeep`, `_ASSEMBLER.md`, скрипт проверки пересечения — [задачей `M-6`]». Скрипт приходит `M-6a`, буфер и роль сборки — `M-6b`. Формулировка «первым шагом по гейту идёт скрипт проверки, а не заведение дерева» НЕ отменяется, а исполняется: скрипт становится задачей без гейта.
**Сплошной поиск понятия (ADR-027).** Прогнаны три поиска — «Файлы на запись» (21 совпадение), «пересечен/непересек» (62), «буфер» (10). Решение по каждому: живые документы `04_ROADMAP`, `05_CONVENTIONS`, `07_STATE`, `07_GAPS`, `08_TASK_BRIEF_TEMPLATE`, `09_RUNBOOK`, `briefs/_GENERATOR.md`, `.claude/agents/generator.md` — правятся, перечислены ниже поимённо. Брифы закрытых задач (`briefs/M-1.md`, `briefs/M-3.md`, `briefs/M-4.md`) — остаются как есть, потому что это запись фактически исполненной работы, а не действующее правило; их наборы не пересчитываются. Датированные артефакты `reference/*` — остаются как есть, потому что снимок не переписывается задним числом (`ADR-024`). Текст `ADR-025` в журнале — остаётся, отменённая строка названа выше поимённо.
**Последствия:**
- `04_ROADMAP.md` — строка `M-6` заменяется двумя (`M-6a` без гейта, `M-6b` под гейтом); строка зависимостей переписана [сейчас].
- `07_STATE.md` — таблица мандата: строка `M-6` заменяется двумя; знаменатель счётчика фазы M становится 7 [сейчас].

## ADR-029 · Ротация пароля администратора БД не выполняется; риск принят владельцем и снят с блокеров
**Дата:** 2026-08-08 · **Статус:** accepted (решение владельца, не архитектора)
**Контекст:** задача `M-5` стояла `todo` класса B и ждала подтверждения с 2026-08-07. Состояние несло блокер: учётная запись администратора БД считается скомпрометированной в пределах контура, значение раскрыто в публичной истории репозитория и удалением файлов не закрывается. Единственным закрытием называлась смена значения на стороне сервера.
**Решение владельца (Ilyas, 2026-08-08, дословно по смыслу):** `M-5` замораживается и к ней до конца проекта не возвращаются; значение не меняется. Решение объявлено не подлежащим обсуждению. Архитектор возражений не заявляет и фиксирует последствия.
**Что это меняет фактически.**
- Раскрытое значение остаётся действующим на всём горизонте проекта. Это не «риск, который закроется позже», а **принятый риск**: строка перестаёт быть блокером и становится записью архива.
- Механическая защита от ПОВТОРЕНИЯ остаётся в силе и не ослабляется: проверка на секреты в хуке (`ADR-022`) стоит и работает.
- Единственная мера, остающаяся в нашей власти, — не запускать прод-конвейер под административной учётной записью. Она реализуется задачей `T-0-5` (read-only пользователь) и от этого решения не отменяется, а становится более важной: раньше она была одной из двух мер, теперь единственная.
- Обращения к БД остаются классом B до `T-0-5` — этот пункт `ADR-018` решением не затрагивается.
**Что отменяется.** Строка блока последствий `ADR-022` «Проверка на секреты закрывает повторение, но НЕ раскрытие, уже случившееся — [задачей `M-5`]» отменяется в части адресата: раскрытие не закрывается ничем, задачи-адресата больше нет. Текст `ADR-022` не переписывается (провенанс), отмена названа здесь.
