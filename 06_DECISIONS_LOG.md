## ADR-001 · Публичный моно-репо + правило санитарии
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** raw-URL без токенов — нулевая настройка для сессий (проверено на dom-prorab-catalog); но проект содержит контур клиента.
**Решение:** репо `lombard-ops` публичный, docs+код вместе. ЗАПРЕЩЕНО в репо: креды/ключи любого рода (в т.ч. VPN-конфиги WireGuard), публичные endpoint'ы контура клиента (DDNS-имена, внешние порты VPN), токены Telegram, ПДн клиентов ломбарда (имена/телефоны/номера договоров в примерах — обезличивать). ДОПУСТИМО: внутренние LAN-IP, номера портов сервисов, PROJECT_ID, имена ресурсов GCP.
**Последствия:** дампы структуры БД перед коммитом санитизируются; секреты — Secret Manager; примеры данных — синтетика.

## ADR-002 · Единое Cloud Run приложение + Identity Platform вместо Apps Script / GCS static / cf-api
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** требование логин/пароль + роли несовместимо с Apps Script «Anyone»; драфт ТЗ размазывал UI по трём технологиям и сам помечал Apps Script на снос при росте; signed-URL через HMAC в Apps Script — самый хрупкий пункт драфта.
**Решение:** один Cloud Run сервис `app-lombard` (React + API); auth — Identity Platform (email+пароль), роли `owner`/`manager`/`assessor` в custom claims; API проверяет токен и роль на каждом запросе. Все экраны — роуты одного приложения.
**Последствия:** cf-api, GCS static hosting и Apps Script не строятся; фото — обычные signed URL из бэкенда.

## ADR-003 · Ingestion: pull-коннектор из БД Firebird; fallback — агент на сервере
**Дата:** 2026-07-10 · **Статус:** accepted (канал доставки — pending, см. ADR по T-0-8)
**Контекст:** дано прямое read-only подключение к БД PawnShop; file-drop драфта делал Бектура ручным звеном и порождал staleness-проблему.
**Решение:** данные забирает `job-connector` (Cloud Run Job) по расписанию напрямую из Firebird. Ручная загрузка файлов не строится. Запасные каналы: (B) агент на ERP-сервере с только исходящим пушем в GCS; (C) штатная выгрузка PawnShop «в бух. программы».
**Последствия:** дискавери смещается на схему БД и сеть; staleness-проверка остаётся как guard обрыва связи.

## ADR-004 · Guard схемы Firebird
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** вендор меняет структуру БД при обновлениях и не уведомляет.
**Решение:** перед каждым чтением — отпечаток метаданных используемых таблиц (RDB$) сверяется с эталоном в mapping.json; расхождение → стоп + алерт, чтения нет. `SELECT *` запрещён. Обновление эталона — осознанная правка конфига.
**Последствия:** обновление PawnShop ломает конвейер громко и безопасно, а не тихо портит данные.

## ADR-005 · Порядок фаз: конвейер данных раньше форм
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** драфт ставил форму осмотра первой (логично при file-drop); при pull-коннекторе данные доступны сразу, а форма требует готового приложения с auth. Урок референс-проекта: интегральный путь проверять рано.
**Решение:** Фаза 1 — конвейер + светофор с tracer bullet в конце фазы; Фаза 2 — приложение и формы; Фаза 3 — Stop-Loss.
**Последствия:** Иса получает ценность (сводка, алерты) раньше; допущения о данных проверяются первыми.

## ADR-006 · balance_amount вычисляется на нашей стороне
**Дата:** 2026-07-10 · **Статус:** accepted
**Контекст:** ответ вендора: начисления (%/пени) в БД не хранятся, считает приложение.
**Решение:** балансовая стоимость вычисляется в cf-daily из условий договора (тело, ставка, пени-правила — маппинг T-0-3) по формулам `03 §4`. Валидация: сверка на нескольких договорах с цифрами из UI PawnShop.
**Последствия:** дискавери обязан найти поля условий; расхождение с PawnShop UI — блокер запуска Фазы 3.

## ADR-009 · Дампы структуры БД вендора не коммитятся в публичный репо
**Дата:** 2026-07-14 · **Статус:** accepted
**Контекст:** вендор «Алгоритм» считает схему БД конфиденциальной; полный дамп структуры (108 таблиц, 1018 колонок) получен при выполнении T-0-2.
**Решение:** дампы структуры БД передаются архитектору только в чат (вне репо). В репо попадает исключительно маппинг используемых полей (документация `02 §3`). Синтетические примеры в кодексе/конфигах — без специфичных колонок вендора.
**Последствия:** T-0-3 и далее работают с производным маппингом (`mapping.json`), не с полным дампом; дамп остаётся в истории чата как справка для аналитики, недоступный для public github.

## ADR-010 v3 · Хранение (STORAGE_*) входит в balance_amount
**Дата:** 2026-07-25 · **Статус:** accepted (v1 и v2 superseded; v2 предполагала возможность «везде ноль»)
**Контекст:** структура CONTRACTS_TERMS показывает три симметричных семейства начислений (проценты / хранение / страховка), STORAGE_VAL имеет тип, идентичный процентной ставке. Владелец (Иса) подтвердил: из 98 договоров 6 несут начисление за хранение по тарифу прошлого года. Формула 03 §4 (тело + % + пеня) их не учитывает. Эти 6 — самые старые договоры портфеля, то есть наиболее вероятные обитатели 🟠/🔴, где точность баланса определяет решения Stop-Loss.
**Решение:** (1) хранение — полноправная компонента balance_amount, 03 §4 расширяется; (2) формула начисления определяется в T-0-3b и подтверждается оракулом UI на всех шести договорах (набор мал — сверяется целиком, не выборкой); (3) в слой канонизации ставится блокирующее утверждение: активный договор с ненулевым STORAGE_VAL или INSURE_VAL, для которого формула не определена → стоп + алерт, не тихий недосчёт (философия ADR-004 применительно к данным); (4) INSURE_* обрабатывается тем же механизмом; на текущих данных нулевое, но утверждение его страхует.
**Последствия:** правка 03 §4 в T-0-3b; T-0-3b получает готовый оракульный набор из 6 договоров и независимый контрольный счёт от владельца.

## ADR-016 · Размещение вендорских артефактов и маппинга
**Дата:** 2026-07-25 · **Статус:** accepted
**Контекст:** ADR-009 запретил полный дамп структуры в публичном репо, но не назвал, где он живёт. Итог: дамп остался в истории чата, а `mapping.json` — на машине Ilyas; 02 §3 в репо простояла пустой 11 дней при выполненной задаче.
**Решение:** (1) `mapping.json` — источник истины в публичном репо по пути `/connector/mapping.json`; допустимо по ADR-009 (производный маппинг used-полей) и необходимо: fingerprint used-таблиц — обязательный вход guard'а ADR-004. Копия в GCS `${PROJECT_ID}-config` — деплой-артефакт, не источник истины. (2) Полный дамп структуры, инвентарь схемы и исторические экстракты — в **приватный репо-сателлит `lombard-ops-vendor-schema`**, путь `schema-snapshots/<YYYY-MM-DD>_<артефакт>` + README с происхождением и версией билда PawnShop. Выбран git, а не GCS: вендор не уведомляет об обновлениях, поэтому нужен `diff` между снимками схемы — git даёт его без инструментов. (3) Инструменты разбора (парсеры) — в публичный репо: это наш код, не схема вендора.
**Последствия:** T-0-10 создаёт хранилище и переносит артефакты; после обновления PawnShop дифф снимков становится штатной процедурой при срабатывании guard'а.

## ADR-017 · Главный принцип: граница контракта двойная + закон фикс-форварда
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** метод держится на границе, которую слои не пересекают, но в конституции она не была объявлена главным принципом. Проверка по репозиторию показала, что границ фактически две и обе уже существуют: структурная — слой канонизации (`00 §3` принцип 3, правило в `02 §3`); приёмочная — экран приложения вендора (ADR-006, ADR-010 v3, «оракул на 6 договорах» в состоянии). Проверка кандидата на структурную границу вопросом «можно ли заменить производителя, не трогая потребителя» пройдена буквально: канал прод-подключения (`T-0-8`) до сих пор не выбран, а потребители уже спроектированы.
**Решение:** внести в конституцию секцию `3-БИС`, назвав (a) слой канонизации структурной границей, (b) внешний эталон границей приёмки с иерархией «экран вендора → агрегат по таблицам → число владельца», (c) guard схемы (ADR-004) её механической проверкой. Добавить закон фикс-форварда: слой не лезет через границу чинить чужой слой; мерить там, где видно, чинить там, где причина; разовое исключение — только явный override с причиной и сроком снятия, записанный решением.
**Последствия:**
- `00_CHARTER.md` §3-БИС — вставка [сейчас]. Номер `3-БИС` намеренный: сквозная перенумерация сломала бы ссылки `00 §4`/`§5`/`§6` в конвенциях, бутстрапах ролей, шаблоне брифа и четырёх брифах.
- `01_ARCHITECTURE.md`, `02_DATA_CONTRACTS.md` — сплошной поиск понятия «канонизация» с печатью всех совпадений и решением по каждому [задачей M-3].
- `03_BUSINESS_SPEC.md` — [без правок].

## ADR-018 · Модель исполнения: сессия исполняет сама; мандат по классу задачи
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** действующая модель (`05 §I`) ставит человека в каждый круг «выдал скрипт → скопировал → запустил → вернул лог». Владелец принял решение перейти на исполнение сессией. Мандат по задаче даёт узкое место: каждая задача ждёт отдельного решения.
**Решение:** мандат выдаётся по КЛАССУ задачи. Класс A — постоянный: чтение всего, дискавери, написание кода и конфигов без применения, запись в staging и `/reference`, локальный коммит. Класс B — задача-специфичное решение владельца, перечислен буквально в `05 §I`: облачные ресурсы, секреты, отправка в мессенджер реальным людям, операции за авторизацией, обращения к БД PawnShop (временно, до `T-0-5`), правки порогов цены, публикация наружу. При сомнении — класс B. Запись в БД PawnShop классом B не является: она запрещена совсем красной линией `00 §4`. Перед запросом подтверждения класса B — отдельное сообщение «что, на каком объекте, чем откатывается». Один скрипт на ШАГ брифа, не на команду. Ревью границы берут три механизма: хук, контрактные тесты, отдельная архитекторская сессия на диффах; совмещение автора и адъюдикатора запрещено.
**Последствия:**
- `05_CONVENTIONS.md` §I — замена блоков «Роли» и «Модель исполнения» [сейчас].
- `07_STATE.md` — таблица мандата, парная задача-строкам [сейчас].
- `CLAUDE.md` — закон о классах [сейчас].
- `.claude/settings.json` — разрешено/спросить/запрещено на уровне инструмента [задачей M-1].
- `08_TASK_BRIEF_TEMPLATE.md` — поле «Класс задачи» [сейчас].
- `09_RUNBOOK.md` — режим ревью на границе [сейчас].
- Строка «обращения к БД — класс B» снимается одной правкой после закрытия `T-0-5` [задачей T-0-5].

## ADR-019 · Компактизация состояния: индекс решений, архив, реестр вопросов, стенд-ап
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** замер по диску: раздел «Сделано» — 10 строк и растёт без границы; открытые вопросы — 9 строк плоским списком без идентификаторов, статусов и гейтов; состояние 4 450 байт, журнал решений 14 396 байт. Ретрофит этого разреза в проекте-доноре делался на файле в 300 КБ и стоил двух решений и сплошного прохода. Цена разреза — единственная в плане перехода, которая растёт каждый день.
**Решение:** три разреза по принципу «оглавление в обязательный контекст, полный текст точечно». (1) `06_DECISIONS_LOG` (полный текст) ↔ `06_INDEX` (номер · заголовок · дата · статус); в обязательный контекст входит только индекс. (2) `07_STATE` (только ОТКРЫТОЕ) ↔ `07_ARCHIVE` (закрытое дословно); полное закрытие строки = перенос в архив ТЕМ ЖЕ коммитом. (3) `07_STATE` (индекс вопросов: `ID · статус · вопрос одной фразой · гейт`) ↔ `07_GAPS` (полный текст); новая строка заводится в ОБА файла одним коммитом. Статус — из закрытого словаря `OPEN` / `READY` / `DEFER` / `PARTIAL`. Блок фокуса разделяется на стенд-ап (ровно пять строк, ЗАМЕНЯЕТСЯ целиком) и «Подробности для модели» (дописывается; критерий записи — только то, без чего сломается СЛЕДУЮЩАЯ сессия).
**Последствия:**
- `06_INDEX.md`, `07_GAPS.md`, `07_ARCHIVE.md` — новые файлы [сейчас].
- `07_STATE.md` — полная замена структуры [сейчас].
- `README.md` — карта базы знаний [сейчас].
- Хук: проверки «append решения ⇒ строка в индексе», «строка исчезла ⇒ архив», «множества ID индекса и реестра совпадают» [задачей M-4].

## ADR-020 · Ретайр роли Applier
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** роль ручного механического переноса session-блоков в файлы репозитория осмысленна, пока сессия не пишет на диск. С переходом на исполнение сессией (ADR-018) она теряет предмет. Плюс прецедент качества: в `CHANGELOG.md` запись `T-0-2` продублирована целиком — блоки строк 3–11 и 12–20 побайтово идентичны. Ручной перенос уже дал дубль, который никто не заметил три недели.
**Решение:** `_APPLIER.md` ретайрится. Файл не удаляется, а заменяется надгробием со ссылкой на это решение: удаление стирает провенанс, а репозиторий публичный и ссылки на файл могут существовать снаружи. Работу роли берут: в режиме внутри инструмента — сама сессия; при появлении параллельных сессий — проход сборки (отложенная часть ADR-025).
**Последствия:**
- `_APPLIER.md` — замена содержимого надгробием [сейчас].
- `README.md` — строка «Applier (Haiku)» в запуске ролей убирается [сейчас].
- `05_CONVENTIONS.md` — упоминания applier в Части III [сейчас].
- Дубль в `CHANGELOG.md` — [задачей T-0-16].

## ADR-021 · Единственный режим чтения — локальный диск; единственный источник списка обязательного контекста
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** два дефекта с общим корнем — источник истины назван в нескольких местах и в разных вариантах. (1) Сплошной поиск дал ТРИ места, где перечислен обязательный контекст, и ДВА разных набора, ни один из которых не совпадает с другим: `05:20` — `00+05+07+11`; `05:126` — `00+04+06+07`; `_ARCHITECT.md:6` — `00+04+06+07`, причём `_ARCHITECT.md:7` относит конвенции к разряду «по задаче, если сессия их касается». Правило языка ответов и правила агента живут операционно только в конвенциях; сессия, стартовавшая по списку бутстрапа архитектора, нарушает их в первом же ответе — этот отказ зафиксирован в проекте-доноре с датой. (2) Раздел «Доступ к документации в чате» предписывает чтение репозитория по сетевым ссылкам с пиннингом по коммиту. Это было верно, пока сессии шли в обычном чате; внутри инструмента файл лежит на диске, а сеть отдаёт кэш, то есть правило прямо вредно. Сплошной поиск нашёл сетевые ссылки в семи файлах, включая **два невыполненных брифа с незаполненным плейсхолдером коммита** (`briefs/T-0-5.md:15`, `briefs/T-0-10.md:14`) — оставленный плейсхолдер есть дефект посева, а не «потом».
**Решение (владелец, 2026-08-07):** (1) **Все роли работают внутри инструмента, на ЛОКАЛЬНОМ репозитории. Второго режима чтения нет.** Файлы читаются с диска по именам; `curl`, raw-URL, браузерный фетчер и пиннинг по коммиту за содержимым репозитория запрещены. Коммит фиксируется командой `git rev-parse HEAD`. Сеть остаётся для работы с удалённым репозиторием (`fetch`, `push`) и для задач, где внешний источник и есть предмет. (2) **Разговор без доступа к диску сессией не является:** он не цитирует файлы, не выдаёт патчей и в репозиторий не входит; чтобы его результат попал в проект, он переформулируется задачей. Роль без доступа к источнику истины неизбежно работает по памяти, а это запрещено главным законом. (3) Список обязательного контекста существует в ОДНОМ экземпляре — в `CLAUDE.md`; из всех прочих мест на него ссылаются, но не цитируют. (4) Разрез автора и адъюдикатора сохраняется: мандат класса A даёт право писать код и коммитить локально, но НЕ даёт права назначать правило.

## ADR-022 · Механические проверки на коммите
**Дата:** 2026-08-07 · **Статус:** accepted

## ADR-023 · Три типа приёмки; правило формулы; след от проверки глазами
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** одно решение (ADR-015) уже было потрачено целиком на спор о том, что считать приёмкой задачи `T-0-3`. Тип приёмки не был назван, поэтому спор был неизбежен. Отдельно: `ADR-010 v3` добавляет в формулу баланса третью компоненту, а `T-0-3b` эту формулу определяет — то есть соблазн написать приёмку «сумма портфеля не изменилась» возникнет на первой же правке и будет невыполним по построению, потому что добавление компоненты сдвигает сумму арифметически неизбежно.
**Решение:** три типа приёмки по типу задачи. (i) **Дискавери:** знание зафиксировано в репозитории и трассируемо к источнику, эталон датирован, открытый вопрос помечен на закрытие; возврат — обогащение репозитория, не код. (ii) **Код:** контрактный тест на границе (отпечаток схемы плюс контракт канонического представления) · интегрированный прогон по реальному пути, не изолированная проверка · «сделано» только по предъявленному логу, никогда по коду возврата; пустая или непарсимая выдача при нулевом коде возврата есть гэп наблюдения, а не факт «данных нет». (iii) **Денежные величины:** приёмка по цифрам против эталона `00 §3-БИС(b)`, расхождение закрыто явным правилом. Проверка «глазами» законна, но обязана оставлять след: что проверено, на каком экране, дата — строкой в session-блоке или артефактом в `/reference`. **Критерий приёмки выводится из формулы, а не из свойства данных:** обе формулы выписываются, разница предъявляется ДО прогона и входит в приёмку ожидаемой величиной.
**Последствия:**
- `08_TASK_BRIEF_TEMPLATE.md` — раздел приёмки [сейчас].
- `04_ROADMAP.md` — каждая детально расписанная задача несёт проверяемый критерий [сейчас].
- `T-0-3b` — приёмка формулируется сравнением формул, а не свойством данных [задачей T-0-3b].

## ADR-024 · Эталон датируется снимком; первоисточник — в приватный сателлит
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** приёмочная граница (ADR-017) требует датированного снимка эталона: учётная система пересчитывает историю при правках задним числом, и недатированный эталон даёт ложные расхождения. Прямой перенос донорского правила «снимок кладётся в `/reference`» сталкивается с красной линией: снимок экрана приложения вендора по конкретному договору несёт номер договора и, с большой вероятностью, имя клиента, а `00 §4` и ADR-001 запрещают персональные данные клиентов ломбарда в публичном репозитории.

В публичный репозиторий, в `/reference`, попадает только **обезличенный результат сверки**: дата снимка, предмет, наша величина, эталонная величина, расхождение, вывод. Номера договоров и имена клиентов не переносятся ни в каком виде.

## ADR-025 · Изоляция параллельных сессий, буфер session-блоков, проход сборки
**Дата:** 2026-08-07 · **Статус:** частично accepted, частично proposed (вариант C, решение Ilyas 2026-08-07)
**Контекст:** донорский метод покупает пропускную способность инвариантом «одна сессия — одно рабочее дерево — одна ветка» и отдельным проходом сборки, применяющим накопленные session-блоки. Три поломки, которые это лечит, у донора различены замером: гонка за индекс git, гонка за файл на диске, ложный вердикт хука под общим индексом. **Локального прецедента нет:** параллельных сессий в проекте не было ни разу, рабочих деревьев одно, веток `s/*` ноль.
**Разрез принятого и отложенного (вариант C).**
- **accepted, применяется сейчас:** закон «одно рабочее дерево на сессию» с явной командой заведения дерева (`git worktree add worktrees/<TASK> -b s/<TASK> HEAD`; точка ветвления задаётся словом `HEAD`, потому что настройка в конфиге машины не переживает переклонирование; каталог видимый, а не скрытый, потому что скрытого нет в диалоге выбора папки десктопного приложения), обе формы каталога деревьев в игнор-файле, счётчики деревьев и веток сессий в скрипте старта. Стоимость — одно предложение в конвенциях: механика под него приходит задачей `M-4` независимо. Основание принятия: класс отказа **тихий** (ложный вердикт хука под общим индексом), и мера стоимостью в предложение закрывает его дешевле любого другого способа. Механической проверки у правила нет; оно помечено непроверяемым намеренно и держится счётчиком, делающим нарушение видимым с одного взгляда.
- **proposed, ждёт гейта:** буфер `reference/_inbox/`, роль прохода сборки, скрипт проверки непересечения наборов файлов, режимы параллели и сборки в руководстве владельца. Основание отсрочки — предмет отсутствует, и это **измерено, а не предположено**: рабочих деревьев 1, веток `s/*` 0, единственная ветка `main`; обе заявленные в состоянии пары (`T-0-5` с `T-0-10`, `T-0-7` с дискавери БД) содержат задачу класса B и по `ADR-018` не параллелятся вовсе. Буфер и сборка сериализуют запись в состояние при нескольких потоках; последовательная очередь упорядочена сама, поэтому при нынешнем режиме они дают ноль, а стоят отдельной сессии на каждую пачку.
**Гейт снятия отложенной части — проверяемая формулировка.** Появление ДВУХ задач, у каждой из которых: (i) в таблице мандата `07_STATE` стоит класс A; (ii) в брифе объявлен полный набор файлов на запись маркированным списком; (iii) наборы не пересекаются. Части (i) и (ii) проверяются чтением, часть (iii) — скриптом, которого нет. Значит **первым шагом по гейту идёт скрипт проверки пересечения, а не заведение дерева.** Отказ проверки (поле отсутствует либо записано не списком) есть ЗАПРЕТ запуска, а не разрешение. До снятия задачи идут ПО ОДНОЙ.

## ADR-027 · Определение берётся из репозитория, не из текста запуска; правка по якорям — со сплошным поиском понятия
**Дата:** 2026-08-07 · **Статус:** accepted
**Контекст:** два разных отказа с одной причиной — утверждение принимается за факт без сверки с файлом. (1) Текст, которым запущена сессия METHOD-UPGRADE, сделал о содержимом этого репозитория восемь утверждений, оказавшихся неверными: журнал решений назван шестнадцатью записями при фактических двенадцати; роудмап назван не требующим правки при семи задачах, живущих в состоянии без строк роудмапа; раскрытие пароля названо однократным при восьми коммитах истории и двух местах в рабочем дереве. Сессия, принявшая текст запуска за вход, приняла бы все восемь. (2) `ADR-009` запретил дамп структуры в публичном репозитории, но не назвал, где дамп живёт; правка применилась по перечисленным в решении якорям, остаток нашёлся через одиннадцать дней и стоил отдельного решения `ADR-016`, а раздел `02 §3` простоял пустым при выполненной задаче.
**Решение:** (1) **Определение работы цитируется дословно из файла репозитория.** Текст, которым сессия запущена, входом НЕ является: его утверждение о содержимом репозитория, не подтверждённое файлом, есть стоп-условие и называется в отчёте поимённо. Отсутствие расхождения тоже называется одной строкой — канал, о котором отчёт молчит, нельзя ни измерить, ни закрыть по факту. (2) **Решение, отменяющее или переопределяющее понятие** (а не двигающее значение), применяется не только по перечисленным в нём якорям: исполнитель обязан прогнать сплошной поиск понятия по репозиторию с печатью совпавших строк с номерами и внести в блок последствий решение по КАЖДОМУ совпадению — «правится» либо «остаётся, потому что …». Пустая выдача поиска фактом не является и подтверждается обратным запросом.
**Последствия:**

- `CLAUDE.md` — короткая форма в законах [сейчас].
- `08_TASK_BRIEF_TEMPLATE.md` — требование «шапка и раздел правил говорят одно и то же» [сейчас].
- `M-3` — приёмка шага построена на сплошном поиске понятия «канонизац» с печатью всех совпадений [задачей M-3].

## ADR-030 · Назначенная модель печатается механически: файл роли — источник истины, скрипт старта — витрина, session-блок — замер
**Дата:** 2026-08-08 · **Статус:** accepted
**Контекст:** владелец спросил, как получать ответ «какой моделью писать брифы» постоянно, без отдельных просьб. Замер показал, что ответ в репозитории УЖЕ есть и в трёх местах не противоречив: конвенция `05 §I` называет архитектору дорогую модель, генератору и исполнителю среднюю; конвенция `05 §II` даёт правило выбора (задача расписана в роудмапе и решений не требует → генератор, нужны решения → архитектор); файлы ролей несут поле `model` со значениями `opus`, `sonnet`, `sonnet`. Дефекта содержания нет — есть дефект ДОСТАВКИ: ни одно из трёх мест не попадается на глаза в момент запуска сессии, и ответ каждый раз добывается вопросом в чат. Отдельно: `Q-13` (правильно ли это назначение) не может закрыться замером, потому что модель фактически запущенной сессии нигде не записывается — канал замера отсутствует.
**Решение.**
1. **Источник истины — поле `model` в файле роли**, а не текст конвенций и не память. При расхождении текста с файлом прав файл: инструмент читает файл.
2. **Скрипт старта печатает таблицу «роль → модель» шестым счётчиком** вместе с правилом выбора. Роль без объявленной модели печатается как `CONTEXT GAP` и валит вердикт: неопределённость обязана быть видимой, а не подразумеваемой.
3. **Шапка брифа несёт поле «Кем исполняется»** — роль и модель. Ответ едет вместе с брифом и не требует ни чата, ни памяти. Отступление от назначенной модели допускается, но объявляется в брифе поимённо с причиной.
4. **Session-блок записывает роль и модель ФАКТИЧЕСКИ запущенной сессии.** Это не украшение отчёта, а единственный вход, по которому `Q-13` когда-либо закроется: сравнивать назначение с отказами можно, только если известно, что было запущено.
**Что это НЕ решает.** Правильность самого назначения. `Q-13` остаётся открытым и решается по НАЗВАННЫМ отказам, а не мнением; до тех пор действует назначение из файлов ролей. Гейт строки переписан под появившийся канал замера.
**Последствия:**
- `tools/session_status.sh` — шестой счётчик [сейчас].
- `08_TASK_BRIEF_TEMPLATE.md` — поле «Кем исполняется» в шапке [сейчас].
- `05_CONVENTIONS.md` §II — абзац об источнике истины; §III — строка роли и модели в `SESSION_LOG` [сейчас].
- `09_RUNBOOK.md` — указание, что модель не выясняется вопросом [сейчас].
- `07_STATE.md` и `07_GAPS.md` — гейт `Q-13` переписан под канал замера [сейчас, одним коммитом].
- Механической проверки у поля «Кем исполняется» нет: хук не знает, какой моделью запущена сессия. Помечено непроверяемым намеренно [без правок].

## ADR-031 · Буфер session-блоков и проход сборки НЕ заводятся; отложенная часть ADR-025 закрывается отказом
**Дата:** 2026-08-08 · **Статус:** accepted
**Контекст:** отложенная часть `ADR-025` (буфер `reference/_inbox/`, роль прохода сборки, режимы параллели в руководстве) стояла `DEFER` со строкой `Q-12` и задачей `M-6b`. Замер на 2026-08-08: рабочих деревьев 1, веток `s/*` 0, параллельных сессий в проекте не было ни разу за всю его историю. Единственная часть связки, имевшая самостоятельную ценность, — скрипт проверки пересечения — выведена из-под гейта решением `ADR-028` и закрыта задачей `M-6a`: инструмент замера уже лежит в репозитории и работает.
**Решение:** отложенная часть закрывается ОТКАЗОМ, а не бесконечной отсрочкой. Буфер, роль прохода сборки и режимы параллели не заводятся. Строка `Q-12` закрывается, задача `M-6b` снимается с очереди, обе уезжают в архив. Фаза M на этом закрыта полностью.
**Основание — три довода, все от фактов репозитория.**
1. Буфер и сборка существуют ради одного: сериализовать запись в состояние при нескольких одновременных потоках. Потоков не было ни разу, и взяться им неоткуда — каждый шаг класса B идёт через подтверждение владельца, а два потока подтверждений на одного человека есть очередь с переключением контекста, а не ускорение (`ADR-018`).
2. Полезное с темы уже снято: скрипт проверки написан, прогнан на реальных брифах и лежит в `tools/`. Отказ не выбрасывает работу, он выбрасывает только церемонию.
3. Держать строку как `DEFER` не бесплатно: реестр открытых вопросов читается каждым стартом сессии, и вечно-отложенная строка тратит внимание каждый раз, ничего не приближая. Решение `ADR-026` требует у задачи проверяемой приёмки; у `M-6b` она была построена на полном обороте, который невозможно выполнить, пока предмета нет.
**Условие оживления — названо, чтобы отказ не был необратимым.** Тема заводится заново, если в очереди одновременно окажутся ДВЕ задачи класса A, которые владелец хочет вести параллельно, и скрипт `tools/intersect_check.sh` подтвердит непересечение их рабочих наборов. До этого момента задачи идут ПО ОДНОЙ, и это не ограничение метода, а описание фактического режима работы.
**Что НЕ отменяется.** Принятая часть `ADR-025` — закон «одно рабочее дерево на сессию», счётчики деревьев и веток в скрипте старта — остаётся в силе целиком: она про запрет двух сессий на одной папке, а не про параллель. Скрипт проверки пересечения остаётся и используется как проверка формы поля «Файлы на запись» в брифах.
**Последствия:**
- `07_STATE.md` и `07_GAPS.md` — строка `Q-12` закрывается, задача `M-6b` снимается [сейчас, одним коммитом].
- `07_ARCHIVE.md` — обе строки переносятся дословно [сейчас].
- `04_ROADMAP.md` — строка `M-6b` заменяется пометкой об отказе; фаза M закрыта [сейчас].
- `05_CONVENTIONS.md` §I — абзац о буфере переписан с «ждут гейта» на «не заводятся, условие оживления названо» [сейчас].
- `08_TASK_BRIEF_TEMPLATE.md` — поле «Параллель» больше не ссылается на снятие гейта [сейчас].
- `09_RUNBOOK.md` — раздел «что не проверено» приводится в соответствие [сейчас].

## ADR-032 · Гранты `PUBLIC` в базе вендора не отзываются; чтение-только обеспечивается нашим слоем и подтверждается замером

Первый: собственные права учётной записи `LOMBARD_RO` верны — ровно девять строк `SELECT` на девять таблиц брифа, грантор `SYSDBA`, скрипт `scripts/grant_ro.sql` идемпотентен, прогон без ошибок. Вопрос `Q-14` требовал выбора: отзывать права `PUBLIC` на девяти таблицах, на всей схеме вендора, или не трогать их вовсе.

**Заявление против факта — что измерено, а что было записано шире измеренного.** Состояние, реестр вопросов и реестр инфра-фактов несли формулировку «`PUBLIC` даёт `D/I/R/S/U` на девять наших таблиц и ещё ≥98 других». Артефакт замера доказывает другое: `SELECT` — на 107 таблицах (то есть кроме наших девяти ещё 98 несут как минимум чтение), а полный набор `D/I/R/S/U` предъявлен на девяти наших плюс одной проверенной вне списка. **Права ЗАПИСИ на остальных 98 таблицах не измерены ничем.** Формулировка правится по всем трём файлам этим решением, а замер, который закрывает неизвестное, добавлен в приёмку `T-0-5` шагом 6-ж. Расхождение названо здесь, потому что решение принимается по фактам, а не по их пересказу.

**Решение.**
1. **Гранты `PUBLIC` не отзываются** — ни минимальным вариантом (девять таблиц), ни полным (вся схема вендора). Ни один шаг проекта не выдаёт `REVOKE` на объектах вендорской базы без НОВОГО решения владельца, опирающегося на письменный ответ вендора.
2. **Красная линия `00 §4` не переписывается и не смягчается.** Правится не она, а описание меры, которое было неточным. Фраза «прод работает под read-only пользователем БД» до сих пор читалась как «СУБД не даст нам записать». Измеренная действительность иная: `LOMBARD_RO` есть учётная запись, СОБСТВЕННЫЕ права которой ограничены чтением, тогда как фактическая возможность записи открыта всем через `PUBLIC`. Обязательство «ни одной операции записи» лежит на нас и остаётся абсолютным; меняется только честное имя контроля, который его поддерживает.
3. **Контроль, физически отбивающий запись, переносится в НАШ слой — read-only транзакция.** Любое подключение коннектора и любой разовый запрос к базе PawnShop открывается транзакцией только на чтение. При живых грантах `PUBLIC` это единственный механизм, отбивающий запись на стороне сервера и не трогающий чужое состояние. Пока отказ не предъявлен логом, это ЗАЯВЛЕНИЕ, а не факт: замер вносится в приёмку `T-0-5` шагом 6-е и обязателен.
4. **Приёмка `T-0-5` переписывается этим решением.** Шаги 6-в и 6-г переклассифицируются из «провалено» в измеренный факт о среде: опровергнута их предпосылка (что фактические права учётки определяются только её собственными грантами), а не их исполнение. Добавляются шаг 6-е (отказ записи в read-only транзакции — лог обязателен, отсутствие строки отказа означает «не измерено», а не «прошло») и шаг 6-ж (агрегаты прав `PUBLIC` по буквам привилегий и счётчик учётных записей с собственными грантами; имена таблиц и учётных записей в публичный репозиторий не пишутся — `ADR-009`, `ADR-001`). Приёмка не подгоняется под результат: меняется проверяемое утверждение, и меняет его решение архитектора, а не рука исполнителя.
5. **Переезд обращений к БД из класса B в класс A по факту закрытия `T-0-5` ОТМЕНЯЕТСЯ.** `ADR-018` и `05 §I` обещали переезд «одной строкой после закрытия `T-0-5`» по названной причине: «класс защищает не от `SELECT`, а от того, что под текущими правами доступна и запись». Замер подтвердил эту причину ДЕЙСТВУЮЩЕЙ. Новое условие переезда — предъявленный лог шага 6-е; и переезжает не «обращение к базе» вообще, а ровно чтение под `LOMBARD_RO` в read-only транзакции. Всё прочее к базе остаётся классом B.
6. **Держатель ответа «сломает ли отзыв само приложение PawnShop» — вендор, а не мы.** Вопрос включается в письмо вендору (`T-0-12`) поимённо: полагается ли приложение на гранты `PUBLIC` и допускает ли вендор их сужение до чтения. До письменного ответа отзыва нет. Под недостающий факт заводится строка `Q-15`.

**Основание — четыре довода, все от фактов репозитория.**
1. **Минимальный вариант даёт меньше всего защиты при наибольшем риске.** Девять таблиц — это `CONTRACTS`, `SUBJECTS`, `OPERATIONS` и прочее ядро учёта, то есть ровно то, куда приложение вендора пишет постоянно. При этом `LOMBARD_RO` после такого отзыва read-only НЕ становится: `PUBLIC` остаётся на прочих таблицах. Наибольшая вероятность остановить работу ломбарда — ради заведомо неполной защиты.
2. **Полный вариант есть правка политики почти всей схемы без документации.** `T-0-2` намерил 108 таблиц; `PUBLIC` несёт `SELECT` на 107 из них. Структуру вендор не документирует (`00 §2`), а проверить последствия негде: копии базы у нас нет, и проверять на живой базе клиента означает проверять на проде.
3. **Отзыв запрещён действующими правилами, и не одной строкой.** Красная линия `00 §4` разрешает единственное исключение — заведение read-only пользователя. `05 §I` («только чтение из PawnShop») называет исключением создание пользователя и `GRANT SELECT`, но не `REVOKE`. Бриф `T-0-5` запрещает «правки существующих пользователей вендора» и отдельно требует лишнее «не отзывать самостоятельно, вернуть архитектору решением». Три независимых источника, ни один из которых не допускает отзыв по умолчанию.
4. **Угроза, от которой отзыв реально защищает, закрывается дешевле и в своём слое.** Наш код читает девять таблиц; практический риск — запись по ошибке нашего кода. Read-only транзакция отбивает её на сервере, стоит одной строки в коннекторе и не трогает ни одного объекта вендора. Это прямое применение закона границы `00 §3-БИС`: чинить там, где причина, — а причина возможной записи НАШИМ кодом лежит в нашем слое.

**Что решение НЕ закрывает — принятый риск, названный явно.** Любой, кто имеет пароль `LOMBARD_RO` и доступ к порту базы, может писать в неё сторонним клиентом: `PUBLIC` позволяет это всем. Периметр держит только правило файрвола на порту базы (`11_INFRA_FACTS`), и оно не защищает от кода, уже подключившегося изнутри LAN или VPN. Риск принят сознательно и по той же логике, что в `ADR-029`: он существовал до нас, создан не нами, а его закрытие требует изменения чужой системы. Формулировка не ослабляется до получения ответа вендора.

**Триггеры пересмотра — названы, чтобы решение не стало вечным.**
- Вендор письменно подтверждает, что приложение не полагается на `PUBLIC` → возвращаемся к отзыву минимальным вариантом, обязательно со снимком прав ДО правки как средством отката.
- Замер шага 6-е показывает, что read-only транзакция запись не отбивает → компенсирующего контроля нет, вопрос заводится в реестр заново и решается уже без опоры на наш слой.
- Зафиксирована любая запись в базу вендора со стороны нашего контура → инцидент, решение пересматривается немедленно.

**Сплошной поиск понятия (`ADR-027`).** Решение переопределяет понятие «после закрытия `T-0-5` чтение базы переезжает в класс A», поэтому прогнан сплошной поиск по репозиторию (`T-0-5`, «переедет», «временно, пока», «временно, до»). Решение по каждому совпадению: `05_CONVENTIONS.md:41,43` — **правится**, это первоисточник правила; `CLAUDE.md:74` — **правится**; `08_TASK_BRIEF_TEMPLATE.md:27` — **правится**; `07_STATE.md:52` (класс `T-0-3b`) — **правится**; `06_DECISIONS_LOG.md:91` (`ADR-018`) и `06_DECISIONS_LOG.md:231` (`ADR-029`) — **остаются**, тексты принятых решений не переписываются, отмена части названа здесь; `02_DATA_CONTRACTS.md:13` — **правится**, строка прод-доступа утверждает больше измеренного; `04_ROADMAP.md:37` — **правится** (приёмка); `04_ROADMAP.md:42,46` (`T-0-3b`, `T-0-14` зависят от `T-0-5`) — **остаются**, зависимость решением не меняется; `05_CONVENTIONS.md:139` — **остаётся**, и именно эта строка запрещает `REVOKE` без нового решения, её сила подтверждена; `07_ARCHIVE.md:76` — **остаётся**, архив дословен; `CHANGELOG.md:33`, `briefs/T-0-3.md:25,30,103`, `briefs/M-6a.md:48`, `01_ARCHITECTURE.md:10,24` — **остаются**, записи исполненной работы и описание канала, класса мандата не задают; `reference/PATCHES_METHOD-UPGRADE_2026-08-07.md:531,771,995,1202` — **остаются**, датированные снимки не переписываются.

## ADR-033 · Проба шага 6-е неразличающая: компенсирующий контроль не опровергнут и не подтверждён; контроль записи перестраивается на проверяемый в НАШЕМ слое
**Дата:** 2026-08-11 · **Статус:** accepted
**Контекст:** `ADR-032` принял риск не отзывать гранты `PUBLIC` при условии, что запись отбивает наш
слой — транзакция только на чтение при каждом подключении. Условие было объявлено заявлением до
предъявления лога. Лог предъявлен третьим прогоном шага 6-е
(`reference/T-0-5_readonly_tx_measurement_2026-08-11.md`) и прочитан состоянием, реестром и
инфра-фактами как ОПРОВЕРЖЕНИЕ контроля. Эта сессия разбирала опровержение и предъявленным логом
его не подтверждает.

**Что на самом деле в логе.** Обе пробы — `UPDATE DEPOSIT_TYPES SET ID = ID WHERE 1 = 0;`. Первая в
обычной транзакции, вторая после `SET TRANSACTION READ ONLY`. Вывод обеих — **тишина**: ни строки
отказа, ни строки успеха. Одинаковый вывод объявлен в брифе контролем исправности пробы для первой
и результатом измерения для второй. Один и тот же наблюдаемый вывод истолкован в две
противоположные стороны, и в логе нет ни одной строки, которая их различает.

**Почему это дефект пробы, а не находка.** Предикат `WHERE 1 = 0` выбран для безопасности и
гарантирует ноль задетых строк — на этом стоит вся карточка подтверждения шага. Значит проба
доходит до сервера, компилируется и не задевает ни одной записи. Утверждение «раз отказа нет —
режим только на чтение запись не отбивает» опирается на невысказанную предпосылку: что отказ по
режиму транзакции обязан прийти на операторе, ничего не меняющем. Предпосылка о движке никем не
измерена. Ровно тем же способом `ADR-032` разобрал шаги 6-в и 6-г: опровергнута не проба, а её
необъявленная предпосылка.

Живых объяснений тишины **три**, и лог не различает ни одной пары:
1. отказ по режиму транзакции печатается на уровне оператора — тогда контроля нет;
2. отказ печатается на уровне изменяемой записи — тогда проба с нулевым предикатом до него не
   доходит НИКОГДА, и контроль этим логом не проверялся;
3. `SET TRANSACTION READ ONLY` в этом клиенте молча не вступил в силу — тогда мерился не тот режим.

**Собственный закон проекта прочитан буквально.** `05 §I`, правила наблюдения: «для
отрицательного случая в выводе обязана быть строка отказа ИМЕННО той проверки, которую мерили».
Строки отказа нет — значит проверка не измерена. Сам бриф `T-0-5` в разделе «Шаг 6-е — НОВЫЙ»
пишет то же: «Отказа нет → это ЗАЯВЛЕНИЕ, а не факт». Пятнадцатью строками ниже, в разделе «Исходы
шага 6-е», тот же бриф пишет обратное: «Второе изменение прошло без ошибки → контроля нет ни на
уровне СУБД, ни на нашей стороне». Две формулировки одного шага противоречат друг другу; исполнитель
пошёл по второй. Расхождение внутри брифа названо здесь поимённо и снимается этим решением в пользу
первой — она совпадает с законом наблюдения, вторая ему противоречит.

**Решение.**
1. **Вердикт «компенсирующий контроль опровергнут» СНИМАЕТСЯ.** Контроль не опровергнут и не
   подтверждён — он **не измерен**. Артефакт замера не переписывается (`ADR-024`): правится не лог,
   а его толкование в состоянии, реестре и инфра-фактах.
2. **Действие исполнителя остаётся в силе целиком.** Остановка по названному стоп-условию, невыпуск
   шага 6-ж и вывод учётной записи из использования — верны при любом из трёх объяснений и
   отменяться не будут. Правило «сомнение толкуется в пользу остановки» сработало как задумано.
3. **Причина имеет значение и снимается замером, а не рассуждением.** Заводится задача `T-0-17`:
   поведение `SET TRANSACTION READ ONLY` в Firebird 2.5.9 меряется на НАШЕМ экземпляре, на
   выброшенной базе, двумя пробами — изменение, не задевающее ни одной строки, и изменение,
   задевающее строку. Класс A: чужого контура задача не касается вовсе.
4. **Решающая проба на базе клиента ЗАПРЕЩЕНА, и это структурный факт, а не осторожность.**
   Различить объяснения 1 и 2 на живой базе можно только изменением, задевающим строку; если контроль
   не держит, такое изменение и есть запись в базу вендора — прямой запрет `00 §4`. Отсюда общий
   вывод: **контроль, проверяемый только реальной записью в чужой прод, на этой базе непроверяем нами
   в принципе.** Проверка обязана уехать туда, где она исполнима, — к нам.
5. **Контроль записи перестраивается в три слоя, и основным становится НАШ, а не движковый.**
   - **Слой 1 (основной, механически проверяемый у нас).** Единственная точка доступа к базе
     PawnShop с белым списком операторов: на сервер не уходит ничего, кроме `SELECT`/`WITH`-выборки
     и чтения системных `RDB$`/`MON$`. Для кода — одна функция коннектора плюс тест на ней; для
     ручного прогона по RDP — файл запроса печатается ДО запуска и содержит только чтение (правило
     уже действует, `05 §I`). Слой не зависит от семантики движка и проверяется без обращения к
     чужой базе.
   - **Слой 2 (эшелон, остаётся, но называется честно).** Транзакция только на чтение остаётся
     обязательной в контракте канала (`02 §1`, `T-0-8`), но до замера `T-0-17` **не называется
     механизмом, отбивающим запись на стороне сервера**. Её наличие подтверждается ПОЛОЖИТЕЛЬНЫМ
     фактом — строкой `MON$`-метаданных о режиме текущей транзакции, — а не отсутствием ошибки.
   - **Слой 3 (СУБД).** Отзыв грантов `PUBLIC` — без изменений: не исполняется, заблокирован
     ответом вендора (`Q-15`, `T-0-12`). Это решение отзыв не разрешает и не приближает.
6. **Приёмка `T-0-5` правится второй раз.** Шаг 6-е в прежней форме (ждать строку отказа) снимается:
   он требует лога, который на этой базе честно получить нельзя. Вместо него — **шаг 6-е-БИС**,
   только чтение: под `LOMBARD_RO` после `SET TRANSACTION READ ONLY` предъявить строку `MON$` о
   режиме текущей транзакции. Он различает объяснение 3 от пары 1–2 и не трогает ни одной записи.
   Шаг 6-ж остаётся как был. `T-0-5` разблокирована: `blocked` → `todo`, класс мандата **B**.
7. **Условие переезда чтения в класс A переписывается второй раз.** Прежнее («предъявленный лог
   отказа записи в транзакции только на чтение») отменяется как неисполнимое. Новое — три
   предъявленных факта разом: (а) `T-0-17` напечатал на нашем экземпляре строку отказа именно по
   режиму транзакции на изменении, задевающем строку, и напечатал поведение пробы с нулевым
   предикатом; (б) на базе клиента предъявлена `MON$`-строка, что транзакция read-only с точки зрения
   движка; (в) обращение идёт через единственную точку доступа с белым списком операторов. Не
   предъявлен хоть один — класс B. Переезжает по-прежнему ровно чтение под read-only учётной записью,
   всё прочее к базе остаётся классом B при любом исходе.
8. **Новое правило наблюдения — «проба обязана различать исходы».** Проверка, у которой ожидаемый и
   противоположный исходы дают ОДИН И ТОТ ЖЕ вывод, проверкой не является ни в одну сторону.
   Положительный контроль засчитывается только тогда, когда он отличается от измеряемого случая
   наблюдаемо. Правило вносится в `05 §I` этим решением.

**Основание — от фактов репозитория.**
1. **Тишина против тишины.** В логе третьего прогона обе пробы дали одинаковый вывод. Вывод, не
   меняющийся между исходами, информации об исходе не несёт — это то же самое возражение, которым
   `05 §I` запрещает считать сделанным по коду возврата.
2. **Положительный контроль шага не контролировал измеряемое свойство.** Первая проба доказывает
   живое соединение и компиляцию оператора — то есть права, уже доказанные отдельно запросом к
   `RDB$USER_PRIVILEGES` в замере 2026-08-11. Того, что проба доходит до попытки изменить запись,
   она не доказывает при нулевом предикате ни в одной транзакции.
3. **Предпосылка о движке нигде в репозитории не измерена.** Ни один артефакт, ни одно решение не
   называет уровень, на котором Firebird 2.5.9 печатает отказ по режиму транзакции. Достраивать
   его рассуждением запрещает главный закон (anti-improvisation); значит остаётся замер, и он
   исполним у нас.
4. **Красная линия сама закрывает решающую пробу на проде.** Это не препятствие, а указание, где
   мерить: `00 §3-БИС` — мерить там, где видно, чинить там, где причина. Причина возможной записи
   нашим кодом лежит в нашем слое, туда же уезжает и основной контроль.

**Что решение НЕ меняет.**
- Красная линия `00 §4` — без правок, ни одной операции записи в базу вендора.
- Запрет `REVOKE` на объектах вендора без нового решения владельца — в силе дословно.

  сторонним клиентом) — в силе дословно и не ослабляется ни этим решением, ни исходом `T-0-17`.

**Триггеры пересмотра.**

## ADR-034 · Письмо вендору не отправляется: задача снята отказом владельца, отзыв прав `PUBLIC` уходит с горизонта проекта
**Дата:** 2026-08-11 · **Статус:** accepted
**Контекст:** решение `ADR-032` назначило держателем ответа вендора и подвесило на его письмо два
следствия: вопрос `Q-15` (полагается ли приложение PawnShop на гранты `PUBLIC`) и единственный путь
к отзыву этих грантов. Очередь исполнения, выставленная 2026-08-11, ставила письмо первым — как
работу с внешними часами. **Владелец решил письмо не отправлять:** вендор доработок под нас делать
не будет, обращение бесполезно. Решение владельца о взаимодействии с внешней стороной есть его
решение, а не архитектурное; здесь оно применяется к плану.

**Возражение названо один раз и снято.** Письмо просило не доработку, а два факта об уже
существующей системе. Возражение фиксируется, потому что решение по фактам, а не по их пересказу;
владелец подтвердил отказ, и дальше действует отказ.

**Что письмо несло — три груза, и каждый получает своё место.**
1. **Вопрос о `PUBLIC`** — снимается вместе с письмом. `Q-15` закрывается ОТКАЗОМ, а не отсрочкой.
2. **Уточнения по семантике начислений** — не теряются: у этой величины уже есть внешний эталон по
   `00 §3-БИС(b)` — экран приложения вендора на ту же дату, и приёмка `T-0-3b` требует схождения
   оракула UI на всех шести договорах с хранением. Письмо здесь было ускорителем, а не источником.
3. **Версия билда PawnShop для `T-0-10`** — переезжает с вендора на замер: свойства исполняемого
   файла и экран «О программе» на сервере ERP. Плейсхолдер `⏳ T-0-12` в брифе `T-0-10` заменяется
   на этот источник, чтобы задача не осталась с гейтом на несуществующее письмо.

**Решение.**
1. **`T-0-12` закрывается отказом** и переносится в архив дословно вместе с приёмкой. В очереди
   исполнения её нет.
2. **`Q-15` закрывается отказом** и переносится в архив дословно. Условие оживления названо, чтобы
   отказ не стал вечным молча: появилась возможность задать вопрос бесплатно (плановое обращение в
   поддержку по другому поводу, визит инженера вендора) ЛИБО появился способ проверить зависимость
   приложения от `PUBLIC` без вендора — тестовая копия базы, на которой отзыв обратим.
3. **Отзыв грантов `PUBLIC` уходит с горизонта проекта.** Не «отложен до ответа», а снят: ответа не
   будет. Триггер пересмотра `ADR-032` «вендор письменно подтверждает, что приложение не полагается
   на `PUBLIC`» объявляется несрабатывающим. Красная линия `00 §4` при этом не трогается, `REVOKE`
   по-прежнему запрещён без нового решения владельца — запрет усиливается, а не ослабляется.
4. **Слой СУБД закрыт постоянно, и это меняет вес оставшихся слоёв.** Из трёх слоёв контроля записи
   (`ADR-033`) третий выбывает навсегда. Наш слой — единственная точка доступа с белым списком
   операторов — становится не «основным на время», а единственным постоянным. Замер `T-0-17`
   (есть ли эшелон в движке) от этого только дорожает: он единственный оставшийся источник второго
   рубежа.
5. **Принятый риск становится ПОСТОЯННЫМ и переписывается в этой форме.** Формулировка «не
   ослабляется до ответа вендора» заменяется на «ответа не будет, риск принят на весь горизонт
   проекта». Периметр держат правило файрвола на порту базы и наш белый список; изнутри контура
   защиты нет и не будет. Это цена решения, названная явно, — по той же логике, что в `ADR-029`.
6. **Очередь исполнения пересобирается:** `T-0-5` (доисполнение, класс B) → `T-0-17` (замер на нашем
   экземпляре, класс A) → `T-0-3b`. Первое место освободилось, и его занимает работа, снимающая
   зависимость двух задач.

**Основание.**
1. **Решение о внешней стороне принадлежит владельцу.** Отношения с вендором ведёт он; сессия
   оценивает последствия для плана, а не целесообразность обращения.
2. **Гейт без держателя есть дефект строки.** `07_GAPS` требует у каждого вопроса названного гейта.
   После отказа гейт `Q-15` («письменный ответ вендора») перестал существовать, и строка обязана
   либо получить новый гейт, либо закрыться. Нового держателя у этого факта нет — значит закрытие.
3. **Дешёвая замена нашлась только одному грузу из трёх.** Версия билда снимается замером на
   сервере; семантика начислений закрыта внешним эталоном; зависимость приложения от `PUBLIC` не
   заменяется ничем, что мы вправе исполнить, — потому она и закрывается отказом, а не переносом.

**Сплошной поиск понятия (`ADR-027`).** Решение отменяет понятие «ответ вендора — гейт». Прогнан
поиск по `T-0-12` и `Q-15` с печатью совпавших строк. Решение по каждому:
`04_ROADMAP.md:45` — **правится** (строка задачи → снята отказом); `07_GAPS.md:22` — **правится**
(строка закрывается); `07_STATE.md:12,60,85,107,126` — **правятся** (стенд-ап, очередь, таблица
мандата, индекс вопросов, формулировка принятого риска); `briefs/T-0-10.md:65` — **правится**
(плейсхолдер версии билда переезжает на замер); `briefs/T-0-5.md:223,318` — **остаются**: это
пояснения к шагу 6-ж о том, что окончательный ответ давал бы вендор; после отказа шаг 6-ж не
меняется — он и был замером «первого факта» своими силами, а роль вендора названа снятой здесь;
`06_DECISIONS_LOG.md:288,316,386,456,495` — **остаются**: тексты принятых решений не переписываются,
отмена названа в этом решении; `07_ARCHIVE.md:105` — **остаётся**: архив дословен;
`reference/*` — **остаются**: датированные снимки.

**Последствия:**
- `06_INDEX.md` — строка `ADR-034` [сейчас].
- `07_STATE.md`, `07_GAPS.md`, `07_ARCHIVE.md` — `Q-15` и `T-0-12` закрываются отказом и переносятся
  дословно; очередь и таблица мандата пересобраны; формулировка принятого риска переписана на
  постоянную [сейчас, одним коммитом].
- `04_ROADMAP.md` — строка `T-0-12` заменяется пометкой об отказе [сейчас].
- `briefs/T-0-10.md` — источник версии билда переписан с письма на замер на сервере [сейчас].
- `00_CHARTER.md`, `05_CONVENTIONS.md`, `CLAUDE.md` — **без правок**: запрет `REVOKE` и красная
  линия решением усилены, а не изменены [без правок].
- `briefs/T-0-5.md` — **без правок**: шаг 6-ж остаётся как есть [без правок].

## ADR-035 · Инвариант проверки 3 переписан: исчезновение из ОБЪЕДИНЕНИЯ состояния и реестра, архив — по добавленным строкам

**Контекст:** четвёртый дефект хука был найден замером 2026-08-11 и сознательно НЕ починен: правка
хука есть назначение правила и требует решения, а не руки внутри сессии о другом предмете. Условие
действия было названо заранее — «следующая сессия, которой понадобится заменить строку вопроса,

НЕ ПРОШЛО: Q-15 пропал из 07_GAPS.md, но не добавлен в 07_ARCHIVE.md тем же коммитом

2. **Сторона архива бралась разницей множеств «до/после».** `Q-15` был перенесён в архив ЭТИМ
   коммитом дословно, но идентификатор уже встречался в архиве прозой от прошлой сессии, поэтому в
   множество «добавленных» попасть не мог никогда. Требование хука было для него неисполнимо в
   принципе — обойти его можно было только неправдой в тексте.

**Решение.** Проверка 3 переписана в причине, а не обойдена у потребителя (`00 §3-БИС`):
1. Множество «исчезнувших» считается по ОБЪЕДИНЕНИЮ `07_STATE.md` и `07_GAPS.md`. Идентификатор,
   ушедший из одного файла и живой в другом, закрытием не является.
2. Сторона архива берётся из строк, ДОБАВЛЕННЫХ в `07_ARCHIVE.md` этим коммитом (тот же разбор
   диффа, что у проверок 6 и 7), а не из разницы множеств. Прежнее упоминание в архиве больше не
   делает требование неисполнимым и одновременно не засчитывается за перенос.
3. Самотест дополнен тремя кейсами на РЕАЛЬНЫХ формах входа, включая обратный: `(e)` идентификатор
   ушёл из реестра, но жив в состоянии — проход; `(f)` закрытие при том, что архив упоминал
   идентификатор и раньше — проход; `(g)` идентификатор пропал из обоих файлов, архив тронут
   посторонним текстом и его не называет — ОТКАЗ. Без `(g)` правка читалась бы как ослабление.

**Что проверка ловит по-прежнему.** Строка закрыта и вычеркнута из состояния и реестра, а в архив
дословно не перенесена — коммит останавливается. Это её работа, и она не тронута: кейсы `(a)` и
`(g)` предъявляют оба отказа логом.

**Замер.** `tools/hooks/selftest.sh`: было 35 кейсов, стало 41, «провалено 0» в обеих локалях.
Дефект найден не синтетикой, а реальным входом — правилом `05 §I` о замере по настоящему
содержимому репозитория.

**Последствия:**
- `tools/hooks/pre-commit` — проверка 3 переписана, комментарий несёт оба дефекта поимённо [сейчас].
- `tools/hooks/selftest.sh` — три новых кейса, счётчик 41 [сейчас].
- `06_INDEX.md` — строка `ADR-035` [сейчас].
- `07_STATE.md` — строка о четвёртом дефекте переписана с «отложен» на «починен замером и
  решением» [сейчас].
- `05_CONVENTIONS.md`, `CLAUDE.md` — **без правок**: инвариант формулировался только в коде хука,
  в текстах правил его формы не было [без правок].

## ADR-036 · Логи шагов 6-е-БИС и 6-ж засчитаны; артефакт различается предметом, а не датой; вызов клиента БД обязан нести оба аргумента
**Дата:** 2026-08-11 · **Статус:** accepted
**Контекст:** исполнительская сессия предъявила два лога класса B по `T-0-5` (шаги 6-е-БИС и 6-ж) и
остановилась двумя вопросами: команды брифа падали и были исправлены владельцем на сервере вручную;
писать результат некуда — единственное имя артефакта, названное брифом, уже занято артефактом
снятого шага 6-е, который переписывать запрещено. Остановка правильная: оба вопроса о правилах, а
правила исполнитель не назначает.

**Проверено по файлам, а не по пересказу.** Дефекты вызова подтверждены чтением брифа:
`briefs/T-0-5.md` в блоке шага 6-е-БИС передавал в `-i` строку подключения к базе, а сам файл
запроса `$q` не подавал вовсе; в блоке шага 6-ж строки подключения не было ни в каком виде. Оба
блока писала не рука исполнителя: первый — эта же архитекторская сессия (`ADR-033`), второй —
сессия `ADR-032`. **Тот же дефект уже сжёг первый прогон шага 6-е** и записан в артефакте
2026-08-11 дословно. Три повторения одного дефекта — довод за правило, а не за аккуратность.

**Решение.**
1. **Оба лога ЗАСЧИТАНЫ.** Правка была ремонтом ВЫЗОВА, а не проверяемого утверждения: SQL, учётная
   запись, режим транзакции и предикаты не менялись. У обоих шагов сработал встроенный контроль
   исправности — в 6-е-БИС признак режима различается между прогонами (`0` против `1`) при разных
   номерах транзакций, в 6-ж контрольная буква привилегии дала ровно `107`, число из прошлого
   замера. Проба различила исходы — правило `05 §I` соблюдено.
2. **Факт, который сняли эти логи, назван прямо:** `SET TRANSACTION READ ONLY` на базе клиента
   режим переключает — движок объявляет транзакцию только на чтение. Третье объяснение тишины
   старого шага 6-е (режим не вступил в силу) СНЯТО. Остались два, и различает их `T-0-17`: отказ
   на уровне оператора (контроля нет) против отказа на уровне записи (контроль есть, проба была
   неразличающей).
3. **Артефакт этих шагов получает СВОЁ имя** — `reference/T-0-5_readonly_mode_measurement_<дата>.md`,
   внесено в набор «Файлы на запись» брифа. Файл `..._readonly_tx_measurement_2026-08-11.md`
   принадлежит снятому шагу 6-е и не переписывается.
4. **Правило именования: дата артефакт НЕ уникализирует.** Имя различается ПРЕДМЕТОМ замера; два
   замера одного дня по одной задаче обязаны получить разные имена, и это обязанность того, кто
   пишет бриф, а не того, кто его исполняет. Правило вносится в `05 §II`.
5. **Правило вызова: команда к клиенту БД обязана нести И файл запроса, И строку подключения.**
   Канонический порядок для `isql`: `-i <файл запроса> -o <файл результата> "<строка подключения>"`
   последним позиционным аргументом. Правило вносится в `08_TASK_BRIEF_TEMPLATE` — в раздел, который
   уже требует писать команды под оболочку Windows.
6. **Отклонение вызова записывается, а не заминается.** В артефакт идут обе формы команды — как
   была в брифе и как исполнена, — и одна строка о том, что изменилось. Изменился SQL или учётная
   запись — это другой замер, и лог не засчитывается. Внесено в бриф `T-0-5`.
7. **Снятая команда шага 6-е из брифа не удаляется**, но получает метку «не запускается» и служит
   образцом дефекта: она и есть тот вызов без строки подключения.

**Что решение НЕ меняет.** Статус `T-0-5` ставит исполнительская сессия по своему session-блоку,
когда артефакт лежит в репозитории; класс мандата задачи остаётся **B**. Переезд чтения в класс A
не наступает: из трёх фактов `ADR-033` предъявлен второй (`MON$`-строка), первый ждёт `T-0-17`,
третий — единственной точки доступа, которой ещё нет.

**Основание.**
1. **Гэп наблюдения отличается от ремонта инструмента.** Первый прогон 6-е был отвергнут ровно за
   то, что команда не дошла до сервера. Здесь команда доведена до сервера, и проверяемое утверждение
   не тронуто — отвергать нечего, иначе правило превратится в запрет чинить опечатки.
2. **Правило вместо аккуратности.** Дефект повторился трижды в одной задаче и пережил две
   архитекторские сессии. Значит он структурный: команда пишется в брифе и проверяется глазами того,
   кто её не запускает.
3. **Имя, зависящее только от даты, ломается на втором замере в тот же день** — что и случилось.

**Последствия:**
- `briefs/T-0-5.md` — оба вызова починены, добавлено имя артефакта в набор «Файлы на запись»,
  добавлены правила об отклонении вызова, снятая команда 6-е помечена [сейчас].
- `06_INDEX.md` — строка `ADR-036` [сейчас].
- `07_STATE.md` — строка о снятом третьем объяснении и о засчитанных логах [сейчас].
- `05_CONVENTIONS.md` §II «Нейминг» — правило об уникальности артефакта по предмету
  [отдельным коммитом].
- `08_TASK_BRIEF_TEMPLATE.md` — канонический вызов клиента БД [отдельным коммитом].
- `reference/T-0-5_readonly_tx_measurement_2026-08-11.md` — **без правок**: артефакт снятого шага
  [без правок].
- Артефакт `reference/T-0-5_readonly_mode_measurement_2026-08-11.md` — пишет исполнительская
  сессия своим session-блоком [задачей `T-0-5`].

## ADR-037 · `Q-17` закрыта замером: отказ по режиму транзакции приходит на уровне ЗАПИСИ; эшелон в движке подтверждён, переезд чтения в класс A НЕ наступает
**Дата:** 2026-08-12 · **Статус:** accepted
**Контекст:** `ADR-033` снял вердикт «компенсирующий контроль опровергнут» и назвал три живых
объяснения тишины шага 6-е задачи `T-0-5`. Третье (режим не вступил в силу) снято логом шага 6-е-БИС
(`ADR-036`). Оставшуюся пару — отказ на уровне оператора против отказа на уровне изменяемой записи —
на базе клиента различить нельзя структурно: различающая проба и есть запись в чужой прод (`00 §4`).
Проверка уехала туда, где исполнима, — на наш экземпляр. Задача `T-0-17` исполнена 2026-08-12,
класс A, коммит `c91f875`; артефакт — `reference/T-0-17_readonly_engine_measurement_2026-08-12.md`.

**Приёмка брифа проверена по логам, а не по вердикту исполнителя.** Каждый критерий
`briefs/T-0-17.md` сверен с артефактом:

1. **Версия.** Напечатано `ISQL Version: LI-V2.5.9.27139 Firebird 2.5`, содержит `2.5.9`.
   Расхождение названо ниже отдельным пунктом.
2. **Положительный контроль (шаг 6).** Оба предиката в ОБЫЧНОЙ транзакции прошли без отказа,
   `CNT_AFTER_RW = 1` — число строк не изменилось. Проба исправна, оба предиката исполнимы,
   второй доходит до записи.
3. **Разные прогоны с чистыми файлами результата (шаги 7 и 8).** Предъявлены отдельно, каждый с
   явным `rm -f` файла результата — ровно та защита, отсутствие которой испортило вторую попытку
   шага 6-е задачи `T-0-5`.
4. **Проба различает исходы — правило `05 §I` соблюдено, и это главное.** Шаг 7 (предикат
   `WHERE 1 = 0`): `RO_FLAG = 1` из `MON$TRANSACTIONS` — положительный факт, что транзакция
   действительно только на чтение, — и тишина после `UPDATE`. Шаг 8 (предикат `WHERE ID = 1`):
   дословно
   ```
   Statement failed, SQLSTATE = 42000
   attempted update during read-only transaction
   ```
   и `CNT_AFTER_RO = 1` — строка не задета, отказ случился раньше записи. Выводы двух проб
   наблюдаемо РАЗНЫЕ, чего и не хватало логу шага 6-е.
5. **Отказ именно по режиму транзакции, а не посторонний сбой.** Текст отказа называет режим
   дословно (`during read-only transaction`) — требование правила «неуспех инструмента — тоже не
   факт» выполнено. Транзакция шага 8 самозаверена этим же текстом: движок печатает не «нет прав»,
   а «изменение в транзакции только на чтение».
6. **Ни один критерий не закрыт кодом возврата.** Коды (`0` в шаге 7, `1` в шаге 8) в артефакте
   есть, но вердикт стоит на строке отказа и на `RO_FLAG`.

**Два расхождения приёмки названы поимённо; оба — дефекты формы, вердикта не касаются.**

1. **Предъявлена версия КЛИЕНТА, а не сервера.** Роудмап и бриф требуют «версия сервера, на котором
   мерили». Команда, которой бриф это закрывает (`isql -z -quiet -i /dev/null`, без подключения),
   строку сервера напечатать не может в принципе — она печатает версию утилиты. Дефект брифа, а не
   исполнения: исполнитель выполнил предписанную команду дословно. Критерий засчитывается, потому
   что `isql` взят из той же инсталляции `/usr/local/firebird/bin` того же образа с тегом `2.5.9-sc`,
   и он же исполнял все пробы; остаточная неопределённость (номер сборки серверного бинарника
   отдельной строкой не предъявлен) названа здесь и стоит одной команды — `isql -z` ПОСЛЕ `CONNECT`.
   Пересматривать закрытие она не требует: вопрос `Q-17` о поведении движка, а не о номере сборки.
2. **Тишина шага 7 зафиксирована прозой, а не дословным блоком всего стандартного вывода.** В шаге 8
   строка отказа процитирована со стандартного вывода, файл результата её не содержит; значит для
   шага 7 чистый файл результата сам по себе тишины на стандартном выводе не доказывает. Артефакт
   утверждает её словами («ни строки `Statement failed`, ни любого другого текста отказа») и
   подкрепляет кодом возврата `0`, откалиброванным в этой же сессии кодом `1` шага 8. Засчитано,
   потому что вердикт опирается на ПОЛОЖИТЕЛЬНЫЙ факт шага 8, а шаг 7 несёт собственный
   положительный контроль `RO_FLAG = 1`; форма фиксации отрицательного случая названа как долг
   формы, а не как недостающий факт.

**Решение.**
1. **Логи засчитаны, приёмка `T-0-17` закрыта, задача `done`.** Артефакт переписыванию не подлежит
   (`ADR-024`).
2. **Вердикт принят: Firebird 2.5.9 отбивает изменение в транзакции только на чтение на уровне
   ИЗМЕНЯЕМОЙ ЗАПИСИ, не на уровне оператора.** Сработал второй триггер пересмотра `ADR-033`;
   первый (отказ на уровне оператора) объявляется НЕсработавшим.
3. **`Q-17` закрывается фактом** и переносится в `07_ARCHIVE.md` дословно вместе с гейтом.
4. **Слой 2 (`ADR-033`) подтверждён замером и получает НАЗВАННУЮ границу.** Транзакция только на
   чтение перестаёт быть «эшелоном до замера» и называется механизмом, отбивающим запись на стороне
   сервера, — но ровно там, где оператор задевает запись. Оператор, не задевающий ни одной строки,
   проходит молча, и это не дыра, а форма отказа: записи не произошло ни в одном из двух случаев.
5. **Следствие для будущих проверок, обязательное к применению:** тишина на пробе с нулевым
   предикатом в транзакции только на чтение больше не читается НИ как «контроля нет», НИ как
   «контроль есть» — теперь измерено, что такая проба не наблюдение вовсе. Проба, которой мерят
   режим транзакции, обязана задевать запись; там, где задевать запись запрещено, режим
   подтверждается `MON$`-строкой, а не поведением `UPDATE`.
6. **Переезд чтения БД в класс A НЕ наступает.** Условие `ADR-033` требует ТРЁХ фактов разом.
   Предъявлены два: (а) замер `T-0-17` на нашем экземпляре — этим решением; (б) `MON$`-строка о
   режиме транзакции с базы клиента — шагом 6-е-БИС (`ADR-036`). Не предъявлен (в): обращение через
   единственную точку доступа с белым списком операторов — её не существует. **Обращения к БД
   PawnShop остаются классом B целиком**, и это не формальность: именно (в) — единственный
   постоянный слой после `ADR-034`, а два предъявленных факта описывают чужой движок, поведение
   которого мы не контролируем.
7. **Задача на недостающий факт (в) этим решением НЕ заводится, и автоматической генерации задач по
   оставшимся фактам НЕТ.** Условие переезда — не список задач и не план работ. Единственная точка
   доступа с белым списком операторов есть проектная работа в производителе данных, у неё своя
   зависимость (канал прод-подключения, `T-0-8`) и своё место в очереди, которое назначает владелец;
   заводить её решением о замере значило бы назначить приоритет мимо владельца. Новый вопрос в
   реестр по этому поводу тоже не заводится: гейт уже назван внутри условия переезда, а строка
   реестра, дублирующая условие решения, — вторая копия, которая однажды разойдётся.
8. **Правило для брифов (наследует `ADR-036`): критерий приёмки и команда, которой он закрывается,
   обязаны совпадать по ПРЕДМЕТУ.** Критерий требовал версию сервера, предписанная команда печатает
   версию клиента — дефект пишущего бриф, обнаруживаемый только глазами того, кто команду не
   запускает. Вносится в `08_TASK_BRIEF_TEMPLATE` рядом с каноническим вызовом клиента БД.

**Основание — от фактов репозитория.**
1. **Различающая проба состоялась.** `05 §I` требует, чтобы контроль наблюдаемо отличался от
   измеряемого случая. Здесь отличие предъявлено дважды: положительный контроль в обычной транзакции
   (тишина по обоим предикатам) против измеряемого в режиме только на чтение (тишина по нулевому,
   отказ по задевающему строку). Ровно эта конструкция и была невозможна на базе клиента.
2. **Объяснение 2 из `ADR-033` подтверждено, а не выбрано как правдоподобное.** Тишина старого шага
   6-е объясняется формой пробы: при отказе на уровне записи предикат `WHERE 1 = 0` до отказа не
   доходит никогда. Это не примирение половин, а измеренная причина.
3. **Мандат не двигается по частичному основанию.** `ADR-033` записал условие как конъюнкцию
   намеренно; засчитывать переезд по двум фактам из трёх значит переписать условие тем же действием,
   которым его применяешь.
4. **Красная линия соблюдена буквально.** Ни одной команды к контуру клиента: площадка — контейнер

## ADR-038 · Единственная точка доступа заводится ПОСЛЕ выбора канала прод-подключения; до тех пор мандат чтения БД не двигается
**Дата:** 2026-08-12 · **Статус:** accepted
**Контекст:** `ADR-037` закрыл `Q-17` замером и намеренно НЕ завёл задачу на третий недостающий факт
условия переезда (`ADR-033`) — единственную точку доступа к базе с белым списком операторов, — оставив
момент её появления владельцу. Развилка предъявлена владельцу двумя вариантами: завести следующей
задачей либо после выбора канала прод-подключения (`T-0-8`, вопрос `Q-3`).

**Решение владельца 2026-08-12: вариант Б — после выбора канала.** Работа в очередь сейчас не
заводится, строки задачи не создаётся.

**Основание.**
1. **Канал не выбран, а точка доступа живёт внутри него.** Белый список операторов реализуется в
   производителе данных — коннекторе; при туннеле из облака и при агенте на сервере это разный код и
   разное место теста. Заведённая до выбора, она была бы переписана после.
2. **Выигрыш от раннего завода почти нулевой.** Единственная задача в очереди (`T-0-3b`) остаётся
   классом B по другой причине — она сама и есть обращение к базе клиента за фактами. Даже мгновенно
   готовая точка доступа подтверждений с неё не сняла бы: условие `ADR-033` требует трёх фактов,
   а её появление лишь закрывает третий и переводит в класс A ровно ЧТЕНИЕ, а не задачу целиком.
3. **Отказ от завода — не отказ от работы.** Триггер назван ниже, поэтому развилка не может
   раствориться молча; именно этого требует правило петли реестра вопросов.

**Триггер.** Канал прод-подключения выбран решением (`T-0-8`, вопрос `Q-3` закрыт) → единственная
точка доступа с белым списком операторов заводится задачей в том же канале, и её появление
предъявляется тестом. Отдельная строка вопроса под это не заводится: гейт уже стоит внутри условия
переезда, а вторая копия условия однажды разойдётся с первой.

**Что решение НЕ меняет.**
- Условие переезда чтения в класс A (`ADR-033`, три факта разом) — дословно.
- Обращения к БД PawnShop остаются классом B целиком до предъявления третьего факта.
- Принятый постоянный риск (`ADR-034`) и красная линия `00 §4` — без изменений.

**Публикация наружу.** Тем же словом владельца разрешена публикация накопленных коммитов
(`git push`, класс B). Разрешение разовое и на следующую партию коммитов не распространяется.

**Последствия:**
- `06_INDEX.md` — строка `ADR-038` [сейчас].
- `07_STATE.md` — развилка снята со стенд-апа, условие завода записано в подробности [сейчас].
- `04_ROADMAP.md` — **без правок**: строка задачи не заводится, работа живёт условием, а не
  строкой [без правок].
- `07_GAPS.md` — **без правок**: новый вопрос не заводится, гейт стоит в условии переезда
  [без правок].
- `05_CONVENTIONS.md`, `CLAUDE.md`, `08_TASK_BRIEF_TEMPLATE.md` — **без правок**: класс мандата
  решением не двигается [без правок].

## ADR-039 · Оракул `T-0-3b` исполняется без приватного сателлита: первоисточник не коммитится никуда, в репозиторий идёт обезличенная сверка; разрез санитарии по именам полей назван
**Дата:** 2026-08-12 · **Статус:** accepted
**Контекст:** бриф `T-0-3b` упирается в три места, где действующие решения не сходятся друг с другом
или молчат, и каждое из них исполнитель встретил бы как стоп-условие.

1. **`ADR-024` требует, чтобы снимок-первоисточник эталона уезжал в приватный репозиторий-сателлит
   `lombard-ops-vendor-schema`, путь `oracle-snapshots/`.** Сателлита НЕ существует: его создаёт
   `T-0-10`, которая не исполнена. Между тем `ADR-010 v3` требует оракул UI на всех шести договорах
   с хранением именно в `T-0-3b`. Буквальное чтение обоих решений даёт неисполнимую задачу.
2. **Санитария имён полей вендора прочитывается в две стороны.** `ADR-009` запрещает дампы схемы в
   публичном репозитории, но прямо разрешает «маппинг используемых полей (документация `02 §3`)».
   Исполнитель, читающий только красную линию, остановится на первой же колонке; исполнитель,
   читающий только `02 §3`, выложит инвентарь схемы. Разрез не назван нигде явно.
3. **`connector/mapping.json` отсутствует, а `02 §3` пуст.** `T-0-3b` добывает ровно те поля,
   которых там не хватает, и соблазн создать файл возникнет сам собой — при том что его формат и
   эталон отпечатка принадлежат `T-0-10` (`ADR-016`).

**Решение.**
1. **Первоисточник оракула в этой задаче не коммитится НИКУДА.** Снимки экрана приложения вендора
   делает и хранит Ilyas у себя, вне обоих репозиториев. Перенос их в `oracle-snapshots/` остаётся
   последствием `ADR-024`, приходящим задачей `T-0-10`, и записывается как названная задолженность,
   а не как невыполненное требование. Очередь из-за сателлита не переставляется: `T-0-3b` идёт
   первой, как назначил владелец.
2. **В публичный репозиторий идёт только обезличенная сверка** (`ADR-024` дословно): дата снимка,
   предмет, наша величина, эталонная величина, расхождение, вывод. **Договоры нумеруются порядково
   внутри артефакта** («договор 1»…«договор 6»); соответствие порядкового номера реальному в
   репозиторий не попадает ни в каком виде и живёт у Ilyas вместе со снимками. Номеров договоров и
   имён клиентов в публичном репозитории нет.
3. **Расхождение с эталоном закрывается правилом или решением, а НЕ подгонкой нашей формулы**
   (`00 §3-БИС(b)`). Сошёлся оракул — формула записывается в `03 §4`; не сошёлся — формула НЕ
   записывается, расхождение предъявляется поимённо по каждому договору, задача закрывается этим
   фактом, а не «уточнённым коэффициентом». Подгонка под цифру экрана есть тихое примирение
   половин и прямо запрещена.
4. **Разрез санитарии назван прямо и обязателен к цитированию в брифе.** В публичный репозиторий
   МОЖНО и НУЖНО: имена таблиц и колонок, которые мы реально используем, их типы и смысл — это и
   есть `02 §3`, прямо разрешённый `ADR-009`. НЕЛЬЗЯ: полный или частичный инвентарь схемы,
   перечни неиспользуемых объектов, значения строк с данными клиентов, номера договоров, имена
   людей. Правило разреза: **в репозиторий попадает то, что мы используем, а не то, что мы
   увидели.**
5. **`connector/mapping.json` этой задачей НЕ создаётся** — файл, его формат и эталон отпечатка
   принадлежат `T-0-10` (`ADR-016`). `T-0-3b` заполняет документацию `02 §3`; расхождение между ней
   и будущим файлом снимается при исполнении `T-0-10`, а не заранее.
6. **`03 §4` правится этой задачей по мандату `ADR-010 v3`** («формула определяется в `T-0-3b`»),
   через session-блок с пометкой, как и требует дисциплина документации для SEMI-STABLE. Правка
   применяется ТОЛЬКО при сошедшемся оракуле — см. пункт 3.

**Основание.**
1. **Неисполнимое требование — дефект плана, а не работа исполнителя.** Ровно так уже было с
   условием переезда мандата (`ADR-033`): требование, которое честно выполнить нельзя, снимается
   решением, а не обходится молча на месте.
2. **Правило `ADR-024` этим не ослабляется, а исполняется в той части, которая исполнима.** Оно
   защищает от двух вещей: недатированного эталона и персональных данных в публичном репозитории.
   Обе защиты сохранены целиком; в сателлит не уезжает только то, чему пока некуда уезжать.
3. **Разрез санитарии выводится из существующего решения, а не изобретается.** `ADR-009` уже
   провёл границу между дампом и производным маппингом used-полей; здесь она лишь названа словами,
   которые исполнитель применит без второго толкования.

**Что решение НЕ меняет.**
- Красная линия `00 §4`: к базе только чтение. Класс `T-0-3b` — **B**, целиком.
- `ADR-024` в части датирования эталона и запрета персональных данных — дословно.
- `ADR-016`: сателлит и `mapping.json` остаются за `T-0-10`.

**Триггер снятия задолженности.** `T-0-10` создаёт сателлит → снимки оракула `T-0-3b` уезжают в
`oracle-snapshots/` с указанием, чей экран и когда снят; обезличенная сверка в `/reference`
остаётся на месте и не переписывается.

**Последствия:**
