### Сетевой канал GCP ↔ контур клиента: АГЕНТ НА СЕРВЕРЕ (`T-0-8`)
Выбор сделан решением владельца 2026-08-12 (`ADR-046`, вариант Б `01 §4`): служба с только исходящим
трафиком кладёт выгрузку в GCS. Первая грабля названа заранее и проверена шагом 1 `T-0-8`: исходящий
HTTPS к `storage.googleapis.com` из сети клиента может быть закрыт прокси или фильтром, а на старой
Windows Server может не хватать доверенных корневых сертификатов. **Связность подтверждена 2026-08-12
(`ADR-048`):** прокси не задан, `hosts` пуст, доверенных корней 42, оба эндпоинта (`storage`, `oauth2`)
отвечают под штатным валидатором. Проверялась не самодельным сравнением `Subject`, а списком
`subjectAltName` и штатным HTTP-запросом под неподменённым валидатором сертификата (`scripts/probe_oauth.ps1`)
— первый вердикт «не пройдено» был ложноотрицательным именно из-за самодельного сравнения строк
(`ADR-048`, правило наблюдения того же имени). **`secretmanager.googleapis.com` — не измерен**, закрывается
тем же скриптом с заменой `$h`/`$path` (см. ниже), класс B, отдельная карточка, до шага 5.

**Единственная точка доступа с белым списком операторов — `connector/agent/access_point.py`.**
Разбирает оператор через `sqlparse` (`Statement.get_type()`), а не текстовым поиском (`ADR-048`):
пропускает только `SELECT`/`WITH … SELECT` по девяти разрешённым таблицам (`briefs/T-0-5.md`) плюс
`RDB$*`/`MON$*`; `SELECT *` отбивается разбором дерева токенов (агрегатные `COUNT(*)` не считаются
списком колонок и не отбиваются). Каждый вызов открывает СВОЮ транзакцию только на чтение через
`fdb.TPB()` (`access_mode = fdb.isc_tpb_read`) и подтверждает режим положительным фактом —
запросом к `MON$TRANSACTIONS` (`ADR-037`), а не отсутствием ошибки. Лог запроса печатается ДО
отправки. Тест — `connector/agent/test_access_point.py`, к базе не подключается (подключение
подменяется), обе стороны каждой проверки. Замер обоих файлов — `reference/T-0-8_access_point_and_agent_2026-08-12.md`.

**Guard схемы (`ADR-004`) — `connector/agent/schema_guard.py`.** Перед чтением каждой из девяти
таблиц отпечаток метаданных (`RDB$RELATION_FIELDS`/`RDB$FIELDS`) сверяется с эталоном в
`connector/agent/schema_fingerprint.json` (временное место эталона, пока `connector/mapping.json` не
заведён `T-0-10` — при появлении маппинга источник эталона переключается решением, не молча).
**Первый прогон на новой машине создаёт эталон и печатает его — сверка включается со второго.**
Расхождение → стоп для ВСЕХ девяти таблиц разом, не только для изменившейся (`00 §3-БИС(c)`: не
смягчать до предупреждения). Список колонок для `SELECT` строится из самого отпечатка — имена
колонок не хардкожены в коде агента, они измерены тем же запросом.

**Поведение при недоступности GCS — `connector/agent/gcs_upload.py`.** До 5 попыток с
экспоненциальной задержкой (`2s, 4s, 8s, 16s`); все провалились → объект пишется побайтово в
локальный журнал (`connector/agent/upload_journal/` на сервере агента) и функция бросает
`UploadFailedPersisted` — вызывающий код узнаёт об отказе явно. `replay_journal()` доисполняет
хвост при восстановлении связи, файл журнала удаляется только при успешной повторной загрузке
(не-идемпотентные операции, `05 §I`).

**Ключ сервисного аккаунта СОЗДАТЬ НЕЛЬЗЯ — запрет политикой организации клиента (замер
2026-08-13, `ADR-049`).** Рецепт для будущих сессий, чтобы отказ не читался как своя ошибка:

- симптом: `gcloud iam service-accounts keys create` → `FAILED_PRECONDITION: Key creation is not
  allowed on this service account`, в тексте назван `constraints/iam.disableServiceAccountKeyCreation`;
- диагностика ровно тремя командами, все read-only:
  `gcloud org-policies describe iam.disableServiceAccountKeyCreation --project=$PROJECT_ID` (без
  `--effective` даёт `NOT_FOUND` — явной политики на проекте нет) и та же команда с `--effective`
  (даёт `enforce: true` — ограничение приходит сверху); `gcloud projects describe $PROJECT_ID
  --format="yaml(projectId,parent,lifecycleState)"` печатает родителя-организацию;
- **`--effective` НЕ различает унаследованную политику и платформенный дефолт** — различить может
  только тот, кто видит организацию; `gcloud organizations list` под нашей учётной записью даёт
  `Listed 0 items`;
- **роль `owner` на проекте здесь не помогает и помогать не должна:** право проверяется на том
  ресурсе, где исполняется операция, а политика организации живёт выше проекта;
- обходов нет. Ключ в другом проекте нарушает `00 §4`, пользовательские креды на сервере клиента
  кладут туда учётку с `owner`, самодельная выдача подписанных URL запрещена `ADR-048`.

**Что вместо ключа: федерация удостоверений через самоподписанный OIDC (`ADR-050`).** Рецепт
записан ДО исполнения намеренно — он снимает два ложных хода, каждый из которых стоил бы сессии:

- **Публично читаемый issuer-URL НЕ обязателен, и публичный бакет заводить не нужно.** Открытые
  ключи передаются провайдеру напрямую: `gcloud iam workload-identity-pools providers create-oidc`
  несёт флаг `--jwk-json-path`; тот же флаг есть у `update-oidc`, поэтому и ротация идёт без
  внешнего URL. Документация платформы называет загрузку ключей штатным способом для случая
  «эндпоинт метаданных IdP не доступен публично»; потолок — 8 ключей. Замер справки —
  `reference/T-0-8_jwks_delivery_measurement_2026-08-13.md`.
- **`--issuer-uri` остаётся обязательным флагом при любом способе доставки ключей** — он задаёт
  значение, с которым сверяется claim `iss` токена. Достижимости при загруженных ключах
  документация не требует, но это чтение, а не замер: различающая проверка одна — фактическое
  создание провайдера.
- **Файл конфигурации учётных данных не пишется руками:** его генерирует
  `gcloud iam workload-identity-pools create-cred-config` (`--credential-source-file`,
  `--service-account`) — штатный механизм платформы бьёт самодельный (`ADR-048`).
- **Проверять ДО создания, одной read-only командой:**
  `gcloud org-policies describe constraints/iam.allowedPolicyMemberDomains --project=$PROJECT_ID
  --effective`. Ограничение доменов в IAM-политиках способно отбить выдачу роли
  `roles/iam.workloadIdentityUser` внешнему principal — тот же класс неизмеренного ограничения,
  который снял шаг 5. Дешевле измерить, чем узнать посреди создания.
- **Часы сервера — часть механизма, а не гигиена.** STS проверяет `iat`/`exp`; на сервере ERP
  служба времени Windows не запущена (`w32tm /query /status` → `0x80070426`, замер 2026-08-13).
  Включать до первого обмена токена, иначе отказ будет выглядеть как отказ федерации.
- **Закрытый ключ подписи в Secret Manager не кладётся:** чтобы прочитать секрет, нужны учётные
  данные, а их даёт этот же ключ — зависимость круговая. Место — файл на сервере с правами на
  учётную запись службы агента.

**Кодировка подключения Firebird и разрядность клиентской библиотеки — измерены шагом 7 `T-0-8`,
2026-08-17.** Три находки, годные для любой будущей задачи, работающей с этой базой с этого сервера:

- **`LOMBARD_DB_CHARSET = WIN1251`.** Не названо ни в конфигурации PawnShop (`pawn.ini` — проверено,
  кодировки там нет), ни в документации — измерено пробными подключениями через уже существующую
  `access_point.py` на таблице `CUSTOM_FIELDS_VALUES` (реальные значения персонала, а не служебные
  латинские коды). Различающий признак: кандидат `NONE` даёт мусор двойного перекодирования (сырые
  UTF-8-байты, прочитанные как cp1251); `WIN1251`, `UTF8`, `DOS866` дают идентичный читаемый текст на
  этом наборе строк — совпадение трёх не объяснено окончательно, `WIN1251` выбран как конвенциональная
  кодировка Firebird-приложений СНГ.
- **Разрядность клиентской библиотеки Firebird обязана совпадать с разрядностью процесса, который её
  грузит через `ctypes`/`fdb`, но НЕ обязана совпадать с разрядностью серверной части.** На этом
  сервере серверный Firebird 32-битный (`Program Files (x86)`), а Python-агент 64-битный — попытка
  подключения падает `[WinError 193] %1 не является приложением Win32`, что выглядит как ошибка
  подключения, но является ошибкой загрузки DLL. Решение — не менять разрядность агента, а найти
  64-битную `fbclient.dll` ОТДЕЛЬНО: официальный ZIP-кит GitHub releases `FirebirdSQL/firebird`
  (тег `R2_5_9`) несёт готовую 64-битную версию, отдельного client-only дистрибутива у проекта нет.
  Путь на сервере — `C:\LombardAgent\firebird-client64\fbclient.dll`, добавлен в `$env:Path` первой
  строкой `run_daily_wrapper.ps1`.
- **Тупиковый путь, не тратить время повторно:** параллельная установка 32-битного Python вместо
  поиска 64-битной DLL упирается в отсутствие готового `wheel` `cryptography` под Python 3.14/win32
  на PyPI (сборка из исходников требует MSVC-линкера, которого на сервере нет). Версия `48.0.1`
  публикует 32-битный `wheel` (`cp311-abi3-win32`), но это не понадобилось — путь через 64-битную
  `fbclient.dll` проще и не добавляет второй интерпретатор в контур клиента.

Артефакт — `reference/T-0-8_step7_charset_measurement_2026-08-17.md`.

**Грабля наследования прав на файлы учётных данных, вскрытая прогоном отрицательных случаев.**
`icacls` на `C:\LombardAgent\keys` ограничивает ТОЧЕЧНО, с разрывом наследования, только два файла —
`private_key.pem` и `credentials.json`; сам каталог `keys` наследование не разрывает, поэтому

TTL. Мера (разрыв наследования на `signed_jwt.txt`, права только системе и служебной учётке) не

### RDP / PowerShell на ERP-сервере — практика
- Вставка в PowerShell: правый клик. Копирование: выделить → Enter.
- Вывод возвращать целиком, включая echo команды (untrusted-правило `05`).
- Ничего не устанавливать и не менять на сервере вне явного брифа; сервер — прод клиента.
- **Доставка скрипта из репозитория на сервер.** Файлы репозитория живут на машине Ilyas, не на
  сервере; сеть между ними — только RDP. Порядок для ASCII-скриптов без нестандартного содержимого:
  открыть файл у себя → скопировать текст целиком → на сервере `notepad C:\Temp\probe.ps1` → правый
  клик (вставка) → сохранить → запустить `powershell -ExecutionPolicy Bypass -File C:\Temp\probe.ps1`.
  Вставлять многострочный текст прямо в консоль PowerShell не надо: пустые строки внутри `try`/`catch`
  консоль разрывает на отдельные команды и скрипт исполняется не целиком. Скрипт после прогона
  удаляется, если бриф не сказал иное.
- **Любой файл с НЕ-ASCII содержимым или заметным объёмом — только через base64 + `certutil -decode`,
  со сверкой SHA-256 (правило обобщено по итогам шагов 6 и 7 `T-0-8`).** RDP-буфер обмена ненадёжен
  для двух разных классов данных, и оба подтверждены измерением: (а) объёмная бинарная передача
  (ZIP-код агента, шаг 6) — первая попытка одним куском дала расхождение SHA-256, исправлено
  разбиением на части; (б) НЕБОЛЬШОЙ текстовый файл с кириллицей (`charset_probe.py`, шаг 7) —
  копирование через Notepad ТИХО перекодировало файл на диске сервера из UTF-8 в Windows-1251 (байты
  кириллицы и длинного тире остались ВАЛИДНЫМ cp1251-текстом, не мусором, поэтому визуальная проверка
  на сервере ничего не показывает — только `SyntaxError` при запуске или HEX-дамп байт). Причина
  подмены не установлена измерением ни в одном случае — годится подозрение «RDP-буфер», не факт.
  **Правило, а не диагноз:** для файла с не-ASCII символами — либо переписать файл на чистый ASCII
  (транслит в служебных строках, если кириллица не критична для смысла), либо доставлять
  base64+`certutil` независимо от объёма. Notepad-вставка годится только для гарантированно
  ASCII-содержимого.
