## Роль

Ты — исполнитель проекта. Законы — `CLAUDE.md`, стандарты — `05_CONVENTIONS.md` Части I и II.
Модель исполнения: ты исполняешь сам в пределах мандата класса A (подготовка команд, чтение
метаданных, сборка артефакта, локальный коммит). Всё из перечня класса B (запись боевых значений
секретов; чтение значения токена; отправка сообщения в боевой чат) — только отдельным действием
после явного подтверждения Ilyas, никогда в связке с диагностикой. Перед каждым запросом
подтверждения — ОТДЕЛЬНОЕ сообщение: что именно исполняется, на каком объекте, чем откатывается.
`Done` — только по предъявленному логу, не по коду возврата.

**Красная линия этой задачи, отдельная от общих (`00 §4`, `05 §I` untrusted-вывод):** значение
токена бота никогда не печатается, не логируется и не вводится через диалог с Claude — по тому же
принципу, что пароль `LOMBARD_RO` в шаге 5-В `T-0-8` (`07_STATE.md`, «Шаг 5-В `T-0-8` ЗАКРЫТ»):
владелец вводит секретные значения сам, в своём терминале (Cloud Shell под своей учётной записью
или локальный терминал с `gcloud` под ней же), Claude готовит для него точный текст команды и
получает обратно только НЕ секретные части вывода (версия секрета, `message_id`, счёт участников).

## Цель

После задачи: боевой бот Telegram существует, три боевых чата (владелец/Иса, менеджер/Бектур,
оценщик/Эльхан) заведены без сотрудников клиента внутри, идентификаторы чатов собраны, реальные
значения токена и идентификаторов чатов лежат новыми версиями в Secret Manager (`telegram-bot-token`,
`chat_id`), тестовое сообщение доставлено в боевой чат и предъявлено ответом API, а токен и
идентификаторы чатов зафиксированы не только у подрядчика, но и у владельца бизнеса (Иса) — снятие
bus factor подрядчика (`T-0-21`, требование R18). Второй вход сквозной нитки (`T-1-0`) готов:
появляется куда отправить сообщение.

## Ограничения

- К БД PawnShop задача не обращается вовсе.
- Секреты и endpoint'ы контура клиента в репозиторий не попадают (`ADR-001`) — здесь применимо
  буквально: значение токена бота в `/reference`, в лог сессии и в диалог с Claude не попадает
  никогда.
- Сотрудники клиента (Иса, Бектур, Эльхан) в боевые чаты НЕ добавляются этой сессией — условие
  `ADR-056`, снимающее необходимость подтверждения владельца на каждую отправку класса A. Добавление
  первого сотрудника — отдельное действие, вне этой задачи, и переводит будущую отправку в этот чат
  в класс B с обязательной записью в `11_INFRA_FACTS.md` тем же днём (не делать в этой сессии).
- Реализация обработчика бота (`cf-tg-handler`), боевая маршрутизация сообщений по ролям в
  `config.json` — вне scope (`T-0-9`, `T-1-4`).
- Один скрипт на ШАГ брифа, диагностику и класс-B действие в одном блоке не объединять.

## Шаги

1. **Владелец создаёт бота через @BotFather** (вне инструмента, в своём Telegram-клиенте). Executor
   не участвует в этом шаге и не видит токен на этом шаге. Результат, который владелец держит у
   себя: имя бота, `@username`, токен.

2. **Владелец создаёт три боевых группы в Telegram** — по одной на Ису (`owner`), Бектура
   (`manager`), Эльхана (`assessor`), называет их сам, добавляет туда только бота (администратором,
   право отправки сообщений), сотрудников клиента НЕ добавляет. Executor готовит для владельца
   точный способ снять `chat_id` каждой группы без ввода токена в сессию:
   ```
   # владелец выполняет сам, в СВОЁМ терминале, после отправки любого сообщения боту в каждой группе:
   curl -s "https://api.telegram.org/bot<TOKEN>/getUpdates" | python3 -m json.tool
   ```
   Ожидаемый результат у владельца: три числовых `chat_id` (отрицательные для групп), без пересылки
   вывода Claude — только сами три числа, они не секрет контура клиента (внутренние идентификаторы
   Telegram-групп, созданных этим проектом).

3. **КАРТОЧКА ПОДТВЕРЖДЕНИЯ 1 (класс B: запись секретов).** Отдельным сообщением назвать владельцу:
   что исполняется (запись реальных значений токена и трёх `chat_id` в Secret Manager новыми
   версиями), на каком объекте (`telegram-bot-token`, `chat_id`, проект
   `project-c451b48a-07ae-4de4-961`), чем откатывается (`gcloud secrets versions destroy` новой
   версии; предыдущая версия-плейсхолдер остаётся нетронутой). После подтверждения — передать
   владельцу точный текст команд ДЛЯ ЕГО СОБСТВЕННОГО терминала (значения он подставляет сам,
   Claude их не видит и не печатает):
   ```
   printf '%s' '<BOT_TOKEN>' | gcloud secrets versions add telegram-bot-token \
     --project=project-c451b48a-07ae-4de4-961 --data-file=-

   printf '%s' '{"owner": <CHAT_ID_ISA>, "manager": <CHAT_ID_BEKTUR>, "assessor": <CHAT_ID_ELHAN>}' \
     | gcloud secrets versions add chat_id \
     --project=project-c451b48a-07ae-4de4-961 --data-file=-
   ```
   Ключи JSON (`owner`/`manager`/`assessor`) — договорённость этой сессии, совпадающая с именами
   ролей `12_UX_CONTRACT.md`; записывается в артефакт и в `INFRA_PATCH`, не выдумывается заново
   будущими задачами.

4. **Проверка версий (executor исполняет сам — не читает значение, только метаданные):**
   ```bash
   gcloud secrets versions list telegram-bot-token --project=project-c451b48a-07ae-4de4-961
   gcloud secrets versions list chat_id --project=project-c451b48a-07ae-4de4-961
   gcloud secrets versions list firebird-readonly-creds --project=project-c451b48a-07ae-4de4-961
   ```
   Ожидаемый вывод: у `telegram-bot-token` и `chat_id` появилась версия `2` (`ENABLED`), у
   `firebird-readonly-creds` версия `2` уже существует (`T-0-8`, шаг 5-В) — печать всех трёх
   закрывает пункт приёмки «по каждому из трёх секретов» буквально.

5. **КАРТОЧКА ПОДТВЕРЖДЕНИЯ 2 (класс B: чтение значения токена + отправка сообщения в мессенджер).**
   Отдельным сообщением назвать: что исполняется (тестовая отправка одного сообщения в один боевой
   чат через Bot API), на каком объекте (боевой чат `owner`, сотрудников клиента в нём нет —
   класс A по составу чата, `ADR-056`; чтение значения токена остаётся отдельно классом B), чем
   откатывается (тестовое сообщение можно удалить вручную в Telegram; необратимого действия с
   данными нет). После подтверждения — владелец выполняет сам, в своём терминале:
   ```
   BOT_TOKEN=$(gcloud secrets versions access latest --secret=telegram-bot-token \
     --project=project-c451b48a-07ae-4de4-961)
   curl -s -X POST "https://api.telegram.org/bot${BOT_TOKEN}/sendMessage" \
     -d chat_id="<CHAT_ID_ISA>" \
     -d text="lombard-ops T-0-18: тестовое сообщение боевого контура (сотрудников клиента в чате нет)"
   ```
   Владелец возвращает в сессию ТОЛЬКО JSON-ответ API (в нём нет токена — токен идёт в URL, не в
   тело ответа): `message_id`, `date`, `chat.id`, `chat.type`.

6. **Состав каждого чата.** Владелец сверяет число участников каждого из трёх чатов (например,
   `getChatMemberCount` тем же способом, что в шаге 5, без повторного чтения токена в сессии, либо
   значением из интерфейса Telegram) и возвращает в сессию три числа со списком ролей участников без
   ФИО — «бот + владелец, сотрудников клиента 0» по каждому чату.

7. **Факт R18.** Владелец подтверждает текстом в сессии, что токен бота и три `chat_id` переданы и
   зафиксированы у Исы (способ передачи владелец называет сам — не команда, а факт). Без этого
   подтверждения пункт R18 приёмки не закрыт.

8. **Сборка артефакта** `reference/T-0-18_telegram_contour_setup_2026-08-18.md`: даты, номера версий
   секретов (без значений), схема JSON `chat_id` (ключи, без значений), результат шага 4 (три
   версии), результат шага 5 (`message_id`/`date`/`chat.id` без токена), результат шага 6 (три
   счётчика состава), факт R18 из шага 7 с указанием способа передачи, ссылка на `ADR-056` как
   основание класса отправки.

## Критерии приёмки

- `gcloud secrets versions list` печатает версию новее плейсхолдерной по каждому из трёх секретов —
  лог шага 4 приложен целиком.
- Тестовая отправка в боевой чат предъявлена ответом API с `message_id` — лог шага 5 (без токена)
  приложен.
- Состав каждого из трёх чатов напечатан числом участников, сотрудников клиента в нём нет — лог
  шага 6 приложен по каждому чату отдельно.
- Токен бота и идентификаторы чатов переданы владельцу бизнеса и зафиксированы у него — предъявлено
  явным текстовым подтверждением владельца (шаг 7), а не обещанием сделать это позже.
