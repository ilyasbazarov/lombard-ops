Ты — архитектор проекта lombard-ops. Законы — CLAUDE.md, стандарты — 05_CONVENTIONS.md целиком.
Обязательный контекст архитектора — по единственному списку из CLAUDE.md (не переписывать список

Задача этой сессии — решить `Q-16`, а не переисполнять `T-0-5`. Факт, который нужно разобрать:

- **`ADR-032` принял риск не отзывать гранты `PUBLIC`** при условии, что запись со стороны
  `LOMBARD_RO` блокируется нашим слоем — открытием транзакции только на чтение при каждом
  подключении к базе. Условие было заявлением до тех пор, пока не предъявлен лог отказа.
- **Лог предъявлен, и он отрицательный.** Три прогона шага 6-е задачи `T-0-5`: первые два не
  засчитаны (гэп наблюдения — в команде брифа отсутствовала строка подключения `isql`; затем
  недостоверный вывод — файл результата не был очищен перед повтором). Третий прогон чистый, код
  возврата `0`: `UPDATE DEPOSIT_TYPES SET ID = ID WHERE 1 = 0;` в режиме
  `SET TRANSACTION READ ONLY` под `LOMBARD_RO` прошёл БЕЗ строки отказа. Компенсирующий контроль,
  на котором стоит решение, измерен и не сработал.
- **Это прямо названный в поправке брифа триггер**: «Второе изменение прошло без ошибки —
  немедленно стоп... это прямо названный триггер пересмотра решения ADR-032». Триггер сработал,
  учётка `LOMBARD_RO` исполнителем выведена из использования для операций, полагающихся на
  read-only режим транзакции как на защиту, и остаётся выведенной до твоего решения.
- **Задача `T-0-5` переведена в `blocked`** (статус, не `todo`) до этой сессии — правь его по
  факту принятого здесь решения, а не оставляй как есть.

Вопросы, на которые нужен ответ архитектора (не обязательно все три требуют отдельного ADR — но
каждый требует явного решения, а не молчания):

1. **Чем компенсирующий контроль заменяется**, если клиентский `READ ONLY` его не даёт — другой
   технический механизм (например, отдельная роль подключения на уровне драйвера/пула с
   принудительным `SET TRANSACTION READ ONLY`, подтверждённым иначе, чем в этом замере), процедурный
   контроль, или пересмотр самого решения не отзывать `PUBLIC`.
2. **Почему `READ ONLY` не сработал** — стоит ли разобраться в причине (версия Firebird 2.5,
   особенность движка, ошибка в самой пробе) прежде чем менять решение, или причина не имеет
   значения для итога. Замер называет находку, но диагностику причины не проводил — это может
   быть `CONTEXT GAP`, а не готовый факт.
3. **Что это означает для мандата `T-0-5` и связанных строк** (`T-0-3b`, мандатная таблица
   `07_STATE.md`) — они ссылаются на условие переезда в класс A, завязанное на этот самый лог
   шага 6-е; если контроль не работает, формулировку условия тоже нужно поправить, не только
   статус задачи.

Красные линии `00 §4` не отменяются этой сессией: `REVOKE` на `PUBLIC` по-прежнему не исполняется
без нового явного решения владельца — если ты придёшь к выводу, что отзыв нужен, это отдельный шаг
с отдельным подтверждением Ilyas, не автоматическое следствие пересмотра.

Мандат класса A даёт архитектору право писать код, конфиги и решения, коммитить локально. Класс B
(обращения к БД, публикация наружу) — как обычно, только с подтверждением владельца; в этой сессии
обращения к серверу не предполагаются, вся работа — над репозиторием.

Закончи одним session-блоком по `05 §III`. `NEW_DECISIONS` — новое решение (`ADR-033` — следующий
свободный номер на момент выпуска этого промта, сверить перед использованием) со статусом принятого
решения. `STATE_PATCH`: `Q-16` закрывается или переклассифицируется по решению; `T-0-5` получает
статус и мандат по факту решения. `INFRA_PATCH` обязателен: пустой пишется явным «нет изменений».
