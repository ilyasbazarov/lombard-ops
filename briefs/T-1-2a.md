## Ограничения
- К БД PawnShop — только SELECT (00 §4). Эта задача к базе клиента не обращается вовсе.
- К BigQuery эта задача не обращается вовсе (приёмка офлайн, на фикстурах) — обращение к BigQuery
  в коде этой задачи есть выход за scope, не находка.
- Секреты и endpoint'ы контура клиента в репозиторий не попадают: он публичный (ADR-001).
- `client_name` не наполняется (висит на `Q-30`); `vehicle_id`, `vehicle_make`, `vehicle_model`,
  `vehicle_year` не наполняются (`T-1-2b`) — SQL этой задачи их не трогает.
- Второе обращение к контуру клиента за уже выгруженными данными запрещено (`00 §3-БИС`,
  `ADR-083` п.5) — вся логика строится только над `raw_*`.

## Шаги
1. Выписать SQL `status_raw`: `raw_contracts.contract_state` → код в `raw_contract_states` →
   человекочитаемая строка статуса источника (JOIN по `state_id`). Прогнать на фикстуре из
   нескольких строк `raw_contracts`/`raw_contract_states` с известным по построению результатом.
2. Выписать SQL детектора продлений — ветвь «Переоткрытие» (`raw_contracts.id_prev_contract IS NOT
   NULL`) отдельным запросом/счётом на фикстуре, где ответ известен по построению.
3. Выписать SQL детектора продлений — ветвь «Погашение» (`raw_operations.op_vid = 0`, JOIN по
   `raw_operations.deposit_id = raw_contracts.contract_id`) отдельным запросом/счётом на той же
   фикстуре.
4. Объединить обе ветви через `OR` в итоговый признак `renewed`/`renewed_date`; предъявить третий
   счёт (объединение) на той же фикстуре — все три числа сверены с ожиданием по построению фикстуры.
5. Выписать SQL выбора снапшота (дедупликация): фикстура из ДВУХ строк одного `contract_id` с
   разными `source_blob`/`loaded_at` должна давать ровно ОДНУ строку на выходе (последний по
   `loaded_at`) — предъявить счёт до/после. Обратный замер: фикстура из ОДНОГО снапшота проходит
   без изменения счёта.
6. Собрать canonical view: по каждому активному договору — `issue_date`, `due_date`
   (`PLAN_CLOSE_DATE`), смещение `today − due_date` (`03 §1`), `status_raw`, `renewed`,
   `renewed_date`. `client_name` и `vehicle_*` — не включать (`NULL`/отсутствуют), предъявить это
   явно на фикстуре, не молчанием.
7. Сплошной поиск по коду задачи: ни одного обращения к BigQuery (`bq`, `google.cloud.bigquery`,
   `bigquery.Client` и т.п.) и ни одного обращения к базе клиента (Firebird/`fdb`/`isql`) — печать
   совпадений (пусто) плюс обратный запрос на заведомо присутствующей конструкции, доказывающий
   исправность поиска.
8. Сплошной поиск по всему репозиторию: ни один потребитель (кроме этой задачи и `T-1-2b`) не
   читает `loans_raw` напрямую — печать совпадений с решением по каждому.

## Критерии приёмки
- SQL канонизации и детектор продлений прогнаны на фикстурах слоя сырья — вывод команды запуска
  тестов приложен файлом, не пересказан.
- Детектор продлений предъявлен ОБЕИМИ ветвями раздельно (`id_prev_contract`, `op_vid = 0`) и их
  объединением — три счёта на фикстуре, где ответ известен по построению.
- Фикстура из ДВУХ снапшотов с разными `source_blob` даёт счёт строк ровно ОДНОГО снапшота —
  предъявлены обе стороны, до и после дедупликации (`ADR-084` п.6). Обратный замер: фикстура из
  ОДНОГО снапшота проходит без изменения счёта.
- `client_name` остаётся `NULL`/отсутствует в выводе canonical view — предъявлено, а не умолчано.
- `vehicle_*` остаются `NULL`/отсутствуют в выводе canonical view — предъявлено, а не умолчано.
- Canonical view отдаёт по каждому активному договору фикстуры дату выдачи, плановую дату
  закрытия, смещение от плановой даты и признак продления — на фикстуре.
- Ни один потребитель не читает `loans_raw` напрямую — предъявлено сплошным поиском по коду с
  печатью совпадений (шаг 8).
- Ни одного обращения к BigQuery и к базе клиента в коде этой задачи нет — предъявлено сплошным
  поиском по коду задачи, включая обратный запрос, доказывающий исправность поиска (шаг 7).
- Пустая или непарсимая выдача любого прогона теста при нулевом коде возврата не засчитывается —
  печатается лог с числами.
