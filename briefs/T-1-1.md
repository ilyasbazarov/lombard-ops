## Цель

После задачи: девять NDJSON-выгрузок, которые агент кладёт в `gs://${PROJECT_ID}-cfsource/agent/<дата>/`
каждые сутки в 03:00 Asia/Bishkek (`T-0-8`, уже исполнено), приземляются по расписанию (без ручного
запуска) в девять таблиц `raw_*` датасета `lombard_ops`, структура которых выведена из единственного
источника истины — отпечатка `connector/mapping.json`. Расхождение состава колонок таблицы с
отпечатком на загрузке останавливает приземление ЭТОЙ таблицы и шлёт алерт в боевой чат — не тихо
проходит с искажением. `loans_raw` эта задача не трогает: её наполнение из слоя сырья — предмет
`T-1-2`.

## Ограничения

- К БД PawnShop эта задача не обращается вовсе (см. «Роль»). Нет операции SELECT, нет `access_point`,
  нет учётной записи Firebird в этом коде.
- Секреты и endpoint'ы контура клиента в репозиторий не попадают (`ADR-001`): значение
  `telegram-bot-token` не логируется, не печатается, не коммитится нигде.
- **`telegram_send.py` копируется в `connector/raw_loader/`, не импортируется из `functions/cf_daily`
  (`ADR-078` пп.4–5).** Cloud Run Job деплоится `--source=connector/raw_loader` (по аналогии с
  `--source=functions/cf_daily` у `cf-daily` и `--source=app` у `app-lombard`) — контейнер получает
  СОДЕРЖИМОЕ этого каталога корнем; импорт из каталога вне `--source` в контейнере неразрешим, и это
  уже стоило раунда деплоя однажды (`ADR-078`, `cf-daily`). Файл копируется байт-в-байт, изменение
  логики отправки — не предмет этой задачи.
- **DDL `raw_*` не пишется от руки.** Любое ручное значение типа или имени колонки, не выведенное из
  `schema_fingerprint`, есть дефект — тот же принцип, что у `loans_raw` (`sql/ddl/lombard_ops.sql`,
  «Явные схемы: SELECT * / autodetect не используются нигде по конвейеру»), только источник данных для
  генерации здесь не голова исполнителя, а измеренный отпечаток.
- Guard на загрузке останавливает ВСЮ загрузку при расхождении хотя бы одной таблицы, тем же принципом,
  что guard на стороне агента (`schema_guard.guard_check`: «чтение НЕ выполняется вообще — ни для одной
  из девяти таблиц, даже для тех, что совпали») — расхождение схемы ставит под сомнение весь снимок.
- Один скрипт на ШАГ брифа, диагностику и класс-B действие в одном блоке не объединять.
- Ретраев на Telegram эта задача не проектирует (тот же принцип, что `T-1-0`): одно сообщение, один
  вызов, отказ — стоп и лог.
- **Прицеп `ADR-063` R3 обязателен**: код этой задачи несёт литеральный путь во внешний каталог данных
  (`gs://${PROJECT_ID}-cfsource/agent/...`) — хук проверки внешних источников (если он уже существует
  в `tools/hooks/`) обязан на него сработать корректно; если хука ещё нет — назвать это отдельной
  строкой в артефакте, не выдумывать хук самостоятельно (это `CONTEXT GAP`, не повод писать хук в
  обход отдельного брифа на него).

## Шаги

1. **Генератор DDL слоя сырья (класс A, код).** `connector/generate_raw_ddl.py`: чистая функция,
   принимающая распарсенный `connector/mapping.json` (или путь к нему), для каждой из девяти таблиц
   `schema_fingerprint` строящая `CREATE TABLE IF NOT EXISTS lombard_ops.raw_<имя таблицы в нижнем
   регистре> (...)` по правилу типов `ADR-083` п.4 (`7`→`INT64`, `8`→`INT64`, `12`→`DATE`, `16`→`INT64`
   при `scale=0` / `NUMERIC` при `scale<0`, `27`→`FLOAT64`, `35`→`TIMESTAMP`, `37`→`STRING`) плюс две
   служебные колонки `loaded_at TIMESTAMP NOT NULL` и `source_blob STRING NOT NULL`. Код типа вне этого
   списка → функция поднимает исключение с именем таблицы, колонки и кода — не «похожий тип», не
   тихий пропуск. Печатает результат в `sql/ddl/lombard_ops_raw.sql`. Тест на фикстуре — копии
   реального `schema_fingerprint` (или его подмножества) плюс мутированная копия с одним кодом типа
   вне списка (например `999`) — приёмка требует лога отказа на этой мутации И прохождения на
   нетронутой копии (обратный замер, `05 §I` «Наблюдение»). Без сети, без BigQuery.

2. **Guard на загрузке (класс A, код).** `connector/raw_loader/guard.py`: функция, принимающая имя
   таблицы, ожидаемую схему (та же, что построена шагом 1, как список `(имя, тип, mode)`) и ЖИВУЮ
   схему из BigQuery (`bigquery.Client.get_table(table_ref).schema`, через фабрику клиента —
   подменяемую точку для теста, тот же приём, что `bq_loader._default_bq_client_factory`). Сверка —
   множество `(имя, тип)` пар, порядок не важен. Расхождение → исключение с именем таблицы и обеими
   сторонами сравнения (эталон/измерено), тем же стилем сообщения, что
   `schema_guard.SchemaGuardMismatch`. Тест на моке BQ-клиента: (а) подмена одного типа в моковой живой
   схеме → стоп, лог отказа предъявлен; (б) нетронутая схема (равна ожидаемой) → проход, лог
   предъявлен (обратный замер). Без сети.

3. **Чтение NDJSON и загрузка в `raw_*` (класс A, код).** `connector/raw_loader/loader.py`: обобщение
   `bq_loader.read_ndjson_from_gcs`/`load_rows_to_bq` на произвольную таблицу — функция, принимающая
   `gs://` путь к блобу, имя целевой таблицы `raw_<table>`, ожидаемую схему (из шага 1), читающая
   объект, для каждой строки добавляющая `loaded_at` (момент запуска, UTC) и `source_blob` (путь
   блоба), загружающая явным списком колонок (`bigquery.LoadJobConfig`, `source_format=
   NEWLINE_DELIMITED_JSON`, `write_disposition=WRITE_APPEND`). Перед загрузкой вызывается guard шага 2
   для этой таблицы. Возвращает счёт загруженных строк и `loaded_at`. Тест на фикстуре из 2–3 строк
   NDJSON, моки GCS и BQ-клиентов, без сети.

4. **Копия отправителя Telegram (класс A, код).** Скопировать `functions/cf_daily/telegram_send.py`
   байт-в-байт в `connector/raw_loader/telegram_send.py` — причина копирования (не импорта) названа в
   «Ограничения». Тесты копируются тем же приёмом (`test_telegram_send.py`).

5. **Точка входа (класс A, код).** `connector/raw_loader/main.py`: точка входа Cloud Run Job (обычный
   Python-скрипт, `if __name__ == "__main__":`, Cloud Run Jobs не несёт HTTP-триггера в отличие от
   Cloud Function). Порядок: (а) прочитать `connector/mapping.json`, построить ожидаемые схемы девяти
   таблиц (шаг 1, тот же генератор — не дублировать логику построения схемы); (б) для каждой из девяти
   таблиц — найти самый свежий блоб `agent/<дата>/<TABLE>.ndjson` в бакете `${PROJECT_ID}-cfsource`
   (листинг префикса `agent/`, максимум по имени даты, тот же приём, что
   `find_latest_contracts_blob`, обобщённый на переменное имя таблицы); (в) вызвать guard (шаг 2) для
   этой таблицы; расхождение → залогировать причину, прочитать `telegram-bot-token`/`chat_id` (ключ
   `owner`) из Secret Manager, отправить алерт с именем таблицы и расхождением, **остановить весь
   прогон** (не продолжать на следующей таблице — «Ограничения», «Guard на загрузке останавливает
   ВСЮ загрузку»), завершиться ненулевым кодом; (г) guard прошёл — вызвать загрузчик (шаг 3),
   залогировать счёт строк и `loaded_at` по этой таблице; (д) после всех девяти — если ни одного
   расхождения не было, залогировать сводную строку (девять таблиц, счёт строк по каждой), завершиться
   кодом `0`. Любой упавший шаг для отдельной таблицы (сеть, GCS, BQ) — лог причины с именем таблицы;
   решение исполнителя, останавливать ли весь прогон на транспортном отказе одной таблицы или
   продолжать остальные восемь и вернуться к упавшей на следующие сутки, фиксируется в артефакте с
   причиной. Локальный тест на моках всех трёх внешних клиентов (GCS, BQ, Secret Manager, Telegram) —
   `connector/raw_loader/test_main.py`, включая сценарий с одной подменённой таблицей (guard стопит
   только показанный сценарий, алерт отправлен, остальные восемь не тронуты в тесте — подтвердить
   явно, какой вариант выбран).

6. **`requirements.txt`** (класс A). `connector/raw_loader/requirements.txt`: `google-cloud-storage`,
   `google-cloud-bigquery`, `google-cloud-secret-manager` — без `functions-framework` (это не Cloud
   Function).

    строкой, не писать хук в обход этого брифа.

## Критерии приёмки

- `bq query` печатает счёт строк по каждой из девяти таблиц `raw_*` и максимум `loaded_at` по
  каждой — лог шага 10 приложен целиком.
- Счёт строк в BigQuery сходится со счётом строк в исходном NDJSON-блобе по каждой из девяти таблиц —
  обе стороны напечатаны (шаг 10).
- Состав колонок каждой `raw_*` сходится с отпечатком `mapping.json` построчно — обе стороны
  напечатаны, ни одна колонка не добавлена и не потеряна (шаг 10).
- Подмена одного типа в эталоне отпечатка даёт стоп и алерт — лог отказа И доставленное (тестовое)
  сообщение предъявлены оба; обратный замер на нетронутом эталоне — прогон проходит (шаг 11).
- Код типа вне закрытого списка `ADR-083` п.4 даёт стоп генератора DDL, а не «похожий тип» — лог
  приложен (шаг 11).
- Повторный прогон в те же сутки не удваивает строки — счёт `raw_*` до и после повторного запуска
  job вручную на тестовом окружении (не боевом расписании) приложен.
- `gcloud scheduler jobs describe raw-loader-trigger` печатает расписание и часовой пояс — лог шага 9
  приложен целиком.
- Прогон не запускался руками — предъявлено источником запуска в логе (`gcloud logging read`,
  инициатор `cloudscheduler.googleapis.com`, не учётная запись человека), шаг 10.
- Прицеп `ADR-063` R3 предъявлен парой логов (подложный коммит завален, легитимный проходит) — шаг 12,
  либо `CONTEXT GAP` назван явно, если хук не существует.
- Локальные тесты всех модулей (`generate_raw_ddl`, `guard`, `loader`, `main`) зелёные — вывод команды
  запуска тестов приложен, не пересказан.
- Ни одного секретного значения (токен, боевой `chat_id` вне контекста версии секрета) в
  коммитируемых файлах нет — предъявлено сплошным поиском по патчу перед коммитом.
