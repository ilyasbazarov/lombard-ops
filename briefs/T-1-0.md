## Роль

Ты — исполнитель проекта. Законы — `CLAUDE.md`, стандарты — `05_CONVENTIONS.md` Части I и II.
Модель исполнения: ты исполняешь сам в пределах мандата класса A (написание кода, локальные тесты,
подготовка команд деплоя). Всё из перечня класса B (создание Cloud Function, IAM-биндинги, Cloud
Scheduler job, любая реальная отправка сообщения в боевой чат) — только отдельным действием после
явного подтверждения Ilyas, никогда в связке с диагностикой. Перед каждым запросом подтверждения —
ОТДЕЛЬНОЕ сообщение: что именно исполняется, на каком объекте, чем откатывается. `Done` — только по
предъявленному логу, не по коду возврата.

**Особенность приёмки этой задачи — растянута во времени.** «Два прогона в разные сутки» не
собираются в одной непрерывной сессии: после деплоя Cloud Scheduler исполняет прогон САМ по
расписанию — навязывать второй прогон вручную запрещено самой приёмкой («ни один прогон не
запускался руками»). Порядок: сессия 1 закрывает шаги 1–7 (код, деплой, первый автоматический
прогон дня N); сессия 2 (тот же бриф, тот же файл артефакта, не позже +48 часов) добирает лог
второго автоматического прогона дня N+1 и закрывает задачу. Это НЕ вторая параллельная сессия — это
продолжение той же незакрытой задачи, следующей по счёту на этой же ветке; закон «одно рабочее
дерево на сессию» этим не нарушается, если сессия 1 закоммитила и закрыла рабочее дерево перед
паузой.

## Цель

После задачи: минимальная версия конвейера работает end-to-end без участия человека. Cloud Scheduler
по расписанию (без ручного запуска) поднимает Cloud Function `cf-daily`, которая читает уже
выгруженный агентом (`T-0-8`) NDJSON одной таблицы Firebird из `gs://${PROJECT_ID}-cfsource`,
загружает его в BigQuery `loans_raw` (staging), вычисляет статус по формуле `03 §1` для одного
договора и отправляет одно сообщение об этом статусе в боевой чат Telegram (`T-0-18`). Задача —
точка переключения режима: до неё нитка шла по одной задаче за раз, после её закрытия — до трёх
параллельных потоков (`ADR-052`).

## Ограничения

- К БД PawnShop эта задача не обращается вовсе — вход уже лежит в GCS выгрузкой `T-0-8`.
- Секреты и endpoint'ы контура клиента в репозиторий не попадают (`ADR-001`): значение
  `telegram-bot-token` не логируется, не печатается, не коммитится нигде.
- **Маппинг `CONTRACTS` в `loans_raw` — ЧАСТИЧНЫЙ, и это сознательно, не дефект.** Заполняются ровно
  те колонки `loans_raw`, что выводятся из ОДНОЙ таблицы `CONTRACTS` по `02_DATA_CONTRACTS.md` §3:
  `contract_id` (`CONTRACT_ID`), `issue_date` (`CONTRACT_DATE`), `due_date` (`PLAN_CLOSE_DATE`),
  `loan_amount` (`DEPOSIT_SUM` ÷ 100). Остальные колонки (`vehicle_id`, `client_name`,
  `vehicle_make`/`model`/`year`, `status_raw`, `renewed`, `renewed_date`) требуют других таблиц
  (`SUBJECTS`, `CUSTOM_FIELDS_VALUES`, `OPERATIONS` и т.д.) — их заполнение и полная канонизация
  через SQL-слой предмет `T-1-2`, НЕ этой задачи. Пишутся `NULL`, это называется явно в артефакте, а
  не скрывается тишиной.
- Кодировка исходных строк — те же значения, что уже сериализовал `agent.py` (`_json_safe`):
  денежные величины строкой, даты ISO-8601. Повторного decode/charset-решения эта задача не делает —
  `LOMBARD_DB_CHARSET` уже применён на этапе агента (`T-0-8` шаг 7).
- Один скрипт на ШАГ брифа, диагностику и класс-B действие в одном блоке не объединять.
- `POST /token`-подобных ретраев на Telegram эта задача не проектирует — одно сообщение, один вызов,
  отказ — стоп и лог, повторная логика идемпотентности отправок — предмет `T-1-4`.

## Шаги

1. **Загрузчик BQ (класс A, код).** `functions/cf_daily/bq_loader.py`: функция, принимающая
   `gs://bucket/blob` пути к NDJSON `CONTRACTS`, читающая объект из GCS, парсящая построчный JSON,
   маппящая по правилу из «Ограничения» выше (`CONTRACT_ID`→`contract_id`, `CONTRACT_DATE`→
   `issue_date`, `PLAN_CLOSE_DATE`→`due_date`, `DEPOSIT_SUM`÷100→`loan_amount`, остальное `NULL`,
   `loaded_at` = момент запуска UTC) и загружающая строки в `lombard_ops.loans_raw` явным списком
   колонок (без autodetect, `05 §II`). Локальный тест на фикстуре из 2–3 строк, без сети — мок GCS и
   BQ-клиента.

2. **Расчёт статуса (класс A, код).** `functions/cf_daily/status.py`: функция, принимающая
   `due_date` и `today`, возвращающая пару (эмодзи/название статуса, кому уведомление) строго по
   таблице `03 §1` (смещение `today − due_date`; пороги `−7`, `−6…+1`, `+2`, `+16`, `+32`,
   `+39/+46/+62`). Тест — по одной проверке на каждую строку таблицы порогов плюс граничные значения
   (`−7` включительно, `−6` включительно), локально, без сети.

3. **Отправка в Telegram (класс A, код).** `functions/cf_daily/telegram_send.py`: функция,
   принимающая токен, `chat_id`, текст, вызывающая `POST https://api.telegram.org/bot<TOKEN>/sendMessage`
   (тот же вызов, что предъявлен в `reference/T-0-18_telegram_contour_setup_2026-08-18.md`), возвращающая
   `message_id` из ответа. Токен и `chat_id` читаются из Secret Manager (`google-cloud-secret-manager`,
   уже зависимость проекта — `connector/agent/requirements.txt`) внутри `main.py`, не в этом модуле:
   модуль принимает готовые значения параметрами, не читает секреты сам (проверяется тестом — вызов
   секретного клиента внутри `telegram_send.py` отсутствует, сплошной поиск `secretmanager` даёт 0
   совпадений в файле). Текст сообщения — `contract_id`, статус, дата плановая закрытия.

4. **Точка входа (класс A, код).** `functions/cf_daily/main.py`: HTTP-функция (сигнатура Cloud
   Functions Gen2 `functions_framework.http`) — порядок: (а) найти самый свежий блоб
   `agent/<дата>/CONTRACTS.ndjson` в бакете `${PROJECT_ID}-cfsource` (не хардкодить дату — листинг
   префикса `agent/` и выбор максимальной по имени даты каталога); (б) вызвать `bq_loader`, залогировать
   счёт загруженных строк и `loaded_at`; (в) выбрать ОДИН договор из загруженных (правило выбора —
   решение исполнителя, фиксируется в артефакте, например «первый по возрастанию `contract_id` с
   непустым `due_date`»); (г) вызвать `status.compute_status`; (д) прочитать `telegram-bot-token` и
   `chat_id` (ключ `owner`) из Secret Manager, вызвать `telegram_send`; (е) вернуть HTTP 200 с телом,
   печатающим все три факта — счёт строк, вычисленный статус, `message_id`. Любой шаг (а)–(д) упал →
   HTTP 500 с текстом причины, не тихий 200. Локальный тест на моках всех трёх внешних клиентов
   (GCS, BQ, Secret Manager, Telegram) — `functions/cf_daily/test_main.py`.

8. **Первый автоматический прогон (наблюдение, без ручного запуска).** Дождаться первого срабатывания
   Scheduler по расписанию (не форсировать `gcloud scheduler jobs run` — это ручной запуск и
   противоречит формулировке приёмки «ни один прогон не запускался руками»). Собрать лог: `bq query`
   печатает добавленную строку `loans_raw` с `loaded_at`; лог Cloud Function печатает вычисленный
   статус; ответ Telegram API (через тот же вызов, что и шаг 3) даёт `message_id`; Cloud Scheduler лог
   вызова (`gcloud logging read` по `resource.type="cloud_scheduler_job"`) — источник запуска
   `cloudscheduler.googleapis.com`, не человек. Положить в
   `reference/T-1-0_tracer_bullet_2026-08-18.md` как «Прогон 1, дата X».

9. **Второй автоматический прогон (наблюдение, другие сутки, возможно другая сессия — см. «Роль»).**
   То же самое на следующие сутки. Положить в тот же артефакт как «Прогон 2, дата X+1». Приёмка
   закрывается только после этого шага.

## Критерии приёмки

- `gcloud scheduler jobs describe cf-daily-trigger` печатает расписание и часовой пояс — лог шага 7
  приложен целиком.
- Два прогона в разные сутки предъявлены логом: строка в `loans_raw` с `loaded_at`, вычисленный
  статус, идентификатор отправленного сообщения — по каждому прогону отдельно (шаги 8 и 9).
- Ни один прогон не запускался руками — предъявлено источником запуска в логе (`gcloud logging read`,
  инициатор `cloudscheduler.googleapis.com`, не учётная запись человека) на КАЖДЫЙ из двух прогонов.
- Локальные тесты трёх модулей (`bq_loader`, `status`, `main`) зелёные — вывод команды запуска
  тестов приложен, не пересказан.
- Артефакт `reference/T-1-0_tracer_bullet_2026-08-18.md` называет: правило выбора одного договора,
  частичность маппинга (какие колонки `loans_raw` остались `NULL` и почему), оба прогона целиком.
- Ни одного секретного значения (токен, боевой `chat_id` вне контекста версии секрета) в
  коммитируемых файлах нет — предъявлено сплошным поиском по патчу перед коммитом.
