## Роль
Ты — исполнитель проекта. Законы — `CLAUDE.md`, стандарты — `05_CONVENTIONS.md` Части I и II.
Модель исполнения: команды на сервере запускает Ilyas по RDP и возвращает логи; ты пишешь команду
и ожидаемый вывод, читаешь лог, решаешь. `Done` — только по предъявленному логу, не по коду
возврата и не по «команда отработала».

## Цель
На сервере Firebird существует отдельный пользователь с правом ТОЛЬКО на чтение девяти нужных
таблиц, и предъявлен лог, что под ним: (а) чтение этих таблиц работает; (б) чтение системных
`RDB$`-таблиц работает — без него не работает guard схемы (`ADR-004`); (в) чтение НЕ выданной
таблицы отбивается ошибкой прав; (г) попытка записи отбивается ошибкой прав. После задачи
регулярные обращения к базе идут только под этим пользователем.

## ЗАМЕРЕННОЕ СОСТОЯНИЕ НА ВХОДЕ — читать до первого шага

**Пользователь `LOMBARD_RO` на сервере УЖЕ СУЩЕСТВУЕТ.** Замер 2026-08-08, просмотр списка учётных
записей сервера: строка `LOMBARD_RO` присутствует, полное имя пустое, код возврата 0. Кроме неё в

это сведения о системе клиента, и `ADR-001` их не разрешает явно, а при сомнении действует запрет.

**В репозитории записи о создании этой учётки НЕТ.** Сплошной поиск по рабочему дереву и по ВСЕЙ
истории: имя встречается только в тексте этого брифа и в артефакте архитекторской сессии; ни один
session-блок её создания не фиксировал. Объяснение владельца: часть задач выполнялась ранними
чатами, не возвращавшими блок в репозиторий. То есть потерян не результат, а ЗАПИСЬ о нём.

**Следствия для этой задачи:**
- Шаг «создать пользователя» ЗАМЕНЯЕТСЯ на ветку «пользователь существует» (см. Шаги).
- Пароль учётки неизвестен. Слепой подбор запрещён; пароль сбрасывается административно.
- Выданы ли ей права — на момент выпуска этой редакции НЕ ИЗМЕРЕНО. Ветка ниже написана под оба
  исхода намеренно: это развилка, а не догадка. Первый шаг исполнителя — снять этот замер.

**История старого чата — ЗАЯВЛЕНИЕ, а не факт.** Если владелец приложит переписку, где учётка
создавалась, оттуда берутся только гипотезы для проверки. В репозиторий идёт результат замера на
сервере, а не цитата из переписки. Совпало — записывается как подтверждённое, с указанием, что
источник гипотезы был чат. Не совпало — расхождение называется поимённо, и верен сервер.

**Ловушка записи файлов, подтверждена замером 2026-08-08.** `Set-Content -Encoding UTF8` в Windows
PowerShell пишет BOM, и `isql` падает на первой строке скрипта с `Token unknown`. Файлы запросов
писать без BOM (`[System.IO.File]::WriteAllText` с `UTF8Encoding($false)`) и печатать первые байты
файла ДО запуска — фикстура проверяется, а не предполагается. Тот же дефект уже был зафиксирован в
журнале изменений задачей `T-0-2` и всё равно повторился: это довод печатать байты, а не помнить.

## Ограничения

- **К данным PawnShop — только чтение** (`00 §4`). Создание пользователя и выдача прав на чтение —
  единственное разрешённое исключение, прямо предусмотренное конвенциями и планом. Никаких иных
  изменений схемы или данных: ни удаления, ни изменения объектов вендора, ни правки существующих
  пользователей вендора.
- `SELECT *` запрещён — везде явные списки колонок.
- **Санитария `ADR-001`:** в логах и session-блоке нет паролей и нет персональных данных клиентов.
  Для проверок достаточно `COUNT(*)`, значения строк не выводятся.
- **Не-идемпотентные шаги:** обрыв связи во время создания пользователя → слепой повтор ЗАПРЕЩЁН.
  Сначала read-only диагностика (просмотр списка пользователей), потом доисполнение только
  недостающего хвоста.
- **Недостоверный вывод:** побитый при копировании лог из RDP фактом не является. Не примирять
  противоречия догадкой — запросить чистый повторный лог.

## Особенности Firebird 2.5, учесть обязательно

1. **Пользователи общесерверные, а не внутри базы.** Живут в служебной базе безопасности в
   каталоге установки Firebird. То есть создание пользователя — запись в служебную базу сервера
   вендора, а выдача прав — запись в метаданные рабочей базы. Оба факта зафиксировать в логе явно.
2. **Старый режим проверки пароля значимо учитывает только первые 8 символов.** Длинный пароль не
   даёт длинной защиты. Это **проверяется замером**, а не принимается на веру (шаг 6-д).
   Практическое следствие: основной контроль доступа — правило файрвола на порту базы.
3. **Обновление ERP может переустановить Firebird и потерять служебную базу безопасности** —
   пользователь исчезнет. Поэтому скрипт пере-запускаемый, а будущий коннектор обязан падать
   громко на ошибке аутентификации, а не молчать. Вписать в «что вернуть» как вход для `T-0-8`.
4. **Права на системные `RDB$`-таблицы** в этой версии обычно доступны всем, но это
   **подтверждается замером** (шаг 6-б). Без чтения `RDB$` guard схемы не работает, и тогда нужен
   отдельный грант либо пересмотр `ADR-004`.

## Шаги

Каждый шаг — одна команда для запуска Ilyas по RDP, с напечатанным ожидаемым выводом.
**Шаг 1 read-only. Шаги 2 и 3 меняют состояние сервера — перед каждым отдельное сообщение
подтверждения по `ADR-018`.**

1. **Диагностика списка учётных записей — ИСПОЛНЕНА 2026-08-08, повторять не нужно.** Результат
   вынесен в раздел «Замеренное состояние на входе»: `LOMBARD_RO` существует. Перезапускать шаг
   только если есть основание считать, что состояние сервера с тех пор менялось.

1-БИС. **Снять права существующей учётки — read-only, это первый живой шаг.** Запрос к
   `RDB$USER_PRIVILEGES` по имени `LOMBARD_RO`, явные колонки, файл запроса без BOM, первые байты
   файла напечатать до запуска. Ожидаемый вывод — либо список таблиц с буквой права напротив
   каждой, либо ПУСТАЯ выдача при коде возврата 0. Пустая выдача при нулевом коде есть факт «прав
   не выдавали»; пустая выдача при ненулевом коде — гэп наблюдения, а не факт. **Откат не нужен:**
   шаг ничего не меняет.

2. **Ветка по результату шага 1-БИС.** Выбрать ОДНУ, назвать выбор в логе и в session-блоке.
   - **(а) Прав нет.** Учётка пустая: выдать права шагом 3, дальше по общей схеме.
   - **(б) Права есть и совпадают с нашими девятью таблицами.** Ничего не выдавать заново; шаг 3
     прогнать только для фиксации идемпотентности и предъявить лог без ошибок.
   - **(в) Права есть, но НЕ совпадают.** Расхождение выписать поимённо в обе стороны: чего не
     хватает против девяти таблиц и что выдано сверх них. Недостающее — выдать. Лишнее **не
     отзывать самостоятельно**: отзыв прав у чужой по происхождению учётки есть изменение чужого
     состояния, вернуть архитектору решением. Формулировка «лишних прав нет» без напечатанного
     сравнения не принимается.

3. **Сбросить пароль существующей учётки.** Пароль неизвестен, подбор запрещён — значение
   назначается административно программой управления пользователями (ключ модификации, не
   добавления: добавление существующего имени вернёт ошибку и это ожидаемо). Новый пароль
   придумывает и хранит Ilyas. **Откат:** пароль назначается повторно тем же способом; учётка при
   этом НЕ удаляется — удаление обнулило бы уже выданные права и историю, которой мы не владеем.
   **Удаление `LOMBARD_RO` этой задачей запрещено.**

4. **Выдать недостающие права** скриптом `scripts/grant_ro.sql`, по одной строке на таблицу.
   Выдача идемпотентна, повторный прогон безопасен. Ожидаемый вывод — без ошибок.
   **Откат:** отзыв прав тем же списком, только по строкам, которые выдала ЭТА задача.

5. **Положить скрипт в репозиторий** как `scripts/grant_ro.sql`: после обновления ERP его гоняют
   заново, и список прав виден в ревью. Пароли и путь к базе в файл не попадают — параметризуются.

6. **Проверки под учётной записью `LOMBARD_RO` — это и есть приёмка.** Все пять предъявляются логом.
   - а. `COUNT(*)` по каждой из девяти таблиц — возвращает числа.
   - б. чтение системных `RDB$`-метаданных — возвращает строки. Не вернуло → стоп, `CONTEXT GAP`
     архитектору: нужен отдельный грант или пересмотр `ADR-004`.
   - в. `COUNT(*)` по одной НЕ выданной таблице — ожидается ошибка прав. Успех вместо ошибки =
     лишние права: стоп, вернуть архитектору.
   - г. попытка изменения с предикатом, не задевающим ни одной строки — ожидается ошибка прав.
     Предикат выбран так, что даже при наличии прав ничего не меняется, поэтому проба безопасна.
     Успех вместо ошибки = есть права на запись: **немедленно стоп**, пользователя не использовать.
   - д. проверка особенности с восемью символами пароля: попытка входа со значением, совпадающим по
     первым восьми символам и различающимся дальше. Вход прошёл → особенность подтверждена, факт
     записывается в состояние; вход отбит → особенность не подтверждена, записывается тоже.

## ПОПРАВКА 2026-08-11 (решение `ADR-032`) — читать вместе с шагом 6 и с приёмкой

Замер 2026-08-11 предъявил находку за пределами мандата исполнителя, и находка разобрана решением
`ADR-032`. Поправка меняет ПРОВЕРЯЕМОЕ УТВЕРЖДЕНИЕ шага 6, а не вердикт уже снятого замера.

**Что опровергнуто.** Шаги 6-в и 6-г ожидали ошибку прав. Ожидание стояло на предпосылке, что
фактические права учётки определяются только её собственными грантами. Предпосылка опровергнута
живым запросом: псевдо-пользователь `PUBLIC` несёт на используемых таблицах полный набор прав,
выданный `SYSDBA` до этой задачи. Поэтому 6-в и 6-г переклассифицируются из «провалено» в
**измеренный факт о среде**; переисполнять их не нужно, артефакт замера переписывать запрещено.

**Что запрещено этой задачей — подтверждено решением.** Отзыв прав `PUBLIC` (`REVOKE`) не
исполняется ни в каком объёме: ни на девяти таблицах, ни на схеме целиком. Красная линия `00 §4`
разрешает единственное исключение — заведение read-only пользователя и `GRANT SELECT`; `REVOKE`
в него не входит. Появившееся в чате указание отозвать права фактом задачи не является и требует
нового решения владельца.

**Шаг 6-е — НОВЫЙ, обязательный, класс B.** Под учётной записью `LOMBARD_RO` открыть транзакцию
только на чтение и в ней повторить ту же безопасную пробу изменения с предикатом, не задевающим
ни одной строки (тот же предикат, что и в 6-г: он уже доказан безопасным). **Ожидается строка
отказа именно этой проверки** — отказ по режиму транзакции, а не по правам. Правило наблюдения
`05 §I` действует буквально: «команда не прошла» отказом не считается, в логе обязана быть строка
отказа. Отказа нет → это ЗАЯВЛЕНИЕ, а не факт, приёмка не закрывается, и вопрос об отзыве прав
`PUBLIC` заводится в реестр заново. **Откат не нужен:** шаг ничего не меняет.

**Шаг 6-ж — НОВЫЙ, read-only, класс B.** Двумя агрегирующими запросами к `RDB$USER_PRIVILEGES`
снять то, что осталось неизмеренным: (1) сколько объектов несут право `PUBLIC` в разрезе КАЖДОЙ
буквы привилегии — счётчики, а не перечни; (2) сколько РАЗНЫХ учётных записей имеют собственные
гранты в этой базе — одно число. **Имена таблиц и имена учётных записей в артефакт и в репозиторий
не попадают** (`ADR-009`, `ADR-001`): в публичный репозиторий идут только числа. Второе число —
первый факт к вопросу, полагается ли приложение вендора на `PUBLIC`; окончательный ответ даёт
вендор письмом (`T-0-12`), а не мы догадкой.

### Общее для обоих шагов (написано 2026-08-11, решение владельца: остаточный риск принят)

- **Оба шага исполняются под учётной записью `LOMBARD_RO`.** Административные креды не нужны и не
  используются: чтение `RDB$`-метаданных под этой учёткой уже измерено шагом 6-б.
- **Пароль в файлы, в лог и в репозиторий не попадает.** Он вводится в приглашение при запуске и
  живёт только в переменной сессии PowerShell.
- **Ловушка BOM (`T-0-2`, повторилась в `T-0-5`).** Файл запроса пишется через `WriteAllText` с
  `UTF8Encoding($false)`, и первые байты печатаются ДО запуска — фикстура проверяется, а не
  предполагается. Ожидаемое начало обоих файлов — байты `83 69 84` (это буквы `SET`); байты
  `239 187 191` в начале означают BOM: файл перезаписать, `isql` не запускать.
- **Путь к `isql.exe` не угадывается, а проверяется** `Test-Path` до запуска; нет файла — стоп и
  `CONTEXT GAP`, а не поиск наугад.
- **Правило вердикта (`05 §I`).** Ничто не считается сделанным по коду возврата. Для обоих шагов
  предъявляется ЛОГ; для отрицательного случая в логе обязана быть строка отказа именно той
  проверки, которую мерили. Ненулевой код возврата у шага 6-е ОЖИДАЕМ и сам по себе фактом не
  является.
- **Санитария (`ADR-001`, `ADR-009`).** В артефакт идут строки логов как есть; из шага 6-ж — только
  числа. Имена таблиц вендора и имена учётных записей в публичный репозиторий не переносятся.

### Шаг 6-е — карточка подтверждения класса B (отдельным сообщением ДО запуска)

- **Что исполняется:** два пробных изменения с предикатом `WHERE 1 = 0` по таблице `DEPOSIT_TYPES` —
  первое в обычной транзакции (контроль исправности пробы), второе в транзакции только на чтение
  (измеряемое). Плюс два `COUNT(*)` как доказательство живого соединения.
- **На каком объекте:** база PawnShop на сервере клиента, подключение `localhost/3057`, файл базы
  `D:\PawnShop_DOL\DB\DOL.FDB`, учётная запись `LOMBARD_RO`.
- **Чем откатывается:** откат не требуется и невозможен по построению — предикат `WHERE 1 = 0`
  гарантирует ноль задетых строк, что уже подтверждено замером 2026-08-11. Схема, права и данные не
  меняются.
- **Почему обе пробы, а не одна:** пара в одном логе и есть доказательство. Первая показывает, что
  проба доходит до сервера и при обычной транзакции проходит; вторая — что режим «только чтение»
  её отбивает. Одна вторая проба без первой не отличает «контроль работает» от «соединение
  сломалось».

```powershell
# ШАГ 6-е — отбивает ли транзакция только на чтение попытку записи.
# Запускать на сервере ERP по RDP. Одна команда на весь шаг (05 §I).
$fbRoot = 'C:\Program Files (x86)\Firebird-2.5-PawnShop\'
$isql   = Join-Path $fbRoot 'bin\isql.exe'
if (-not (Test-Path $isql)) { Write-Host "CONTEXT GAP: не найден isql по пути $isql"; return }

New-Item -ItemType Directory -Force -Path $work | Out-Null
$q   = Join-Path $work 'step6e.sql'
$out = Join-Path $work 'step6e_out.txt'

$sql = @'
COMMIT;
SELECT COUNT(*) AS CNT_ALIVE_RW FROM DEPOSIT_TYPES;
UPDATE DEPOSIT_TYPES SET ID = ID WHERE 1 = 0;
COMMIT;
SET TRANSACTION READ ONLY;
SELECT COUNT(*) AS CNT_ALIVE_RO FROM DEPOSIT_TYPES;
UPDATE DEPOSIT_TYPES SET ID = ID WHERE 1 = 0;
COMMIT;
'@
[System.IO.File]::WriteAllText($q, $sql, (New-Object System.Text.UTF8Encoding($false)))

# Фикстура: первые байты файла ДО запуска. Ожидается "83 69 84", НЕ "239 187 191".
Write-Host "первые байты файла запроса:" (([System.IO.File]::ReadAllBytes($q))[0..7] -join ' ')

$ro = Read-Host 'Пароль учётной записи LOMBARD_RO'
& $isql -user LOMBARD_RO -pas $ro -e -m -i $q -o $out

Get-Content -Path $out -Encoding UTF8
```

**Ожидаемый вывод шага 6-е.** Первые байты — `83 69 84 ...`. `CNT_ALIVE_RW` и `CNT_ALIVE_RO` —
числа (по замеру 2026-08-11 в этой таблице 7 строк; иное число означает изменение данных, а не
отказ проверки). Первое изменение — **тишина, без ошибки** (так уже было измерено шагом 6-г).
Второе изменение — **строка отказа**, ожидаемо вида `Statement failed, SQLSTATE = 25006` с текстом
о попытке изменения в транзакции только на чтение. Код возврата `isql` при этом ненулевой — это
ожидаемо. Текст отказа переносится в артефакт ДОСЛОВНО, каким бы он ни оказался: сверять надо, что
отказ пришёл по режиму транзакции, а не по правам и не по соединению.

**Исходы шага 6-е и что делать.**
- **Отказ получен** → компенсирующий контроль подтверждён фактом. Шаг пройден.
- **Второе изменение прошло без ошибки** → **немедленно стоп.** Контроля нет ни на уровне СУБД, ни
  на нашей стороне; это прямо названный триггер пересмотра решения `ADR-032`. Учётку не
  использовать, вопрос завести в реестр заново, вернуть архитектору.
- **Отказ пришёл, но не по режиму транзакции** (например, соединение или права) → это гэп
  наблюдения, а не результат: перезапустить чисто и предъявить разделимый лог.

### Шаг 6-ж — карточка подтверждения класса B (отдельным сообщением ДО запуска)

- **Что исполняется:** два запроса ТОЛЬКО НА ЧТЕНИЕ к системной таблице прав `RDB$USER_PRIVILEGES`,
  оба агрегирующие: счётчики объектов по каждой букве привилегии у `PUBLIC` и число разных
  получателей прав в разрезе типа. Ни одной операции изменения.
- **На каком объекте:** та же база и та же учётная запись, что в шаге 6-е.
- **Чем откатывается:** откат не нужен, шаг ничего не меняет.
- **Зачем:** закрывает то, что осталось неизмеренным, — сколько объектов реально несут ПРАВА ЗАПИСИ
  у `PUBLIC` (раньше в состоянии стояла цифра шире замера) и сколько вообще получателей прав есть в
  этой базе. Второе число — первый факт к вопросу о зависимости приложения вендора от `PUBLIC`;
  окончательный ответ даёт вендор письмом (`T-0-12`), а не мы догадкой.

```powershell
# ШАГ 6-ж — агрегаты прав PUBLIC и число получателей прав. Только чтение.
$fbRoot = 'C:\Program Files (x86)\Firebird-2.5-PawnShop\'
$isql   = Join-Path $fbRoot 'bin\isql.exe'
if (-not (Test-Path $isql)) { Write-Host "CONTEXT GAP: не найден isql по пути $isql"; return }

$work = 'C:\Temp\lombard'
New-Item -ItemType Directory -Force -Path $work | Out-Null
$q   = Join-Path $work 'step6zh.sql'
$out = Join-Path $work 'step6zh_out.txt'

$sql = @'
SET LIST ON;
SELECT RDB$PRIVILEGE AS PRIV, COUNT(*) AS CNT_OBJECTS
  FROM RDB$USER_PRIVILEGES
 WHERE RDB$USER = 'PUBLIC' AND RDB$OBJECT_TYPE = 0
 GROUP BY RDB$PRIVILEGE
 ORDER BY RDB$PRIVILEGE;
SELECT RDB$USER_TYPE AS UTYPE, COUNT(DISTINCT RDB$USER) AS CNT_GRANTEES
  FROM RDB$USER_PRIVILEGES
 WHERE RDB$OBJECT_TYPE = 0
 GROUP BY RDB$USER_TYPE
 ORDER BY RDB$USER_TYPE;
'@
[System.IO.File]::WriteAllText($q, $sql, (New-Object System.Text.UTF8Encoding($false)))

Write-Host "первые байты файла запроса:" (([System.IO.File]::ReadAllBytes($q))[0..7] -join ' ')

$ro = Read-Host 'Пароль учётной записи LOMBARD_RO'
& $isql -user LOMBARD_RO -pas $ro -e -m -i $q -o $out
Write-Host "код возврата isql: $LASTEXITCODE"
Get-Content -Path $out -Encoding UTF8
```

**Ожидаемый вывод шага 6-ж.** Первый запрос — до пяти строк вида «буква привилегии → число
объектов». **Встроенная проверка исправности:** строка `S` обязана дать `107` — ровно то число,
которое уже измерено 2026-08-11. Не дало → инструмент или предикат не тот, результат не
засчитывается. Строки `I`, `U`, `D` и есть искомое: они впервые называют, на скольких объектах
`PUBLIC` несёт ПРАВА ЗАПИСИ. Второй запрос — по строке на тип получателя с числом разных
получателей.

**Известный риск шага 6-ж и что делать.** Если второй запрос вернёт отказ вида `Column unknown`
на `RDB$USER_TYPE`, колонка в этой версии называется иначе: **не подбирать имя наугад**, а снять
перечень колонок системной таблицы (`SELECT RDB$FIELD_NAME FROM RDB$RELATION_FIELDS WHERE
RDB$RELATION_NAME = 'RDB$USER_PRIVILEGES' ORDER BY RDB$FIELD_NAME;`) и повторить запрос уже по
измеренному имени. Пустая выдача при нулевом коде возврата фактом «получателей нет» не является —
это гэп наблюдения.

**Что закрывает приёмку после поправки:** пройденные 1-БИС, 2, 3(заменён), 4, 6-а, 6-б, 6-д плюс
предъявленные логи 6-е и 6-ж. Переезд обращений к базе в класс A по факту закрытия этой задачи
**не наступает** — условие переезда переписано `ADR-032` и завязано на лог шага 6-е.

## ПОПРАВКА 2 · 2026-08-11 (решение `ADR-033`) — заменяет шаг 6-е, читать вместо него

Поправка `ADR-032` выше остаётся на месте как запись принятого тогда решения и переписыванию не
подлежит. Действует то, что ниже.

**Что снято.** Шаг 6-е в прежней форме («ожидается строка отказа») **снимается и не
переисполняется**. Разбор — `ADR-033`. Коротко: обе пробы шага, в обычной транзакции и в режиме
`SET TRANSACTION READ ONLY`, — это один и тот же `UPDATE ... WHERE 1 = 0`, и обе дали одинаковую
тишину. Вывод, не меняющийся между исходами, об исходе ничего не говорит. Предикат `WHERE 1 = 0`
гарантирует ноль задетых строк, поэтому при отказе на уровне изменяемой записи проба до отказа не
доходит НИКОГДА — тишина в этом случае ожидаема и при исправном контроле. Вердикт «контроль
опровергнут» снят; правильный вердикт — «не измерен».

**Действие исполнителя признано верным целиком.** Остановка по названному стоп-условию, невыпуск
шага 6-ж, вывод учётной записи из использования — верны при любом объяснении тишины и не
отменяются. Правило «сомнение толкуется в пользу остановки» сработало как задумано.

**Что запрещено — подтверждено решением.** Проба, задевающая хотя бы одну строку, на базе клиента
**не исполняется никогда**: если контроль не держит, это и есть запись в базу вендора, прямой
запрет `00 §4`. Уровень отказа в движке меряется на НАШЕМ экземпляре Firebird 2.5.9, задачей
`T-0-17`, и в эту задачу не входит. `REVOKE` на объектах вендора по-прежнему не исполняется ни в
каком объёме.

**Шаг 6-е-БИС — НОВЫЙ, обязательный, класс B, ТОЛЬКО ЧТЕНИЕ.** Под `LOMBARD_RO` предъявить
ПОЛОЖИТЕЛЬНЫЙ факт: как движок называет режим текущей транзакции. Один и тот же запрос к
`MON$TRANSACTIONS` выполняется дважды — в обычной транзакции и после `SET TRANSACTION READ ONLY`.
**Проба обязана различать исходы (`05 §I`, пятое правило наблюдения):** засчитывается только
результат, в котором два прогона напечатали РАЗНЫЕ значения признака режима. Одинаковые значения
означают, что режим не вступил в силу, — это факт о клиенте подключения, и он тоже записывается.

### Шаг 6-е-БИС — карточка подтверждения класса B (отдельным сообщением ДО запуска)

- **Что исполняется:** два запроса `SELECT` к системной таблице `MON$TRANSACTIONS` по текущей
  транзакции. Ни одной операции изменения, ни одного `UPDATE` — в отличие от снятого шага 6-е.
- **На каком объекте:** база PawnShop на сервере клиента, подключение `localhost/3057`, файл базы
  `D:\PawnShop_DOL\DB\DOL.FDB`, учётная запись `LOMBARD_RO`.
- **Чем откатывается:** откат не нужен и не имеет предмета — шаг только читает.
- **Почему два прогона, а не один:** одно значение ни о чём не говорит, потому что не с чем
  сравнить. Различие двух и есть доказательство, что режим переключается.

```powershell
# ШАГ 6-е-БИС — как движок называет режим текущей транзакции. Только чтение.
# Запускать на сервере ERP по RDP. Одна команда на весь шаг (05 §I).
$fbRoot = 'C:\Program Files (x86)\Firebird-2.5-PawnShop\'

$q   = Join-Path $work 'step6ebis.sql'
$out = Join-Path $work 'step6ebis_out.txt'
Remove-Item -Path $out -Force -ErrorAction SilentlyContinue   # чистый файл результата (урок 2-й попытки 6-е)

$sql = @'
SET LIST ON;
COMMIT;
SELECT MON$TRANSACTION_ID AS TX_RW, MON$READ_ONLY AS RO_FLAG_RW, MON$ISOLATION_MODE AS ISO_RW
  FROM MON$TRANSACTIONS WHERE MON$TRANSACTION_ID = CURRENT_TRANSACTION;
COMMIT;
SET TRANSACTION READ ONLY;
SELECT MON$TRANSACTION_ID AS TX_RO, MON$READ_ONLY AS RO_FLAG_RO, MON$ISOLATION_MODE AS ISO_RO
  FROM MON$TRANSACTIONS WHERE MON$TRANSACTION_ID = CURRENT_TRANSACTION;
COMMIT;
'@
[System.IO.File]::WriteAllText($q, $sql, (New-Object System.Text.UTF8Encoding($false)))

# Фикстура: первые байты файла ДО запуска. Ожидается "83 69 84", НЕ "239 187 191".

$ro = Read-Host 'Учётная запись LOMBARD_RO — введите её пароль'

```

**Ожидаемый вывод шага 6-е-БИС.** Две группы строк. `RO_FLAG_RW` и `RO_FLAG_RO` — признак режима;
ожидается, что они РАЗНЫЕ. Номера транзакций тоже разные — это доказательство, что второй прогон
идёт в новой транзакции, а не в прежней.

**Известный риск шага и что делать.** Если запрос вернёт отказ вида `Column unknown` на
`MON$READ_ONLY` (или `Token unknown` на `CURRENT_TRANSACTION`), имя в этой версии другое: **не
подбирать наугад**, а снять перечень колонок (`SELECT RDB$FIELD_NAME FROM RDB$RELATION_FIELDS WHERE
RDB$RELATION_NAME = 'MON$TRANSACTIONS' ORDER BY RDB$FIELD_NAME;`) и повторить по измеренному имени.
Если отказ придёт на правах доступа к `MON$TRANSACTIONS` — это тоже факт, он записывается, и шаг
закрывается им: чтение `MON$` под нашей учёткой оказалось недоступно. Пустая выдача при нулевом коде
возврата фактом не является — это гэп наблюдения (`05 §I`).

**Исходы шага 6-е-БИС и что делать.**
- **Признаки различаются** → режим транзакции переключается, третье объяснение тишины снято.
  Остаётся вопрос уровня отказа — он у `T-0-17`, не здесь. Шаг пройден.
- **Признаки одинаковые** → `SET TRANSACTION READ ONLY` в этом клиенте не вступает в силу. Шаг тоже
  пройден (факт снят), но эшелон объявляется отсутствующим до починки клиента подключения, и это
  записывается в состояние отдельной строкой.
- **Отказ по правам или по имени колонки** → см. известный риск; после уточнения имени — повтор.

**Шаг 6-ж остаётся без изменений** — он read-only и к разбору отношения не имеет.

**Что закрывает приёмку после ПОПРАВКИ 2:** пройденные 1-БИС, 2, 3(заменён), 4, 6-а, 6-б, 6-д плюс
предъявленные логи 6-е-БИС и 6-ж. **Переезд обращений к базе в класс A по факту закрытия этой задачи
не наступает** — условие переезда переписано `ADR-033` и завязано на три предъявленных факта, из
которых один добывается задачей `T-0-17`, а не этой.
