# BRIEF · T-0-5 · Read-only пользователь Firebird + GRANT SELECT

> Механический бриф. Свежий Sonnet-чат выполняет задачу, не зная о других чатах.
> Всё нужное — ниже или в context-to-load.

## Цель

На сервере Firebird PawnShop существует отдельный пользователь БД, имеющий право
только на чтение нужных нам таблиц, и подтверждено логом, что под ним: (а) SELECT
из этих таблиц работает; (б) SELECT из RDB$-метаданных работает (нужно guard'у
ADR-004); (в) любая попытка записи отбивается ошибкой прав. Прод-конвейер после
этого подключается только под ним, а SYSDBA перестаёт использоваться для
регулярных операций.

## Ограничения

- **К данным PawnShop — только SELECT** (00 §4, 05 §I). Единственное разрешённое
  исключение этой задачи, прямо предусмотренное 05 §I и 04_ROADMAP: создание
  пользователя и `GRANT SELECT`. Никаких иных DDL/DML. Ни `DROP`, ни `ALTER` над
  объектами вендора, ни изменения существующих пользователей вендора.
- **`SELECT *` запрещён** (05 §II) — везде явные списки колонок.
- **Санитария ADR-001**: в логах и session-блоке нет паролей, нет ПДн клиентов.
  Значения из проверочных SELECT'ов маскировать/не выводить — достаточно `COUNT(*)`.
- **Не-идемпотентные операции (05 §I)**: обрыв RDP во время создания пользователя →
  слепой retry запрещён. Сначала read-only диагностика (`gsec -display`), потом
  доисполнение только недостающего хвоста.
- **Untrusted-вывод (05 §I)**: побитый paste из RDP недостоверен — не примирять
  противоречия, запросить чистый повторный лог.
- **Модель исполнения (05 §I)**: Sonnet пишет команды с ожидаемым выводом; запускает
  Ilyas и возвращает логи; done только после подтверждённого человеком лога.

## Известные особенности Firebird 2.5, учесть обязательно

1. **Пользователи в Firebird 2.5 — общесерверные, не в базе.** Живут в
   `security2.fdb` в каталоге установки Firebird
   (`C:\Program Files (x86)\Firebird-2.5-PawnShop\`). То есть создание
   пользователя — запись в служебную БД сервера вендора, а `GRANT` — запись в
   метаданные `DOL.FDB`. Оба факта зафиксировать в логе явно.
2. **Legacy-аутентификация значимо учитывает только первые 8 символов пароля.**
   Длинный пароль не даёт длинной энтропии. Это надо **проверить, а не принять на
   веру** (шаг 5). Практическое следствие: основной контроль доступа — firewall-
   правило на 3057, а не длина пароля.
3. **Обновление PawnShop может переустановить Firebird и потерять
   `security2.fdb`** — пользователь исчезнет. Поэтому скрипт создания должен быть
   пере-запускаемым, а коннектор обязан падать громко на ошибке аутентификации
   (не молчать). Отразить в return-this как вход для T-0-8.
4. **Права на системные `RDB$`-таблицы** в Firebird 2.5 обычно доступны всем
   пользователям по умолчанию, но это **надо подтвердить замером** (шаг 5.б), а не
   предположить: без чтения RDB$ guard ADR-004 не работает, и тогда потребуется
   явный `GRANT SELECT` на нужные RDB$-таблицы.

## Шаги

1. **Read-only диагностика до любых изменений.** Дать Ilyas на запуск в PowerShell
   на ERP-сервере: список существующих пользователей сервера. Ожидаемый вывод —
   перечень с SYSDBA и, возможно, пользователями вендора. Цель: убедиться, что
   имени `LOMBARD_RO` ещё нет, и не затронуть пользователей вендора.

       & "C:\Program Files (x86)\Firebird-2.5-PawnShop\bin\gsec.exe" `
         -user SYSDBA -password <из_кред_Ilyas> -display

2. **Создать пользователя `LOMBARD_RO`.** Пароль генерирует и подставляет Ilyas
   (в бриф не пишется). Ожидаемый вывод — пустой (gsec молчит при успехе), затем
   повторный `-display` показывает нового пользователя.

       & "C:\Program Files (x86)\Firebird-2.5-PawnShop\bin\gsec.exe" `
         -user SYSDBA -password <из_кред_Ilyas> `
         -add LOMBARD_RO -pw <пароль_от_Ilyas>

3. **Выдать `GRANT SELECT`** на девять таблиц из «Входных артефактов», по одной
   строке на таблицу, скриптом в файле (не по одной команде вручную — скрипт должен
   быть пере-запускаемым по п.3 особенностей). Файл `grant_ro.sql`, запуск через
   isql. Ожидаемый вывод — без ошибок; `GRANT` в Firebird идемпотентен, повторный
   прогон безопасен.

4. **Зафиксировать список гранта в репо** как `/scripts/grant_ro.sql` — чтобы после
   обновления PawnShop его можно было прогнать заново, и чтобы список прав был
   виден в ревью. Пароли и путь к .fdb в файл не попадают — параметризовать.

5. **Проверки под новым пользователем** (это и есть приёмка):
   а. `SELECT COUNT(*)` по каждой из девяти таблиц — должно вернуть числа.
   б. `SELECT FIRST 5 TRIM(RDB$RELATION_NAME), RDB$FIELD_POSITION FROM
      RDB$RELATION_FIELDS ORDER BY 1, 2` — должно вернуть строки. Не вернуло →
      guard ADR-004 под этим пользователем не работает: остановиться, вернуть
      CONTEXT GAP на Opus (нужен отдельный GRANT на RDB$ или пересмотр ADR-004).
   в. `SELECT COUNT(*)` по одной НЕ гранутой таблице (взять любую из дампа вне
      списка девяти) — ожидается ошибка прав. Успех вместо ошибки = у пользователя
      лишние права: остановиться и вернуть на Opus.
   г. Попытка записи: `UPDATE CONTRACTS SET NOTE = NOTE WHERE 1 = 0` — ожидается
      ошибка прав. **Важно:** предикат `1 = 0` не изменяет ни одной строки даже при
      наличии прав, поэтому проба безопасна. Успех вместо ошибки = права на запись
      есть: немедленно остановиться, вернуть на Opus, пользователя не использовать.
   д. То же для `INSERT`
