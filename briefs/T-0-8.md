## ПОПРАВКА 3 (`ADR-050`, 2026-08-13) — обязательна к чтению; побеждает текст ниже и ПОПРАВКИ 1–2

**`Q-21` ЗАКРЫТ. Задача разблокирована. Шаг 5 в форме «ключ SA» остаётся снятым навсегда и

новый публичный бакет НЕ заводится, три бакета `T-0-7` не трогаются. Замер способа доставки —

**Что из этого следует для исполнителя, до первой команды:**

1. **Закрытый ключ подписи есть НОВЫЙ секрет контура клиента.** В репозиторий, в артефакт

2. **В Secret Manager закрытый ключ не кладётся.** Чтобы прочитать секрет, агенту нужны учётные

3. **Отказ платформы на любом шаге — стоп и вопрос архитектору, а не подбор значения** (`ADR-050`,

4. **Штатный механизм бьёт самодельный** (`ADR-048`): файл конфигурации учётных данных

Исполняется в Cloud Shell под учётной записью владельца. Порядок внутри шага обязателен: сначала
две read-only проверки, потом создание.

- **Карточка подтверждения.** Что исполняется: две read-only команды и три команды создания —
  пул федерации, OIDC-провайдер с загруженными открытыми ключами, привязка роли на существующий

  `gcloud iam service-accounts remove-iam-policy-binding` той же привязки,
  `gcloud iam workload-identity-pools providers delete` и `... pools delete` — команды отката
  пишутся в карточке ДО создания. Значения в лог не печатаются: их в этом шаге нет — открытый ключ
  секретом не является.

Состав:

1. **Read-only, обязательно ПЕРВЫМ:**
   `gcloud org-policies describe constraints/iam.allowedPolicyMemberDomains --project=project-c451b48a-07ae-4de4-961 --effective`
   — ограничение доменов в IAM-политиках не измерялось ни разу, а оно способно отбить выдачу роли
   внешнему principal. Это ровно тот класс неизмеренного ограничения, который снял шаг 5.
   Ограничение действует → **СТОП и вопрос архитектору**, а не попытка обойти.
2. **Read-only:** `gcloud services list --enabled --project=project-c451b48a-07ae-4de4-961`
   с печатью совпавших строк по `iamcredentials` и `sts`. Отсутствует — включается
   `gcloud services enable` тем же шагом; `iamcredentials` в проекте уже был подтянут зависимостью
   (`reference/T-0-7_gcp_foundation_measurement_2026-08-12.md`, шаг 2), это сверка, а не догадка.
3. Создание пула: `gcloud iam workload-identity-pools create` с локацией `global`.
4. Создание провайдера: `gcloud iam workload-identity-pools providers create-oidc` с

   полученным на шаге 5-Б**. Из этого следует порядок: **открытая часть ключа рождается ДО этой

5. Привязка: `gcloud iam service-accounts add-iam-policy-binding` на

   `roles/iam.workloadIdentityUser`, member — `principal://…/subject/<субъект агента>`.
   **Новых ролей сервисному аккаунту не выдаётся:** он уже несёт ровно то, что нужно конвейеру
   (`11_INFRA_FACTS`).

**Ожидается и что означает каждый исход.** Провайдер создан → механизм замкнут, идём на 5-В.
Отказ по `--issuer-uri` (значение не принято, требуется достижимость) → **СТОП**, порядок
отступления в `ADR-050`: сначала issuer-URI под доменом, которым владеет клиент, без публикации по

отдельное решение владельца, а не действие сессии. Отказ по политике организации → **СТОП и вопрос
архитектору**: это второй случай того же класса, и он меняет постановку, а не параметр команды.

- Артефакт: `reference/T-0-8_federation_setup_<дата>.md` — вывод всех команд дословно, включая

### Шаг 5-Б — ключ подписи, JWKS и конфигурация учётных данных на сервере (класс B, сервер клиента)

- **Карточка подтверждения.** Что исполняется: генерация пары ключей на сервере ERP, запись файла
  закрытого ключа с ограниченными правами, экспорт открытой части в файл JWKS, генерация файла
  конфигурации учётных данных штатной командой, установка Python и включение службы времени
  Windows. На каком объекте: сервер ERP по RDP. Чем откатывается: удаление созданного каталога
  агента с ключом и конфигурацией; служба времени и Python остаются — это откату не подлежит и
  названо в карточке явно.

Состав:

1. **Пара ключей RSA 2048** генерируется на сервере (годность измерена:
   `reference/T-0-8_server_identity_measurement_2026-08-13.md`, раздел 3). Закрытая часть — файл с
   правами ТОЛЬКО на учётную запись службы агента; права предъявляются в артефакте выводом команды,
   а не утверждением.
2. **JWKS** — открытая часть в формате RFC 7517 (`kty`, `alg`, `use`, `kid`, `n`, `e`). Файл
   уезжает на сторону облака как вход шага 5-А, пункт 4. Секретом не является.
3. **Модуль подписи JWT в `connector/agent/`** — этого модуля НЕТ, и он пишется здесь (`ADR-050`
   п. 10: это добавление, а не переписывание). Он подписывает JWT с `iss`, равным значению
   `--issuer-uri`, `sub`, совпадающим с условием провайдера, `aud` провайдера, `iat`/`exp`, и
   кладёт результат в файл, на который смотрит конфигурация учётных данных. **`exp` минус `iat` —
   не больше 24 часов** (требование платформы), фактически — минуты.
4. **Файл конфигурации учётных данных** генерируется командой
   `gcloud iam workload-identity-pools create-cred-config` с `--credential-source-file` и
   `--service-account`; руками не пишется (`ADR-048`).
5. **Служба времени Windows включается и её работа предъявляется** выводом `w32tm /query /status`
   без ошибки. Замер 2026-08-13 показал `0x80070426` — служба не запущена; при неверных часах STS
   отобьёт JWT по `iat`/`exp`. Это **условие приёмки шага**, не пожелание.
6. **Python ставится** — на сервере его нет ни в одной из четырёх проверенных форм, а агент написан
   на Python. Версия печатается в артефакт.
7. **Отрицательный случай предъявляется отдельно:** JWT с истёкшим `exp` (или с `sub`, не
   проходящим условие провайдера) обменивается на токен и получает ОТКАЗ — в лог идёт строка отказа
   именно этой проверки, а не посторонний сбой (`05 §I`, «неуспех инструмента — тоже не факт»).

Ровно эта строка, побуквенно, без завершающего слэша, идёт в ДВА места и больше никуда:

1. **шаг 5-А, пункт 4** — флаг `--issuer-uri` команды
   `gcloud iam workload-identity-pools providers create-oidc`;
2. **шаг 5-Б, пункт 3** — claim `iss` подписываемого JWT, то есть поле `issuer` конфигурации
   `JwtSigningConfig` в `connector/agent/jwt_signer.py` (модуль отказывает на пустом значении —
   подстановка обязана быть явной).

Расхождение между этими двумя местами хоть на один символ означает отказ обмена токена на шаге 5-Б
п. 7 — сверять их печатью обеих строк в артефакте, а не глазом.

### Почему домен клиента не нужен (кратко; полностью — `ADR-051`)

Замер `reference/T-0-8_issuer_uri_requirements_measurement_2026-08-13.md`: единственное названное
платформой требование к значению — схема `https`; `gcloud` значение не валидирует вовсе; обращение
платформы по issuer-URI документировано ровно для случая, когда JWKS НЕ загружен, а мы загружаем
его флагом `--jwk-json-path`. TLD `.invalid` (RFC 6761 §6.4) в корневую зону не делегируется
никогда — имя не может быть зарегистрировано ни нами, ни третьей стороной, поэтому оно безопаснее
реального домена: если платформа когда-нибудь всё же пойдёт за документом обнаружения, она не
получит ничего вместо чужого содержимого. Нового облачного и сетевого ресурса значение не создаёт;
секретом и endpoint'ом контура клиента не является (не указывает ни на один живой хост), поэтому
лежит в публичном репозитории законно.

### Что делать при отказе платформы на пункте 4 (порядок отступления ЗАМЕНЁН)

Прежняя первая ступень `ADR-050` («issuer-URI под доменом, которым клиент владеет, без публикации
по нему чего-либо») **ОТМЕНЕНА** `ADR-051` п. 6: она лечила не тот отказ — требование достижимости
есть требование документа обнаружения по `/.well-known/openid-configuration`, а домен без
публикации его не отдаёт, то есть отказ повторился бы слово в слово.

Действующий порядок:

1. Значение выше — единственная ступень, исполняемая сессией.
2. Отказ платформы (любой: значение не принято, требуется достижимость, требуется документ
   обнаружения) → **СТОП, текст ошибки в артефакт дословно, вопрос владельцу**. Подбор другого
   значения запрещён. На столе три варианта, и каждый есть решение владельца: покупка домена
   клиентом плюс публикация документа обнаружения и JWKS (новый публичный ресурс и новый расход);
   домен подрядчика (issuer федерации клиента становится чужим активом); возврат к туннелю
   (оценён и не рекомендован).

**Приёмка пункта 4 дополняется одной строкой:** артефакт печатает значение `--issuer-uri` из
вывода `describe` созданного провайдера и рядом — строку `issuer` из конфигурации подписи; обе
совпадают дословно.

## Ограничения

- **К БД PawnShop — только чтение** (`00 §4`). Ни одной операции записи ни при каких условиях.
- **Каждое подключение открывается транзакцией только на чтение** и доказывает это положительным
  фактом — строкой `MON$` о режиме текущей транзакции, а не отсутствием ошибки (`ADR-037`).
- **Белый список операторов — не «проверка на всякий случай», а условие приёмки.** Функция доступа
  пропускает `SELECT`, `WITH` и чтение `RDB$`/`MON$`; всё остальное отбивает исключением ДО отправки
  на сервер. **Проверка идёт по разобранному оператору, а не по подстроке:** запрет по вхождению
  слова ловится первым же комментарием или строковым литералом и даёт ложное чувство защиты.
- **Секреты — только Secret Manager** (`05 §II`). Пароль базы не лежит в коде, в конфиге агента и в
  репозитории. В артефакт не печатается ни при каких условиях.
- **Ничего не устанавливать на сервер вне явного шага этого брифа** (`10`, практика RDP).
- **Не-идемпотентные операции**: обрыв → сначала read-only диагностика, потом доисполнение хвоста.
- **Пустая выдача при нулевом коде возврата — гэп наблюдения.**

## Шаги

### Шаг 1 — связность, ДО всякого кода (класс B, сервер клиента)

**Это шаг, ради которого порядок именно такой.** Проверить с сервера клиента:
исходящий HTTPS до `storage.googleapis.com` и `oauth2.googleapis.com` — код ответа и цепочка
сертификатов; наличие прокси в системных настройках; версию Windows и наличие актуального
хранилища корневых сертификатов.

- **Карточка подтверждения.** Что исполняется: несколько исходящих HTTPS-запросов с сервера
  клиента, ничего не устанавливается и не меняется. На каком объекте: сервер ERP по RDP. Чем
  откатывается: откат предмета не имеет — только сетевые запросы на чтение.

**Ожидается и что означает каждый исход.** Прошло — канал жив, идём дальше. Не прошло по прокси или
фильтру — **СТОП, вариант А (туннель) возвращается решением владельца**, задача переоформляется.
Не прошло по сертификатам — это чинится на сервере и остаётся в пределах задачи, но фиксируется
отдельной строкой инфра-фактов. **Ни один исход не «обходится» подбором** — угадывание причины
запрещено, печатается текст ошибки дословно.

### Шаг 2 — точка доступа с белым списком (класс A, стол)

Без сервера и без облака. Написать `connector/agent/access_point.py`: единственную функцию, через
которую в проекте уходит любой SQL к PawnShop.

Требования, каждое проверяемо:
- принимает текст запроса, возвращает строки; больше в базу ничего не уходит;
- **разбирает оператор**, а не ищет подстроку: пропускается только `SELECT` и `WITH … SELECT`;
- перед выполнением открывает транзакцию только на чтение и **проверяет режим положительным
  фактом** — читает признак режима текущей транзакции и падает, если он не тот;
- печатает текст запроса в лог ДО отправки;
- явные списки колонок обязательны, `SELECT *` отбивается как запрещённый.

### Шаг 3 — тест точки доступа (класс A, стол)

`connector/agent/test_access_point.py`. Обе стороны каждой проверки обязательны (`ADR-033`: проба
различает исходы):
- разрешённый `SELECT` по разрешённой таблице — проходит и возвращает строки;
- `UPDATE`, `INSERT`, `DELETE`, `DROP`, `GRANT`, `EXECUTE BLOCK` — каждый отбивается исключением;
- `SELECT` с запрещённым оператором внутри комментария или строкового литерала — **проходит**
  (доказывает, что проверка идёт по разобранному оператору, а не по подстроке);
- `UPDATE`, замаскированный переносами строк и регистром, — **отбивается**;
- обращение к таблице вне девяти разрешённых — отбивается;
- попытка работы при режиме транзакции не «только чтение» — отбивается.

Тест гоняется на нашей стороне, к базе клиента не подключаясь: подключение подменяется. Логика
белого списка не зависит от того, есть ли база.

### Шаг 4 — агент: чтение и выгрузка (класс A, стол)

Код агента поверх точки доступа: guard схемы (`ADR-004`) перед чтением — снять отпечаток метаданных
используемых таблиц и сверить с эталоном, расхождение даёт **стоп и алерт, не искажение**; затем
чтение разрешённых таблиц явными списками колонок; запись выгрузки в бакет
`${PROJECT_ID}-cfsource` (или бакет, названный в `11_INFRA_FACTS` под выгрузку); поведение при
недоступности GCS — назвать явно и реализовать: повтор с задержкой, предел попыток, запись в
локальный журнал, отсутствие тихой потери.

Эталон отпечатка на входе задачи может отсутствовать (`connector/mapping.json` заводится `T-0-10`).
Тогда первый прогон **создаёт** отпечаток и печатает его, а сверка включается со второго — это
записывается фактом, а не обходится молча.

## Критерии приёмки

- Связность агент→GCS предъявлена логом ДО кода агента; исход назван и, если отрицательный, задача
  остановлена, а не обойдена.
- Точка доступа существует одной функцией; **весь SQL проекта к PawnShop идёт через неё** —
  предъявить поиском по коду, что другого пути нет.
- Тест точки доступа предъявлен логом, **обе стороны каждой проверки**: разрешённое проходит,
  запрещённое отбивается, запрещённое слово внутри комментария не даёт ложного отказа,
  замаскированный запрещённый оператор отбивается.
- Транзакция только на чтение подтверждена ПОЛОЖИТЕЛЬНЫМ фактом — строкой признака режима.
- Guard схемы вызывается перед чтением; отпечаток предъявлен, поведение при расхождении — стоп.
- Выгрузка легла в бакет — предъявлен объект командой чтения; число строк напечатано.
- Поведение при недоступности GCS названо и проверено — предъявлен лог отказа и повтора.
- Ни один секрет не напечатан в логе и не лежит в репозитории — предъявить поиском.
- Ни один критерий не закрывается кодом возврата.
