## Ограничения
- **К БД PawnShop — только чтение** (`00 §4`). Ни одной операции записи, ни `GRANT`, ни правки
  метаданных.
- **Весь SQL идёт через `access_point()`.** Ни `cursor.execute` напрямую, ни второй путь к базе.
  Обращение мимо точки доступа — нарушение мандата, а не «другой способ сделать то же самое».
- **`SELECT *` запрещён** — везде явные списки колонок.
- **Санитария (`ADR-039`, дословно).** МОЖНО: имена и типы используемых таблиц и колонок, их смысл,
  агрегаты, распределения, порядковые номера. НЕЛЬЗЯ: номера договоров, имена людей, VIN, значения
  строк с данными клиентов.
- **Пустая выдача при нулевом коде возврата — гэп наблюдения**, а не «данных нет». Каждый счётный
  запрос сопровождается обратным контролем.
- **Ни одно число не вписывается в приёмку константой** (`ADR-042`): счёт печатает сам прогон на дату.
- **Правка порогов `03 §1`** при обнаружении материальной группы коротких сроков — НЕ этой задачей:
  вердикт называется и передаётся архитектору решением.

## Шаги

### Шаг 1 — модуль замера (класс A, локально)
Написать `connector/agent/discovery_t0_6.py`: именованные запросы, каждый через
`access_point(connection, sql)`. Печатает только агрегаты, ничего не пишет в базу. Подключение —
тем же способом, что в `run_daily.py`. Запросы:
- `active_status_distribution` — счёт активных договоров и распределение по значениям
  `CONTRACT_STATES` (join `CONTRACTS.CONTRACT_STATE`);
- `active_offset_distribution` — для каждого активного договора `today − PLAN_CLOSE_DATE`,
  распределение по бакетам порогов `03 §1` (`−7 и раньше`, `−6…+1`, `+2…+15`, `+16…+31`, `+32 и
  далее`);
- `anomaly_empty_plan_close_date` — счёт активных договоров с пустой `PLAN_CLOSE_DATE`;
- `anomaly_nonpositive_term` — счёт активных договоров с `PLAN_CLOSE_DATE − CONTRACT_DATE ≤ 0`;
- `anomaly_renewal_without_predecessor` — счёт договоров, отмеченных признаком продления (`03 §2`,
  обе ветви), у которых при этом не находится валидный предшественник (пустой/нерезолвящийся
  `ID_PREV_CONTRACT` при отсутствии операции `OP_VID=0`);
- `active_term_histogram` — распределение `PLAN_CLOSE_DATE − CONTRACT_DATE` **по активным
  договорам**, отдельно по признаку продления (есть/нет) — обе стороны;
- `renewal_share_active` — доля активных договоров в цепочке продления (`OR` обеих ветвей);
- `op_vid0_distinct_contracts` — счёт РАЗЛИЧНЫХ договоров с хотя бы одной операцией `OP_VID = 0`,
  отдельно общий счёт договоров (для сверки с 1111 / 2509 из `T-0-4a`);
- `vehicle_field_candidates` — все строки `DIR_CUSTOM_FIELDS` по `LIKE '%<фрагмент>%'` для марки,
  модели, года и госномера (не голое имя — `11_INFRA_FACTS.md`), печатает ВСЕ совпавшие строки с
  `ID_FIELD`;
- `vehicle_field_value_counts` — по каждому найденному `ID_FIELD` из предыдущего запроса — счёт
  непустых значений в `CUSTOM_FIELDS_VALUES`.

### Шаг 2 — оффлайн-тест белого списка (класс A, локально)
`connector/agent/test_discovery_t0_6.py`: каждый запрос модуля прогоняется через `validate_query`
без подключения к базе. Два исхода обязательны: все запросы задачи проходят, заведомо запрещённый
оператор отбивается. **Ожидается:** число проверенных запросов равно числу запросов модуля (печатаются
оба числа), провалов ноль, отрицательный случай отбит.

### Шаг 3 — доставка на сервер (класс B, карточка подтверждения)
Модуль и обёртку `scripts/T-0-6_run_discovery.ps1` доставить на сервер ERP по проверенному каналу:
base64 + `certutil`, сверка SHA-256 на обеих сторонах. Через буфер RDP текстом не передавать.

### Шаг 4 — положительные контроли (класс B, карточка подтверждения)
Первый прогон на сервере: версия движка · признак режима текущей транзакции из `MON$` · счёт строк
одной разрешённой таблицы. Только после того, как эти три величины напечатаны, идут остальные шаги.

### Шаг 5 — распределение по статусам и аномалии (класс B, карточка подтверждения)
`active_status_distribution`, `active_offset_distribution`, `anomaly_empty_plan_close_date`,
`anomaly_nonpositive_term`, `anomaly_renewal_without_predecessor` — все пять с печатью счёта.

### Шаг 6 — срок договора по активным, в разрезе продлений (класс B, карточка подтверждения)
`active_term_histogram`. **Ожидаемое ДО прогона:** если материальная группа коротких сроков (по
аналогии с 9-дневной группой на всей истории, `03 §2`) присутствует и среди активных — порог `03 §1`
требует правки на долю срока, и это называется вердиктом архитектору, не правится здесь; если группы
нет — вопрос закрывается как снятый.

### Шаг 7 — `renewal_share_active` и гипотеза 44% (класс B, карточка подтверждения)
`renewal_share_active`, `op_vid0_distinct_contracts`. **Ожидаемое ДО прогона** (`ADR-023`): счёт
различных договоров близко к 1111 при 2509 — гипотеза о происхождении 44% усилена; заметно меньше —
отвергнута.

### Шаг 8 — поля объекта: марка, модель, год, госномер (класс B, карточка подтверждения)
`vehicle_field_candidates`, затем `vehicle_field_value_counts` по каждому найденному `ID_FIELD`.
**Поле с нулём значений в `CUSTOM_FIELDS_VALUES` полем-источником не является.** Печатаются ВСЕ
совпавшие строки, а не только отобранные.

### Шаг 9 — фиксация знания (класс A)
- `02_DATA_CONTRACTS.md §3`: строки марки, модели, года и госномера — только по найденным и
  подтверждённым ненулевым счётом `ID_FIELD`; не найдено → явное «не найдено» с именем поля.
- `03_BUSINESS_SPEC.md §1`: измеренные счёт и распределение аномалий; вердикт по короткому сроку.
- `03_BUSINESS_SPEC.md §2`: измеренное значение `renewal_share_active` на дату прогона; вердикт по
  гипотезе 44%.
- Артефакт замера со всеми логами, все запросы напечатаны дословно ДО запуска.

## Критерии приёмки
(взяты из строки `T-0-6` `04_ROADMAP.md`, читать оригинал как приёмку)
- счёт активных договоров печатает сам прогон на дату (не константа);
- распределение по статусам напечатано таблицей;
- три класса аномалии названы поимённо числом случаев: активный статус при прошедшей плановой дате
  (через бакеты `active_offset_distribution`), отрицательный/нулевой день цикла
  (`anomaly_nonpositive_term`), продление без предшественника (`anomaly_renewal_without_predecessor`);
- **два новых класса аномалии `ADR-070`** со счётом: пустая `PLAN_CLOSE_DATE` у активного договора,
  разность `PLAN_CLOSE_DATE − CONTRACT_DATE ≤ 0`;
- распределение срока договора напечатано **по активным** и **отдельно в разрезе признака
  продления** — обе стороны;
- `renewal_share_active` напечатан прогоном на дату;
- различающая проверка гипотезы 44%: счёт различных договоров с `OP_VID = 0`, отнесённый к счёту
  договоров, напечатан;
- **пятый пункт `ADR-083` п.8:** имена полей госномера, марки, модели и года найдены `LIKE`-поиском
  по `DIR_CUSTOM_FIELDS`, все совпавшие строки напечатаны с `ID_FIELD`; по каждому найденному
  `ID_FIELD` напечатан счёт непустых значений; результат лёг строками в `02 §3`;
- оффлайн-тест белого списка предъявлен обоими исходами;
- ни один критерий не закрывается кодом возврата; пустая или непарсимая выдача при нулевом коде —
  гэп наблюдения, а не результат.
