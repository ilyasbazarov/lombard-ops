## Цель

Предъявлен лог, отвечающий на один вопрос: **на каком уровне Firebird 2.5.9 отбивает попытку
изменения в транзакции только на чтение — оператора или изменяемой записи, — и отбивает ли вообще.**
От этого зависит, есть ли у проекта второй рубеж защиты от записи в базу вендора или его нет вовсе
(`ADR-033`, `ADR-034`). Ответ закрывает строку `Q-17`.

## Входы

Замерено 2026-08-11 на машине Ilyas, повторной проверки не требует, но и слепо не наследуется —
первый шаг сверяет:
- архитектура `arm64`, macOS `15.3.1`;
- Homebrew установлен: `/opt/homebrew/bin/brew`, версия 6.0.14;
- **контейнерного движка нет**: `colima`, `docker`, `podman`, `lima` не установлены;
- **Firebird на машине нет**: `isql`, `fbsvcmgr`, `gfix` не найдены, каталога
  `/Library/Frameworks/Firebird.framework` нет.

Отсюда площадка замера: контейнер с Firebird 2.5.9 на машине Ilyas. Образ x86_64 под arm64 идёт
через эмуляцию — медленно, и это нормально: проба крошечная.

## Ограничения

- **Ни одной команды к контуру клиента.** Ни сервера ERP, ни базы PawnShop, ни RDP. Если по ходу
  возникает соблазн «проверить заодно на живой базе» — это прямой запрет `00 §4` и причина, по
  которой задача вообще существует (`ADR-033`).
- **Версия не подменяется.** Мерим ровно `2.5.9` — версию инсталляции вендора (`11_INFRA_FACTS`).
  Тега `2.5.9` нет в реестре образов → печатается ошибка, СТОП, `CONTEXT GAP`. Замер на `2.5.8`,
  `3.0` или «примерно той же ветке» ответом на `Q-17` не является и в артефакт не пишется.
- **Пароль контейнера в репозиторий не пишется** (`ADR-001`). Он выброшенный и живёт минуты, но
  правило не знает исключений, а проверка секретов на коммите завалит патч.
- **Санитария:** в артефакт идут логи проб как есть. Никаких данных клиента здесь нет и быть не
  может — база создаётся пустой.

## Шаги

1. **Сверить площадку.** Один скрипт: `uname -m`, `sw_vers -productVersion`, `brew --version`,
   `which colima docker`. Ожидается совпадение с разделом «Входы». Расхождение — не стоп, а факт:
   записывается в артефакт и дальше действуют по фактическому состоянию.

2. **Поставить контейнерный движок** (класс A, наша машина):
   ```bash
   brew install colima docker
   colima start --arch x86_64 --cpu 2 --memory 4 --disk 20
   docker info | head -20
   ```
   Ожидается печать сведений о демоне. Ошибка — печатается целиком, не заминается.

3. **Забрать образ ровно версии 2.5.9.**
   ```bash
   docker pull jacobalberty/firebird:2.5.9-sc
   ```
   Тег не найден → **не подбирать соседний**: напечатать ошибку, снять перечень доступных тегов
   любым доступным способом и остановиться с `CONTEXT GAP`. Версию решает приёмка, а не удобство.

4. **Поднять контейнер и ПРЕДЪЯВИТЬ ВЕРСИЮ СЕРВЕРА.** Пароль администратора образ генерирует сам и
   печатает в свой лог — оттуда он и берётся; явным присваиванием в командной строке его не задавать.
   ```bash
   docker run -d --name fb259 jacobalberty/firebird:2.5.9-sc
   sleep 20
   docker logs fb259 | tail -20
   docker exec fb259 /usr/local/firebird/bin/isql -z -quiet -i /dev/null
   ```
   **Встроенная проверка исправности:** напечатанная версия сервера обязана содержать `2.5.9`.
   Не содержит — прогон не засчитывается, независимо от того, что вернули остальные шаги.
   Путь к `isql` внутри образа не угадывается: не нашёлся — `docker exec fb259 sh -c 'command -v isql
   || ls /usr/local/firebird/bin /opt/firebird/bin 2>/dev/null'`, и дальше по измеренному пути.

5. **Создать выброшенную базу и одну строку.** Скрипт `scripts/readonly_probe_setup.sql`:
   ```sql
   CREATE DATABASE '/tmp/probe.fdb';
   CREATE TABLE PROBE (ID INTEGER NOT NULL, TXT VARCHAR(16));
   INSERT INTO PROBE (ID, TXT) VALUES (1, 'row');
   COMMIT;
   SELECT COUNT(*) AS CNT_SETUP FROM PROBE;
   ```
   Ожидается `CNT_SETUP = 1`. Иного исхода у шага нет: пустая выдача при нулевом коде возврата —
   гэп наблюдения, а не «таблица создана».

6. **Контроль пробы в ОБЫЧНОЙ транзакции — оба предиката.** Тем же подключением:
   ```sql
   UPDATE PROBE SET ID = ID WHERE 1 = 0;
   UPDATE PROBE SET ID = ID WHERE ID = 1;
   COMMIT;
   SELECT COUNT(*) AS CNT_AFTER_RW FROM PROBE;
   ```
   Ожидается тишина по обеим и `CNT_AFTER_RW = 1`. **Это и есть положительный контроль:** он
   доказывает, что оба предиката исполнимы и что второй действительно доходит до записи. Отказ здесь
   означает неисправную пробу — вердикт не выносится, разбирается причина.

7. **Измеряемое, проба с НУЛЕВЫМ предикатом** — точная копия шага 6-е задачи `T-0-5`. Отдельный
   файл `scripts/readonly_probe_zero.sql` и отдельный прогон с ЧИСТЫМ файлом результата:
   ```sql
   COMMIT;
   SET TRANSACTION READ ONLY;
   SELECT MON$READ_ONLY AS RO_FLAG FROM MON$TRANSACTIONS WHERE MON$TRANSACTION_ID = CURRENT_TRANSACTION;
   UPDATE PROBE SET ID = ID WHERE 1 = 0;
   COMMIT;
   ```
   Ожидается либо строка отказа, либо тишина — обе одинаково валидны и обе записываются дословно.
   Строка `RO_FLAG` печатается ЗДЕСЬ намеренно: она заодно проверяет форму пробы шага 6-е-БИС
   задачи `T-0-5` до того, как её понесут на базу клиента. Колонка не найдена (`Column unknown`) →
   не подбирать имя, а снять перечень колонок `MON$TRANSACTIONS` из `RDB$RELATION_FIELDS` и
   повторить по измеренному имени.

8. **Измеряемое, проба с предикатом НА ОДНУ СТРОКУ.** Отдельный файл
   `scripts/readonly_probe_row.sql`, отдельный прогон, чистый файл результата:
   ```sql
   COMMIT;
   SET TRANSACTION READ ONLY;
   UPDATE PROBE SET ID = ID WHERE ID = 1;
   COMMIT;
   SELECT COUNT(*) AS CNT_AFTER_RO FROM PROBE;
   ```
   Разнесение шагов 7 и 8 по разным прогонам обязательно: отказ в одном не должен проглотить вывод
   другого, и смешанный файл результата уже один раз испортил замер этой задачи (`T-0-5`, вторая
   попытка шага 6-е).

9. **Снести площадку.** `docker rm -f fb259`, `colima stop`. Выброшенная база уезжает вместе с
   контейнером; в репозитории от неё остаются только скрипты и лог.

## Критерии приёмки

- Напечатана версия сервера, и в ней есть `2.5.9`. Нет — прогон не засчитан целиком.
- Шаг 6 предъявлен логом: обе пробы в обычной транзакции прошли без отказа, число строк не
  изменилось. Это положительный контроль; без него вердикт не выносится.
- Шаги 7 и 8 предъявлены РАЗНЫМИ логами, каждый — с чистого файла результата. По каждому напечатано
  дословно: либо строка отказа с текстом и кодом состояния, либо явная тишина.
- Вердикт назван по таблице исходов ниже и опирается на СОВПАВШИЕ строки логов, а не на метку:
  - **тишина в 7, отказ в 8** → отказ на уровне ЗАПИСИ. Компенсирующий контроль СУЩЕСТВУЕТ, а проба
    шага 6-е была неразличающей — ровно то объяснение, которое `ADR-033` назвал вторым;
  - **отказ в 7 и в 8** → отказ на уровне ОПЕРАТОРА. Тогда тишина на базе клиента означает одно из
    двух: режим не вступил в силу либо контроля там нет; различает шаг 6-е-БИС задачи `T-0-5`;
  - **тишина в 7 и в 8** → `SET TRANSACTION READ ONLY` запись не отбивает вовсе. Второго рубежа у
    проекта нет, и после `ADR-034` его больше неоткуда взять;
  - **отказ в шаге 6** → проба неисправна, вердикта нет, разбирается причина.
- Строка `RO_FLAG` шага 7 напечатана либо явно названа недоступной с текстом отказа.
- Ни один критерий не закрывается кодом возврата.
