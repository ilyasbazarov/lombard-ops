## Роль

Ты — исполнитель проекта. Законы — `CLAUDE.md`, стандарты — `05_CONVENTIONS.md` Части I и II.
Модель исполнения: ты исполняешь сам в пределах мандата класса A (подготовка запроса владельцу,
формулировка процедуры снятия значений, сборка обезличенного артефакта, локальный коммит). Всё из
перечня класса B (обращение к клиенту за доступом; сам факт подключения по RDP к рабочему месту
клиента; чтение экрана приложения вендора) — только отдельным действием ИЛЬЯСА после явного
подтверждения, никогда исполнителем внутри сессии инструмента: RDP к машине с интерфейсом вендора
физически недостижим из этой сессии (это не облачный ресурс и не команда, а рабочее место человека
на стороне клиента). Перед каждым запросом подтверждения — ОТДЕЛЬНОЕ сообщение: что именно
исполняется, на каком объекте, чем откатывается.
`Done` — только по предъявленному логу (здесь — по предъявленному артефакту и скриншоту, который
живёт вне репозитория), не по коду возврата.

**Красная линия этой задачи, отдельная от общих (`00 §4`, `ADR-001`):** ни один номер договора и ни
одно имя клиента не попадает в репозиторий ни в каком виде (`ADR-039` п.4, разрез санитарии).
Скриншот экрана — первоисточник — **никуда не коммитится, ни в этот репозиторий, ни в сателлит**:
приватный репозиторий-сателлит `lombard-ops-vendor-schema` перманентно выведен из объёма поставки
решением `ADR-057` п.3 («вне поставки»), и это НЕ временная задолженность до какой-то будущей
задачи — задачи, которая создаёт сателлит, в карте нет. Скриншот делает и хранит Ilyas у себя, вне
обоих репозиториев, тем же способом, каким уже решено для `T-0-3b` (`ADR-039` п.1: первоисточник
оракула не коммитится никуда).

## Цель

После этой задачи: у Ilyas есть рабочий RDP-доступ к рабочему месту с приложением PawnShop вендора
«Алгоритм», доступ проверен предъявленным скриншотом экрана конкретного договора с датой снимка;
в репозитории записан воспроизводимый порядок снятия эталонных значений с экрана (какие поля
искать, как их читать, как датировать снимок); на трёх контрольных договорах эталонные суммы сняты
и положены в `/reference` обезличенной таблицей. Это открывает оракул для `T-0-4b`/`T-0-3b` —
сверку нашей формулы баланса с показанием вендора, которая сейчас блокирована `Q-18`/`Q-19`.

## Ограничения

- К БД PawnShop эта задача не обращается вовсе — работа идёт с ИНТЕРФЕЙСОМ приложения вендора
  (визуальный оракул), не с СУБД напрямую.
- Скриншот-первоисточник, номера договоров, имена клиентов — в репозиторий не попадают никогда
  (`00 §4`, `ADR-001`, `ADR-039` п.4). Их место — у Ilyas, вне обоих репозиториев (сателлит
  перманентно вне поставки, `ADR-057` п.3).
- Договоры в артефакте нумеруются порядково («договор 1»…«договор 3»); соответствие порядкового
  номера реальному не переносится в репозиторий ни в каком виде (`ADR-039` п.2).
- Endpoint и креды рабочего места вендора — вне репозитория (`00 §4`); в `11_INFRA_FACTS.md`
  записывается только факт наличия доступа и дата, не значения.
- Один скрипт/действие на ШАГ брифа; диагностику и действие класса B в одном блоке не объединять.

## Шаги

1. **Запрос клиенту (класс B, отдельное сообщение владельцу ДО отправки).** Executor формулирует
   для Ilyas точный текст запроса к клиенту: RDP-доступ к рабочему месту, на котором установлен
   клиент приложения PawnShop, для самостоятельного снятия эталонных значений начислений по
   отдельным договорам (не к серверу БД — это уже есть, `T-0-8`). Карточка перед отправкой: что
   исполняется (обращение к клиенту с запросом ресурса), на каком объекте (рабочее место с
   приложением вендора у клиента), чем откатывается (доступ можно не выдавать или отозвать —
   необратимого действия нет). Ilyas отправляет запрос сам, вне сессии инструмента.

2. **Получение и первая проверка доступа (класс B, исполняет Ilyas вне сессии).** Ilyas подключается
   по RDP к выданному рабочему месту, открывает приложение вендора, находит один договор, делает
   снимок экрана с датой. Результат сессии: снимок существует у Ilyas (не передаётся в диалог с
   Claude — экран несёт номер договора и потенциально имя клиента).

3. **Executor формулирует порядок снятия значений (класс A, стол).** По описанию Ilyas того, что он
   видит на экране (без номеров договоров и имён — только структура экрана: какие поля, в каком
   разделе интерфейса, как переключиться на другой договор), executor записывает воспроизводимую
   процедуру: где искать договор в интерфейсе, какие суммы читать (аналог `balance_amount`), как
   зафиксировать дату снимка. Процедура пишется так, чтобы её мог повторить другой человек, не
   видевший это приложение прежде.

4. **Три контрольных договора (класс B, исполняет Ilyas вне сессии, по процедуре шага 3).** Ilyas
   выбирает три произвольных договора, по каждому снимает: дату снимка, эталонную сумму(ы) с
   экрана. Передаёт executor'у только порядковую привязку («договор 1» = такая-то сумма на такую-то
   дату), без номеров и имён.

5. **Сборка обезличенных артефактов (класс A, стол).** Executor кладёт в `/reference` процедуру
   (шаг 3) и таблицу трёх контрольных договоров (шаг 4) — обезличенно, дата снимка + суммы, без
   идентификаторов.

## Критерии приёмки

- Скриншот экрана конкретного договора с датой снимка предъявлен Ilyas (существование факта
  подтверждается его словом в сессии — сам файл в репозиторий и в диалог не идёт).
- Порядок снятия эталонных значений записан шагами в `reference/T-0-19_oracle_access_procedure_<дата>.md`,
  воспроизводимыми человеком, не видевшим интерфейс вендора прежде.
- Таблица трёх контрольных договоров в `reference/T-0-19_oracle_control_contracts_<дата>.md`:
  дата снимка, порядковый номер, эталонная сумма(ы) — по каждому из трёх.
- Ни одного номера договора, ни одного имени клиента, ни одного значения токена/пароля ни в одном
  из двух артефактов — проверяется сплошным просмотром обоих файлов перед коммитом.
- Ни один критерий не закрывается кодом возврата: доступ подтверждается предъявленным скриншотом
  (со слов Ilyas в сессии), не «RDP прошёл».

## Что вернуть человеку

- Два артефакта в `/reference` (имена файлов — из раздела «Файлы на запись» с реальной датой).
- Сообщение владельцу — по форме `05 §I`: шапка «Сделано: · Нужно от владельца: · Рекомендация:»,
  затем не более 25 строк; артефакты называются именами файлов, скриншот и номера договоров в чат
  не идут никогда.
- Если клиент не выдал доступ или процесс затягивается — это называется строкой, не растворяется:
  задача остаётся `todo` с указанием, чего конкретно ждём.

## Вне scope этой задачи

- **Массовая сверка на 200+ договорах** — это `T-0-4b`, отдельная задача, зависящая от этой.
- **Правка формулы `03 §4`** — эта задача не считает баланс и не сравнивает его с формулой; она
  только добывает эталонные значения. Сравнение и патч формулы — `T-0-3b`.
- **Создание приватного репозитория-сателлита** — навсегда вне поставки (`ADR-057` п.3), этой
  задачей не заводится и не ждётся.
- **Доступ к самой БД PawnShop** — уже есть (`T-0-8`); эта задача про ДРУГОЙ канал (визуальный
  интерфейс вендора, не СУБД).
- **Постоянный регламент повторной сверки после даты поставки** — предмет наблюдения `00 §6.2`, не
  этой задачи.
