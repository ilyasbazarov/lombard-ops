## Ограничения

- **Все ресурсы — на аккаунте клиента** (`00 §4`). Ничего не создаётся в личном проекте.
- **Регион `europe-west3` обязателен для КАЖДОГО ресурса.** Приёмка требует списка, доказывающего,
  что ресурсов вне региона нет.
- **Секреты и endpoint'ы — вне репозитория.** В артефакт идут имена ресурсов и их регионы, не
  значения.
- **Не-идемпотентные операции** (`create`, `deploy`): обрыв или timeout → слепой повтор запрещён,
  сначала read-only диагностика (`describe`/`list`), потом доисполнение недостающего хвоста.
- **`SELECT *` и autodetect запрещены** — схемы задаются явно (`05 §II`).
- **Пустая выдача при нулевом коде возврата — гэп наблюдения**, а не «ресурсов нет».

## Шаги

### Шаг 1 — сверка входов и прав (класс A, только чтение)

Без создания чего-либо: `gcloud config list`, `gcloud projects describe` по идентификатору проекта,
`gcloud services list --enabled`, `gcloud auth list`. Предъявить: активный аккаунт, активный проект,
роль текущего пользователя.

**Ожидается:** идентификатор проекта совпадает с `11_INFRA_FACTS`; аккаунт — Ilyas; роль editor.
Расхождение любого из трёх — СТОП и вопрос владельцу, а не продолжение «похоже, то же самое».

### Шаг 2 — включение API (класс B)

Один скрипт на шаг. Включить: BigQuery, Cloud Storage, Cloud Run, Cloud Functions, Cloud Scheduler,
Secret Manager, Artifact Registry, Cloud Build, IAM.

- **Карточка подтверждения.** Что исполняется: включение перечисленных API в проекте клиента. На
  каком объекте: проект `project-c451b48a-07ae-4de4-961`. Чем откатывается: `gcloud services
  disable <api>`; включение API само по себе денег не стоит и ресурсов не создаёт.

**Ожидается:** `gcloud services list --enabled` печатает все перечисленные — предъявить списком.

### Шаг 3 — датасет и таблицы (класс B)

`bq mk --location=europe-west3 lombard_ops`, затем DDL из `sql/ddl/lombard_ops.sql`, написанного по
`02 §2`. DDL пишется в файл ДО применения и печатается целиком в лог.

- **Карточка подтверждения.** Что исполняется: создание датасета и ШЕСТИ таблиц по `02 §2`. На каком объекте:
  BigQuery проекта клиента, регион `europe-west3`. Чем откатывается: `bq rm -r -f lombard_ops`;
  данных в таблицах нет, потеря невозможна.

**Ожидается:** `bq show --format=prettyjson lombard_ops` печатает `"location": "europe-west3"`;
`bq ls lombard_ops` печатает ШЕСТЬ таблиц — ровно те, что перечислены в `02 §2`; седьмой в контракте данных нет. **Если location оказался `US` — датасет удаляется и
пересоздаётся, а не оставляется**: регион датасета в BigQuery не меняется.

### Шаг 4 — бакеты (класс B)

Три бакета в `europe-west3`, единый доступ на уровне бакета, **публичный доступ запрещён**.

- **Карточка подтверждения.** Что исполняется: создание трёх бакетов. Чем откатывается:
  `gcloud storage rm --recursive`; бакеты пусты.

**Ожидается:** `gcloud storage buckets describe` по каждому печатает `location: EUROPE-WEST3` и
отсутствие публичного доступа — предъявить по всем трём.

### Шаг 5 — сервисный аккаунт и роли (класс B)

Создать `lombard-pipeline@`, выдать минимальный набор: запись в BigQuery в пределах датасета, чтение
и запись в три бакета, чтение секретов. **Роли уровня проекта уровня `editor`/`owner` не выдаются** —
если минимальный набор не собирается ролями, названными поимённо, это стоп и вопрос архитектору, а
не «дадим пошире, потом сузим».

- **Карточка подтверждения.** Что исполняется: создание сервисного аккаунта и привязка ролей.
  Чем откатывается: удаление аккаунта и снятие привязок.

**Ожидается:** `gcloud projects get-iam-policy` печатает привязки этого аккаунта — предъявить
списком ролей; ключ сервисного аккаунта **этой задачей не создаётся** (он понадобится агенту в
`T-0-8` и заводится там, чтобы не лежать без дела).

### Шаг 6 — секреты-заглушки (класс B)

Создать три секрета с плейсхолдерными версиями. **Значения не печатать.**

- **Карточка подтверждения.** Что исполняется: создание трёх секретов с заглушками. Чем
  откатывается: `gcloud secrets delete`.

**Ожидается:** `gcloud secrets list` печатает три имени; `gcloud secrets versions list` печатает по
одной версии на каждый. Содержимое не читается и не печатается.

### Шаг 7 — сплошная проверка региона (класс A, только чтение)

Один запрос, доказывающий отрицательное утверждение «ресурсов вне `europe-west3` нет»: перечислить
датасеты с их локациями, бакеты с их локациями, и напечатать результат целиком. **Пустой вывод
фактом не является** — рядом печатается положительный контроль: тот же запрос находит созданные
ресурсы.

### Шаг 8 — фиксация знания (класс A)

`11_INFRA_FACTS` заполняется через INFRA_PATCH по фактам логов: регион, датасет, таблицы, бакеты,
сервисный аккаунт, секреты. Каждая строка — с датой замера. Ничего «по плану».

## Критерии приёмки

- Каждый ресурс предъявлен командой ЧТЕНИЯ, печатающей его имя и регион, — логом, не заявлением.
- `bq ls lombard_ops` печатает ШЕСТЬ таблиц (`02 §2`); `bq show` печатает `europe-west3`.
- Три бакета предъявлены с их локацией и отсутствием публичного доступа.
- Сервисный аккаунт предъявлен списком привязанных ролей; роли уровня проекта `editor`/`owner`
  в списке отсутствуют.
- Три секрета предъявлены именами и числом версий; **ни одно значение не напечатано**.
- Шаг 7 предъявил сплошной список с положительным контролем: ресурсов вне `europe-west3` нет.
- `11_INFRA_FACTS` заполнен через INFRA_PATCH фактами с датами.
- Ни один критерий не закрывается кодом возврата.
